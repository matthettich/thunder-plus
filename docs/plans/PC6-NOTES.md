## 1. fx.values

`{t:'fx.values', tr, slot, kind:'pump'|'mod', v:[numbers]}`; `tr` 0..31 or 32 (the master chain), as `fx.set`. Sent with `tc.ask` (a reply is needed for refusals).
- **When:** while a native PLAY runs, from PC4's diff (`liveFlush`, one task per 16 ms, last value wins), only when `hello.caps.fxValues` is truthy. A slot whose list is unchanged, whose structure changed (that is an `fx.plan`), or whose list holds a non-finite value (left to the song) sends nothing. Stopped: nothing (the whole song carries it).
- **Cap name:** PP-NOTES / N2-NOTES define the core's `THUNDER_LIVE_CAP_FXVALUES` (0x800) but no name in the hello reply. The page looks for `caps.fxValues` (like `caps.meters2`). **Shell: add `fxValues: true` to the hello caps when it handles `fx.values`.**
- **Values:** the page's own mapping, the same one the plan uses. Pump: `pumpPv(D, f)` on a COPY of the slot after `pumpSync` (the song's slot is never written), the plugin's whole parameter list in its own order (`D.pd.length`, 32 for WIDE, 277 for EQ), each value `Math.fround`ed (float32 on the control side). Modular: `TFX[type].map(f, sr, bpm)` (the table's order, doubles, count = the effect's control count). The core judges the count against the planned one (`npv` / `nmp`). `host.fxSlot` returns `{kind, v}` now (`v` for pump / mod only).
- **Reply handling (the shell answers each `fx.values`):** `{ok:true}`, or `{ok:false, error}` for a refusal (E_ARG: linear-phase EQ, EQ `phase` / `lin_quality` changed, count mismatch, not a hosted slot of that kind; E_STATE), or `{ok:false, busy:true}` / `error:'busy'` for E_BUSY (the ring of 16). A refusal is silent (no toast, no log beyond the first): the slot is marked and its knobs ride in the whole song, which the page sends 250 ms after the last edit anyway (the "existing whole-plan path" for a pump / modular slot is the song; there is no `fx.set` for them). Busy: the current list of that slot is sent again at the next tick. A rejected / timed-out ask counts as a refusal. The mark is dropped at the next accepted song (an EQ made minimum-phase is tried again; at most one refused ask per slot per accepted song), at a new `fx.plan` for that track, and on engine up / down.
- **Decision:** refused slots are not re-sent per knob step (no ask storm for a linear-phase EQ drag). The cost is that after a refusal that was only transient the knob waits for the song.

## 2. Recovery

Shell facts (N2-NOTES H5): on swipe-away the shell writes `recovery.thunder` + `recovery.json`; its copy is the last `song.load` MESSAGE (`{t:'song.load', title, S, vars, rev}`), not the project text or the kit. Events / asks already there: `recovery {title, time, file}` (shell -> page, once after each hello reply, only if a copy exists), `recovery.get {id}` -> `{ok, title, time, file, text}`, `recovery.drop {id}` -> `{ok:true}`.

**New message (the shell must build it): `recovery.put {project}`**, page -> shell, `send` (no reply). `project` is a string: the page's own project file text (`projText()`: `{app:'thunder-project', v:1, build, song, kit}`, the same text File > Save writes; with kit sample audio, so it can be several MB). Rules the page follows:
- every ~10 s (`RCV_MS`), only while the page says the song is unsaved (`projDirty`), only when the text differs from the last put, only with `hello.caps.recoveryPut` truthy (**the shell adds `recoveryPut: true` to the hello caps**), never while a recovery copy is waiting for the person's answer (so it cannot overwrite it), not above 24 million characters (`RCV_MAX`; the shell's `song.load` copy stays then), and the interval grows to 40x the cost of the last stringify on a slow device.
- when the song is saved (`projDirty` false) nothing is sent; the shell already clears its copy on `file.save` / `file.saveAs` success (RecoveryTracker) and should keep the put the same way: **suggested shell behaviour:** store the latest `project` in memory (and, ideally, to `recovery.thunder` as it arrives, atomic temp + rename, not only on `onTaskRemoved`, since an Android kill gives no swipe callback); on `recovery.get` return `text` = the put project if there is one newer than / as new as the `song.load` copy, else the `song.load` copy as today. A put arriving while no save has happened and the tracker says "saved" should still be kept (the page decides dirty).
- **Prompt:** the `recovery` event starts "Restore unsaved changes?" (Restore / Discard) 1.2 s later (host `askRestore`, the page's `askPick`). **Restore:** `recovery.get`; a text with `app:'thunder-project'` is loaded with the page's `loadProjText(text, name, {dirty:true})` (kit, samples, presets, impulse responses: everything a project file has) after a backup of what is open (`backupNow(true)`); then `recovery.drop`. **Only the `song.load` copy:** its `S` is wrapped as `{app:'thunder-project', v:1, song:S}` and loaded the same way: **lost:** the kit (pads / voices / sample audio stay as they are in the open app), preset and impulse-response audio, variations (`vars`), and anything the engine snapshot does not carry; a toast says the kit is not in the copy. **Discard:** `recovery.drop`. **Closed without answering** (Back): nothing is dropped and no `recovery.put` is sent for the rest of the session (it would replace the copy); asked again at the next start. An unreadable copy or a refused restore keeps the copy (a toast for the first).
- The prompt appears once per hello. The `recovery` listener is installed in `subscribe()` in the same tick the hello reply is handled, so an event sent right after the reply is not missed.
