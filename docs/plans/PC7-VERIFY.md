## Findings

### MEDIUM
**M1. The native MIDI path is not gated to the desktop shell: it also turns on for the Android live shell.** `natMidi()` (index.html:8922) is true on `caps.midi === true` alone (client `capOn('midi')`, thunder-core-client.js:929). The Android live shell sends `caps.midi = LiveNative.nativeMidiOn()` (`LiveBridge.kt:163`), true when its MIDI is up, and it sends `midi.ports` / `midi.in` / accepts `midi.cfg` (CORE-BRIDGE 148). So on Android with Sequencer = "Native core (test)", `connectMidi1` (index.html:17941) now builds the `ncore` access instead of Web MIDI, and its outputs' `send()` drops (index.html:~18797): hand-played MIDI out and any page-engine MIDI stop working. PC7-NOTES, HANDOVER and the CHANGES line say "Android unchanged" / "no such caps on Android": not true for `midi`. (`devices`, `inputs`, `rt` are desktop only: Android sends `inputs:false`, no `devices`.) Fix: gate `natMidi()` (and `h7Subscribe`'s midi branch) on `NC.hostName === 'desktop'` or on `caps.devices` as well; add an inert-test case with an Android-shaped hello (`host:'android'`, `caps.midi:true`).

**M2. The shell still re-asks the old rate after an unplug (shell-side, not the page).** `devFallback` (bridge_session.cpp, "c.outId.clear(); c.bufferFrames = 0; // ... the old rate is asked again (converted if the new device runs at another)") keeps `sampleRate`; and the input opens at the engine rate (`ic.sampleRate = host_.sampleRate()`, devOpen and hello), which need not be one of the input device's `rates`. So "the page must never request any other rate (including fallbacks after unplug, input open)" holds for everything the PAGE sends (see Rate rule below) but not for what the shell does by itself. The PR records this (Q2, Q3, "For native"); it needs the native fix before the F-review rule is true end to end. The page-side mitigation (zero `aset.natSr` after a fell-back `reopened`, index.html:16011) only affects later page requests; it does not change the shell's own rebuild. Not a blocker for this PR if the native fix is tracked; do not claim the rule is fully met.

### LOW
- L1. `NC.detach()` runs `h7Reset()` which clears `LS` (all `NC.listen` listeners), but `natAudInit` is guarded by `natInit === C` (index.html:16021) and the same client object is reused on re-attach, so after a detach/attach the `dev` toasts and the MIDI-in listeners (`NMC.off`) are not re-registered until the page reloads. Only matters when the client is detached and re-attached.
- L2. `h7Hello` seeds `DV.wantOut` with the OPEN device's id (`audio.id`) until `dev.list` answers (thunder-core-client.js, h7Hello). A `dev.open` sent in that few-ms window (nothing sends one at start-up) would pin the default output to a concrete id. Harmless in practice.
- L3. After an output fell back, `DV.wantOut` stays the unplugged id (correct: the shell keeps it saved), so a later input pick resends `out:<unplugged id>`, `sr:0`. The shell then falls back again without a rebuild loop; just noisy (`fellBack` toast on an input pick). Not wrong.
- L4. A mono pick gives `rcdMsg({ch:[L, L]})` with the same Float32Array twice (index.html natFinish). Fine if rcdCollect does not mutate in place; the Electron path does the same shape. Worth one look on the Mac.
- L5. PC7-NOTES Q1: Rate / Buffer rows rely on localStorage; after clearing storage they read "Device" while the shell may run another rate. Display only; shell fix (`want:{...}` in `dev.list`) listed.
- L6. `take` metadata `hostNs0` / `latencyFrames` are fetched and unused; "Measure gear delay" is refused on the native input. Both documented.

## Evidence by area

**1. Protocol match (all match; no mismatch found).**
- `dev.list` reply `{ok, devices[{id,inId,outId,name,backend,inputs,outputs,ins,outs,rates,isDefaultIn,isDefaultOut}], out, in, audio{open,name,id,sr,buf,latOut}, input{open,name,id,channels,sr,buf,latIn}}` (bridge_session.cpp devList/audioBody, audio_devices.cpp:37): client `takeList` / `devRates` / index.html `natAudSync` read exactly these (outId, inId, outputs, inputs, rates, isDefaultOut/In, latOut, latIn, channels).
- `dev.open {out, in?, sr, buf}`: the translator (bridge_translator.cpp:245) wants `out`/`in` strings, `sr`/`buf` numbers; client sends `out` always as a string, `in` only when named, numbers otherwise (thunder-core-client.js devOpen). `sr` 0 or 8000..384000, `buf` 0 or 16..8192 (audio_devices.cpp:52): client sends 0 or a validated rate, `buf` 0 or 16..8192. Reply `{ok, rebuilt, fellBack, requested, audio, input, inError?}` read as such; error `{ok:false, error, err}` read via `r.error || r.err`.
- `rec.arm {ins:[0-based]}` (reply `{ok, nch, inputs, sr, latIn}`), `rec.start` (reply `{ok, hostNs}`; page uses `r.hostNs`), `rec.stop` (reply `{ok, take, frames, sr, nch, hostNs0, latencyFrames, gaps, full, dropped}`): match. `take {take, ch, off, n}` + `take.chunk {rid, c, off, b}`, reply `{ok, sr, nch, frames, hostNs0, latencyFrames}`: the bridge's own `tc.take` (desktop_bridge.js:59) reads `p.c`, `r.nch`, returns `data[]`, which `recTake` uses; the 8M-frame (32 MiB) step stays under the 64 MiB limit. `take.free {take}` is sent (no reply): matches.
- Events: `dev` kinds `changed{devices}`, `lost{which,id,name?,fellBack?}`, `reopened{which,name,sr,buf,fellBack}`, `changed{wantedBack:'out', id}`; `rec {pk,frames,rec,full,dropped}`; `rec.done {take, partial, why, frames, sr, nch}`: all read with these names. `pk` is per ARMED channel in arm order (input_capture.cpp arm / drain), and the page maps it by `nat.chs.indexOf(c)`: correct.
- `midi.cfg {outs[4], clockOut[4], gearDelay[4], clockIn}`: translator (bridge_translator.cpp:165) reads exactly these, clamps gear to -50..200 like the client. `midi.ports {devs[{id,name}], ins[{id,name,port}], ports, late, sent}`: matches. `rt.snapshot` / `rt.reset`: ask / send; the page just stringifies the reply.
- Hello: `caps.devices`, `inputs`, `rt`, `midi` truthful on desktop; `hello.audio` / `hello.input` bodies read.

**2. Rate rule (page).** The only `dev.open` sender is `devOpen`; it sends `sr` only if it is in the output device's own `rates` (`devRates(out).indexOf(sr) < 0 -> 0`), so a stale `aset.natSr` or a changed Output cannot send a foreign rate. Settings Rate = `[0 Device] + C.devRates(naOut)` (index.html natAudSync); after an unplug-fallback `aset.natSr` is cleared if the new device lacks it (07613256). Input open (`rcdOpenNat`, `devOpen({in})`) goes through the same check. The shell's own rebuild rates: see M2.

**3. Off the native shell.** `natC()` is `NCON() ? NC() : null`; with no `window.thunderCore` the client is not loaded, so `natDev/natIn/natMidi` are null. The new calls in the shared paths (`audStatus`, `audRefresh -> natAudSync`, `rcdOpen1`, `fillIn`, `connectMidi1`, `midiAccessDrop`, `saveMidi -> midiCfgPush`, `rcdCloseIo`, `rcdRateMsg`, `midiLatRun`, `rcdTake`) all short-circuit; `natAudSync` with no shell sets `#audNat` hidden and un-hides rows nothing else hides (checked: no other code touches `audOutRow` / `segLat` / `segARate` hidden). The one changed existing line, `IOAPI` null under `window.thunderCore`: electron/ has no `thunderCore` (grep), so Electron is unchanged. Exception: Android MIDI, see M1.

**4. Recording.** Stop: `rec.stop` -> `take` per channel (channel index k in arm order) -> `take.free` -> `rcdMsg({f0:0, ch:[L,R], done:true})`, same as the worklet's last message; rate = take `sr` (`RCD.natSr`, used by `rcdTake`); length = `frames` from the stop reply (Float32Array(frames) per channel). Unplug: shell `rec.done {partial}` -> `natFinish(nat, id, m)` fetches and frees the take, toast "the take so far is kept". Frees: take freed on every path after the fetch (also fetch failure and `frames < 1`); `rec` / `rec.done` / `dev` listeners are removed in `rcdCloseIo` (`nat.off`); `tc.take` removes its own `take.chunk` listener on reply and timeout. The window closing leaves the shell input open by design. A take that arrives with the recorder not recording is freed.

**5. MIDI in.** `midi.in {f, wallNs, port, bytes[]}` (midi_in.cpp:55; the shell's parser has already assembled full messages, running status expanded, SysEx / active sensing / reset dropped, realtime F8/FA/FB/FC as single bytes): page does `Uint8Array.from(bytes)` -> `onmidimessage({data, timeStamp})`, so the existing `onMidi` byte format (status, d1, d2) and the `st >= 0xF8` clock branch work. Timestamp: `wallNs` (host clock) / 1e6 + lower-envelope offset to `performance.now()`; the client also reads `wall`, harmless. Shell sends `clockIn` handling itself (fit flag) as well as the page's own `clkIn()`; no conflict seen.
