## 2. The tempo settle (#263)

Code: `stLiveBpm(b, songB, playing, now)` + `applyChop(..., live)`: only for sync 2 / 3 and only when `live` (the sequencer's
live `makeSeq`, `o.live`) and only when the note's tempo `b` equals `S.bpm` (a TPO command's tempo, or a fractional tempo from Link /
MIDI clock, is "exact").

(a) **Static tempo: bit-identical.** Same 264,960 cases with the settle active (above), plus 100 notes 100 ms apart at 60 / 131 / 200 / 300 BPM,
playing and stopped: 0 notes at a tempo other than the song's.
(b) Where it is exact: preview, offline render, stems, bounce (`makeSeq` without `live`), a TPO command, and any tempo the seq holds
that is not equal to `S.bpm` (Link and MIDI clock set `tp.seq.bpm` to a fractional value while `S.bpm` is whole, so they take the exact
path: no lag, but also **no relief from the per-note re-render the settle was written for**, so the notes' claim "Link / MIDI clock" is not
true for fractional tempos). The audio-thread core's `applyChop` is an empty stub (the core plays stretched instruments unsynced), the
core change is only the extra argument, and `core/seq-core.js` is byte-identical to `node tools/make-core.mjs` output (checked in a
scratch copy, and `--check` passes on both branches).
**Stale tempo, measured through the real function:**
 - Window is not 300 ms. The 300 ms is counted from the first note that SEES the new tempo, not from the change. A drag 131 -> 140
   ending at t: first note at 140 comes 280 / 335 / 450 / 680 / 1060 ms later for notes every 60 / 125 / 230 / 460 / 900 ms (1060 ms
   for 1800 ms). Each stale note is a loop of the wrong length (6.9% here).
 - First note after PLAY after a tempo edit made while stopped: fine when the last stretched note was more than 1 s earlier (snap). Within
   1 s of the last stretched note (stop, edit, PLAY quickly): the first note uses the OLD tempo (131 not 140), the second the new one.
   Same when a new song is started less than 1 s after a stretched note: first 3 notes (300 ms) at the old song's tempo.
 - **Settled but never applied (must fix):** while the song plays, a change under 0.5% is ignored for good. S.bpm is whole BPM, so
   from 201 BPM up a 1-BPM edit is ignored (201 -> 202: stretches stay at 201, 0.498% off; 250 -> 251 0.40%; 299 -> 300 0.33%) for as long as the
   song plays (it corrects only after a stop and a replay more than 1 s later). A 32-beat stretched loop is then about 70 ms off the grid at
   its end. This is "a stretched loop at the wrong length after a settled tempo change". At 200 BPM and below, every 1-BPM edit applies
   (131 -> 132, 140 -> 141: 0 error).
(c) Classic STRETCH / LOOP once the tempo is still: identical to beta (item 1), except the sub-0.5%-at-201+-BPM case above, which is
a classic-mode difference from beta while playing, and the up-to-1 s stale window after an edit. Not acceptable as written for the
tolerance case; the worker's own switch (`sy >= 2 && live` -> `sy === 3 && sx === 1 && live`) would keep classic modes exactly as in beta.

## 3. `I.sx`

- Stored only when needed: CONFIRMED. 848 old instruments load and save with no `sx`; `syPut` deletes `sx` for a classic mode; OLDSCHOOL's
  `og ou orp ox opt` exist only while `sx` is 1 (a sync 0 / 1 / 2 instrument with `sx: 1` in the file loads without it).
- A song WITH `sx` (sync 3, sx 1, og 30 ...) opened by `origin/beta`'s loader (and #261's): loads, no throw, `sync` 3 = LOOP, as stated.
  What the older build then SAVES: the instrument as plain LOOP: `sx` and `og ou orp ox opt` are gone from the file, silently (the older
  loader never copies them). So an older build that opens and saves a 660 song converts every OLDSCHOOL instrument to LOOP for good.
  Expected for this app's loaders, but HANDOVER says only "an older build plays it as LOOP"; it should also say it saves it as LOOP. (note)
- Corrupt values on #263: `sx` "OLDSCHOOL" / "oldschool" / 2 / -1 / null / false / {} / 1e9 / "x" / undefined load as the classic mode (sx
  dropped, no params); 1, 1.9, "1", true, [1] load as OLDSCHOOL (accepted by `Math.trunc(+x)`, harmless). Parameters: NaN and strings get the
  default; out of range is clamped (og 0.5..250, ou 0..6, orp 0..3, ox 0..50, opt -24..24); absent params with `sx` 1 get the defaults.
  One quirk: `og: null` or 0 or negative loads as 0.5 ms (a buzz) instead of the default 12 (`+null` is 0). (note)
- PERFORM parts: `partSnap` is a JSON clone of `S.insts`, so `sx` and the five parameters are copied and `partLoad` clones them back. But
  `normParts` keeps a part's `insts` raw (never normalised, for every field, as before): a hand-edited part with `opt` 1e9 renders NaN for
  the whole OLDSCHOOL buffer (measured: 44100 of 44100 samples NaN). Not reachable from the UI. (note)
- Every write of `I.sync` goes through `syPut` (loop, record-fit, SYNC TO LINES, the picker): no path leaves a stale `sx`.
- SYNC TO LINES sheet and the INST page both read `syPick(I)` from the instrument and write with `syPut`: in step by construction (code
  read; NOT run in a browser here).
- Leaving OLDSCHOOL (even one step of the left / right keys on SYNC) deletes the parameters; Undo brings them back (the worker's choice 4). (note)

## 4. OLDSCHOOL correctness (my own signals: exact ramp, sines, noise, impulse train, unique-valued permutation; no drum loop in `sounds/` (the two
`.thunder` songs hold samples only inside the kit, not as a file I could use), so the "break" is the synthetic one)

- Output length: CONFIRMED exact. 169 cases (BPM 60..200, LPB 3..16, 1 to 1024 lines): length == `round(lines / lpb * 60 / bpm * sr)`, 0 off.
- Independent reference (my own 15-line implementation of the design: hard-cut grains, start = round(L * ramp(k g / T)) clamped, rate 2^(st/12),
  linear interpolation): 256 renders at SMOOTH 0 (4 ramps x 4 pitches x 4 grains x 4 length / tempo cases) are bit-identical to `oldschoolData`.
  This is the independent check on the PR's self-recorded golden (which only says "unchanged").
- Discontinuities only at grain boundaries at SMOOTH 0: CONFIRMED on 40 renders (10 grain sizes x 4 ramps, unique-valued source so every
  jump is certain): jumps ON a boundary 7 to 4009, OFF a boundary 0. Grain length = LOOP: 12 ms -> 529 samples (11.995 ms), 0.5 ms -> 22,
  250 ms -> 11025; each line division at several BPM / LPB (1, 1/2, 1/4, 1/8, 1/16, 1/32 line at 131/4, 60/8, 200/4, 131/8, 174/3) is within
  one sample of `division * 60 / bpm / lpb`.
- Ramp: the recovered start of every grain equals the definition (max error 0 samples) and the analytic FWD / REV / PING / EASE curve; FWD
  starts at 0, REV at the end, PING goes there and back (ends near the start), EASE is the smoothstep. "Reaches the end": the highest sample
  read is L-2 for L = T and a 12 ms grain (the last sample is never read), 99.2 to 99.9% of L for 12 to 50 ms grains when the sample is 1.5x the
  length, 95.9% for 250 ms grains (the last ~4% of the sample is never played: the last grain starts at L*(1 - g/T)). (note)
- PITCH: grain playback rate = 2^(st/12) measured by zero crossings on a 1 kHz sine at -24, -12, -5, 0, 7, 12, 24: error under 3e-6; length
  unchanged (88200 at every setting). NaN: 0.
- SMOOTH: the crossfade itself is fine: in the body of the render the max step is 1.5x the source's at 5% (220 Hz sine, 12 ms; 3.0x at a
  0.5 ms loop), 1.13x at 20%, 1.10x at 50%; 1 kHz sine 1.11 / 1.03 / 1.02; noise 1.00; hard cut for comparison 31x / 7.9x / 1.0x. Peak never
  above the source's. **But a defect at the end (and start):** the crossfade reads past the sample (zero fill) because `p` is kept inside the
  sample only for the grain body, not for the `xf` samples read beyond it. In the last 5% of an FWD render the max step is 9.1x the source's at
  12 ms / 50% (220 Hz), 6.8x at 35%, 10.7x at 0.5 ms / 20%, 13.1x at 50% (a click of up to 0.23 on a 0.8 sine). REV, PING, EASE read before
  sample 0 (j < 0 gives 0) in the same way. Material that ends in silence does not click. **A setting can click louder than SMOOTH 0:** 13 of
  2520 renders (5 sources x 6 grains x 4 ramps x 3 pitches x 7 smooth values) step more than the same material at SMOOTH 0: up to 2.42x (100 ms
  FWD +7 st 50%: the end overrun), and 1.0 to 1.25x in 12 more (REV / PING). Fix: clamp the read positions into 0..L-1 (hold the edge sample,
  not zero) or shrink the fade at the ends. (should fix)
- Extremes, all finite and in range, no NaN: LOOP 0.5 ms and 250 ms (FWD, PING, smooth 0 / 50), a sample shorter than a grain (30 ms in 250
  ms), 10 samples, 1 sample, 0 samples (silence), 60 s sample to 32 s, sync length 1 line (5050 samples) and 1024 lines (5.2 M samples, 117 s),
  PITCH +-24, mono and stereo (each channel is the same function, same state). Slowest: 2.5 s for a 60 s sample stretched to 1024 lines at
  60 BPM (11.3 M samples, 0.5 ms grain, smooth 50, +24 st), 1.26 s for 1024 lines at 131 BPM; typical 10 to 300 ms. These run on the main
  thread today (HANDOVER item 3 says so). Corrupt PERFORM part (above) is the only NaN.
- Today's LOOP mode still bit-identical: item 1.

## Findings

- F1 (#263, must fix): `STQ_TOL`: while playing, a tempo change under 0.5% is ignored for good, so from 201 BPM up every 1-BPM edit (and any
  fractional tempo equal to `S.bpm`) leaves GRANULAR / LOOP / OLDSCHOOL loops 0.33 to 0.5% off until a stop and a replay more than 1 s later.
  Beta applies it at the next note. Fix: drop the tolerance (S.bpm is whole BPM; jitter is not a case here).
- F2 (#263, should fix): the 300 ms is counted from the first note that sees the new tempo, not from the change: stale for 0.28 to 1.06 s after
  a drag settles (notes every 60 ms to 900 ms); first note after PLAY or a new song within 1 s of the last stretched note uses the old tempo. Fix:
  stamp the change time (S.bpm setter or `stq.at` from the real change) and snap on `tStart`.
- F3 (#263, should fix): classic GRANULAR / LOOP are affected by the settle (F1, F2); the worker's switch `sy >= 2 && live` -> only OLDSCHOOL keeps them
  exactly as beta. Decide with the owner; with F1 and F2 fixed the classic modes are identical to beta once still.
- F4 (#263, should fix): SMOOTH > 0 reads zeros past the sample's ends: a click at the end of FWD / EASE renders (and the start of REV / PING),
  up to 9 to 13x the source's step on tonal material, 2.4x louder than SMOOTH 0 at worst.
- F5 (#263, note): Link / MIDI clock (fractional tempo) are not covered by the settle (exact path): no lag, no relief either.
- F6 (note): older builds save an OLDSCHOOL song as LOOP; the last 1 to 4% of the sample is never read by FWD with long grains; a corrupt PERFORM part
  can give NaN; `og: null` loads as 0.5 ms; leaving OLDSCHOOL drops its settings (Undo restores).

## Verdicts

- #261 (build 659): **MERGE.** Old songs identical on every check; no must-fix finding. (Its full test failure is the FlexCore test #262 fixes.)
- #263 (build 660): **MERGE AFTER FIXES**: F1 (must fix), F2 and F4 (should fix), decide F3. OLDSCHOOL itself measures as designed; old songs identical
  at a static tempo.
