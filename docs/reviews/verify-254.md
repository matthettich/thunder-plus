## 5. No added block of delay - CONFIRMED for the graph, with one caveat
- The host has no ordering code of its own: every track has its own nodes; a Track In of another track reads that track's `p -> fdl -> splitter -> merger -> input 4/5` of the bus node. Order is the Web Audio graph's topological order, so it is the same for the page (live context) and for offline render / stems (`makePlayer` is shared; `pass()` builds the same nodes then `busSync()`). It does not depend on node creation order and is recomputed by the browser after any rewire (edit, CHN toggle, `busSync` rebuild). The PR's own test does call `A.process` then `B.process` by hand, so it only proves the worklet adds no latency; it is not evidence about the host.
- My own check, headless Chrome, OfflineAudioContext, two pass-through worklets, A -> gain -> DelayNode(0) -> splitter -> merger -> B input 4: an impulse at sample 200 arrives at 200, with A created first or second. So same block, creation order irrelevant (Chrome only; Firefox and Safari NOT CHECKED).
- CAVEAT (F2, note/should fix later): when the patch has a Sidechain Out (`chnSends`), `sendSync` connects every chains node's output 1 -> sendBus -> sendDly -> every node's input 3. That makes 08 -> fdl -> 14 -> sendBus -> sendDly -> 08 a graph cycle. By the Web Audio spec a DelayNode inside a cycle is clamped to at least one quantum, so `fdl` (set to 0) becomes 128 samples (2.7 ms at 48 kHz): the bus-into-bus feed would be one block late, and `pdcPlan` does not know. I could not get my cycle test to run in headless Chrome (not confirmed), so this is by spec + reading. It exists on `beta` too for any source with its own chains node feeding a bus; the PR makes it likelier because middle buses always have nodes.
- Stale order: none found; wiring is rebuilt by `busSync` (key = plan + node identity).

## 9. Live edit of the plan while playing (owner's 17 dB drop on build 647)
Read: `chains/mod(op)` (a cable edit) puts the op in the patch, sends it to every node, `tapsSync`, `chainsAutoOn`. The audio re-route happens when the editor autosaves (`save` -> `chainsChanged` -> `chainsPush`): `rtFx(t)` -> `routeTrack(t)` for every track with `chainsFeed(t)` or a chains node, and each `routeTrack` ends in `busSync()`. `busSync` is global: its key is the whole plan + node identity; on a change it disconnects every bus's mergers / splitters, gives every `_routed` source its `dl -> out` back, then rewires the new plan and cuts the new pure sources. So old sources are restored, the old bus is dropped, the new end bus is wired, whichever track's `routeTrack` triggered it. CHN toggles go through `chainsFeedChanged` -> `rtFx` -> same path (`chnOut`/new node, then `busSync`).
- Simulated (the real `busSync` text with a mock graph, plan from the real `busPlan`, on `beta` and the PR): A (bus 08) -> B (+ Track In 08 -> Chain Out 14) -> A -> B -> CHN off / on on 08 -> CHN off / on on source 01. Every track keeps exactly ONE route to the master in every state, on both. No silent track, no doubled track, no orphaned feed, from wiring alone. (On `beta` after the edit the eight sources go dry because 08 is "not a bus": the designed MISS state, and the loudest source through a bus compressor / limiter / makeup would sound different; the PR makes that edit work instead.)
- The audio-thread core: `coreSong` (100 ms after a save) sends a patch op; the core resets its plan cache. So the core's plan is current within 100 ms, BUT `busT` (tracks whose notes are dropped) is computed once per `makeSeq` (page and core), so a track that stops / starts being a bus keeps its old note rule until the next PLAY. Same on `beta` and the PR.
- FINDING F3 (should fix; both `beta` and the PR; the PR neither fixes nor worsens it, but deeper solo makes more edits plan-dependent): `routeTrack` / `chainsPush` never call `applyMix`. The per-track gains (`g`, `pre`) come from `audible()`, which depends on the plan. If solo or mute is set while a cable edit changes the plan, the gains stay on the OLD plan until the next `applyMix` (any mixer change; PLAY and STOP do not call it). E.g. solo 08 keeps sources 1-6, 9, 13 audible; the edit makes 08 not a bus on `beta`: the sources should now be silent (not soloed), but stay audible; the reverse edit leaves them silent while they should play. That can leave a track silent or doubled until the next fader / solo move, surviving STOP / PLAY, without an audio restart. Fix: call `rt.pl.applyMix()` at the end of `chainsPush` (and after `chnOut` / CHN toggles). This is a candidate for the owner's report only if a solo or mute was set at the time; I could not produce a 17 dB drop without that and did not find another stale state. NOT CHECKED: audio level in a real browser.
- Window: between the cable edit and the autosave (about 1 s) the plan (patch) is new but the wiring old.
