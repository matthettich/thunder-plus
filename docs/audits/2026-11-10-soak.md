# Soak test of audio stability, 10 Nov 2026

Tool: `tests/sweep/soak.mjs` (new, see the README section "Soak test"). Build: `beta` at aaf7554, no app code touched.
Raw samples: `tests/sweep/out/soak-*.json` (gitignored, 85 samples per run, 5 s apart).

## Bottom line

**No leak found in 10 and 8 minutes of real-time play with the usual actions.** After a forced GC the JS heap grew 0.03 to 0.07 MB per
minute (bound 1 MB/min). DOM nodes, event listeners, documents, intervals, pending timeouts, live voices, AudioNode / GainNode /
AudioWorkletNode / AudioBuffer / MessagePort wrappers, the app's own queues and caches, and localStorage all returned to the same
level after every STOP / PLAY and every screen tour. Four things worth knowing are below (none is a leak); the audio-health numbers
are mostly machine load and have to be repeated on a quiet machine.

## What was run

| run | command | length | machine load (1 min avg, mean / max) |
|---|---|---|---|
| page sequencer, desktop 1400x900 | `--minutes=10 --seq=page` | 10 min | 3.6 / 4.8 |
| audio-thread core, desktop | `--minutes=10 --seq=core` | 10 min | 3.1 / 4.7 |
| page sequencer, phone profile | `--minutes=8 --phone --seq=page` | 8 min | 2.4 / 3.1 |

Plus one 3 minute smoke run (not scored) while building the tool. 2 CPUs shared with other agents (load 2 to 5 the whole time, so
about 100 to 250% over-subscribed): **every timing number below could be load noise.** Chrome 153 headless, no audio device
(`ctx.playbackStats` exists, average latency 31.3 ms). Song: `sounds/ELECTRO.thunder`. Phone profile = touch, Mobile setup, 412x915,
CPU throttle x4 (CDP), page sequencer. Schedule in every run: STOP then PLAY every 60 s, screen tour (6 screens, Synth, Waves, Chains,
back) every 120 s from 90 s, Settings + the pump window of the song's "pverb" slot + waves/chains screens every 180 s from 150 s, one
song reload (`__seqTest.load`, the `setSong` path) at half time. Fits start after a 2 minute warm-up. Verdict rule: a count FAILs
only when its slope is over the bound, it is higher in the last third than the first third, and it is still rising in the second half
(a step is not growth). DOM nodes and listeners are judged on each minute's lowest value. Bounds were chosen from the 3 minute smoke
run and the first 10 minute run, then the first two runs were scored again with the final rules (`--rescore=`): the first page run
printed 4 FAIL with the first rule set (DOM nodes and listeners sawtooth, AudioParam wrappers, canvases); all four were the
metric being wrong, not the app, and are explained below.

## Findings

Ranked by what they would cost in a 2 hour session.

**1. DOM churn while playing: about 500 text nodes per second (low; phone more than desktop). Not a leak.**
Evidence: CDP `Nodes` climbs about 1,700 per 5 s sample (15.2k to 21.4k in 25 s on the phone run, 16.3k to 21.7k on desktop) and falls
back to the same floor (15.2k / 22.7k) at every forced GC and every STOP; the per-minute floor was flat for 10 minutes. A
`MutationObserver` on the tracker for 5 s while playing counted 2,300 to 3,200 added nodes: `#tTitle`, `#tInfo`, `#tArrSub`,
`#dkStripT` (88 each, about 18 Hz), `#tState` (264), and the `<output>` value readouts in rows (550 to 620) on all four screens tried
(song, phrase, mixer, fx), plus about 950 `.mt` / `.mm` spans per 5 s on the Mixer. Where: `draw()` (index.html line 27548) assigns
`$('tTitle').textContent = title` (27759) and `$('tInfo').textContent = info()` (27767) on every redraw even when the string is
unchanged, and a text node is replaced each time. Suggested fix: compare with the last string and assign only on change (a small
`setText(el, s)` helper for the per-frame readouts). Effect: less garbage for the GC, fewer style/layout invalidations; on a phone
in a 2 hour session it is steady GC pressure, not memory growth.

**2. The audio-thread core had about 10x the dropouts of the page sequencer in this environment (unproven, repeat on a quiet machine).**
Core run: `glitch.n` 15 to 248 (24.6 per minute, 2.48 s of underrun in total, latest note up to 924 ms late, 4 notes dropped at the song
reload). Page run on a similar load: 26 to 47 (2.4 per minute, 0.47 s, 0 ms late, 0 dropped). The core run's dropouts came in bursts (+48 in the
start-up minute, +51 in the minute of the song reload, +16 to +21 in minutes 1 to 4), but the rate stayed at 11 to 35 per minute at load
2.2 to 2.5 (minutes 6 to 9), so it is not only a load spike. With the CPU over-subscribed the audio thread competes with other processes; the core does more work
there (sequencer plus voices on the render thread) so it is the one that misses deadlines first. Cannot separate that from a real
cost difference without a quiet machine and a 20 minute A/B. The app's CPU meter read 0.65 to 0.72 on core against 0.49 to 0.62 on the
page sequencer (also load dependent).

**3. The song reload (`setSong`) and the start of the session cost 3 to 14 s of main-thread long tasks (low; one-off).**
Per minute: the minute of the reload had 167 long tasks / 13.8 s on page, 33 / 3.3 s on core, 184 / 13.2 s on the throttled phone
profile; the first (cold start) minute had 154 to 232 tasks / 12 to 19 s. Every other minute had 2 to 7 tasks (0.2 to 1.6 s). So:
loading ELECTRO (856 kB, 32 tracks) plus re-creating the waves / chains frames is the cost, once per load. It is the same order as
cold start. The reload does free the two frames (documents 3 to 1 on the reload, back to 3 on the next visit), which is the
behaviour the code comment promises. Machine load multiplies these numbers.

**4. Page sequencer "moved on" rate on a throttled CPU: 144 times in 8 minutes, about 19 per minute, constant (info).**
`PB.pg.re` (index.html line 22287: the tick found the song's time more than `max(0.15, outLat + 0.05)` s behind the audio clock on a
touch screen and re-anchored it). Desktop page run: 11 in 10 minutes; core: not exposed. Constant rate, no growth, so not a leak; it
shows how thin the margin of the page sequencer is on a slow CPU (CPU x4 plus load 2.5), which is what the core is for. Not a phone
measurement.

Not findings but looked like them, and are bounded:

- **`PB.log`** reaches 391 of its 400 cap and is cut by 100 (`pbLog`, "if (PB.log.length > 400) PB.log.splice(0, 100)").
- **`VAR.map` / `VAR.bytes`** stayed 0 (ELECTRO has no MUT / GEN), so the cache was **not exercised**; it is capped at 48 MB, oldest
  out first (`varPut`, line 10666). `VAR.bufs` is a WeakMap per context.
- **`padSrcs`** entries are deleted on the source's `ended` event (`padTrack`); `MOLED` is pruned by `moledPrune` and capped at 4,096;
  `MOB.q` and `tp.q` stayed at 0 and 5 to 8.
- **AudioParam wrappers** step up with actions (page 24 to 277 near 430 s, core 17 to 168, phone 32 to 130) while AudioNode and
  GainNode counts stay flat (about 465 and 260). A param's JS wrapper is created lazily the first time the page touches it and lives
  as long as its node, so it is bounded by nodes times params per node (0.3 to 0.65 per AudioNode, the check is at most 4). I could not
  pin down which action makes each step (the objects are counted every 30 s only), so this is "flat after the step", not proven.
- **Canvas elements** 4 to 9 on desktop (screens build theirs on first visit), 4 flat on the phone. Marked "watch" in the tool.
- **Renderer RSS** moves between 480 and 880 MB in every run without a trend (the core run's fit says +8.5 MB/min but the last third
  is not above the first by more than the noise and it falls again in minute 9). Wasm memories and decoded audio live here, not in the
  JS heap. A 2 hour run is needed to be sure.
- **localStorage** 870k to 875k characters: the first autosave after the first actions, then flat.
- The DOM node count's 15.2k to 46k swings: the sawtooth of finding 1 plus the waves / chains frames (about +6.5k nodes while loaded).

## What this soak cannot see

- A phone's real audio stack (AAudio / Oboe, Bluetooth latency, battery saver, thermal throttling). The x4 throttle only
  slows the page's JS, not the audio thread, and the machine has no audio device.
- Hidden-page behaviour: the headless page is always visible, so `visibilitychange`, the background keep-alive stream, wake locks,
  the silent-stream hand-over and the hidden-page timer clamping are not exercised.
- Real touch / mouse input: the actions call `setView`, `go`, `tStart` and `tStop` directly (Settings is a real click); no drawing,
  no editing, so undo stack, autosave size and pattern edits are not stressed. MIDI, Link, recording, sample import, live-engine
  heavy songs and songs with MUT / GEN (the `VAR` cache) are not exercised.
- Ten minutes is not two hours: a leak under about 1 MB per minute of heap, or under 3 MB per minute of RSS, cannot be ruled out
  by this fit; the heap measurement itself is good to a few tenths of an MB per minute here.
- The waves / chains frames' own AudioContexts and heap are not in the `queryObjects` counts (they are separate JS contexts); their
  intervals are (10 live, flat).
- Hardware: the audio interface, USB MIDI, room correction.
- Absolute timing: load average was 2 to 5 on 2 CPUs. The tool counts `setTimeout` / `setInterval` through wrappers installed before
  the app loads, which adds a little overhead to every timer.
