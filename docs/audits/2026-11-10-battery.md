# Stability plan step 3: battery / efficiency audit of Thunder Plus (beta, build 544)

Read-only. Measured on a clone of `beta` at `.../scratchpad/step3/repo`; nothing in `/home/claude/thunder-plus` was touched.
Harness scripts and raw JSON: `.../scratchpad/step3/h/` (measure.mjs, threads.mjs, ab*.mjs, ablate2.mjs, forced.mjs, startup.mjs, trace.mjs).

## How to read the numbers (important)

- The box is a shared 2-core machine. My first pass (wall-clock `TaskDuration`) ran at load average 30-50 from other jobs, so every wall-clock "task" figure was saturated at about 1000 ms/s and is **discarded**. All numbers below are **CPU time** (per-thread, read from `/proc/<pid>/task/*/stat` of the page's renderer, GPU and audio processes), or event counts, from runs at load 2-10.
- "main" = the renderer main thread's CPU, ms per second. "audio" = the Chrome "Realtime AudioWorklet" thread, ms per second. Headless Chrome 153, software rendering, 1400x900, unthrottled (desktop).
- A trivial context (one empty worklet) costs 8-12 ms/s on the audio thread in this setup, so the idle audio numbers below are real, not a null-sink artifact.
- **Phone profile (Pixel 7, 4x CPU throttle): main-thread CPU is not usable.** The throttler itself burns about 470 ms/s of main-thread CPU with the page idle and the engine suspended (row 5b). Phone-profile audio-thread numbers are valid (the throttle does not touch that thread) and match desktop; phone startup numbers (wall time) are valid.
- Headless forces `document.hidden` by script (the page sees hidden; Chrome itself does not). So rAF is paused by the page's own guards, not by Chrome. Real Android Chrome also throttles background timers to about 1/s.
- Counts (timers, rAF, DOM mutations, canvas calls) come from wrappers in an init script, run at load 4. The wrapped run costs a little more than a clean one. A phone-profile count run was started and killed (box too loaded); phone timer/mutation counts are **not measured**.

## Findings, ranked by saving per risk

### 1. The CPU meter bar redraws the page about 60 times a second while idle (BIGGEST, SAFEST)
- Where: `cpuMeter()` index.html:30853-30864 (runs every 500 ms from `frame()` at :30944 and from the idleTick at :30865), CSS `.tcpu i{... transition:width .3s}` at :1306.
- What it does: every 500 ms it unconditionally sets `sp.textContent`, re-prepends the `<em>`, sets `i.style.width`, toggles two classes and sets `b.title` (a long string). With the engine running, `v` (the sum of `fxLoads()`, which comes from worklet load messages measured with `Date.now()`) wobbles from one reading to the next, so the width changes almost every time and the 0.3 s CSS transition then runs frames continuously. Each frame costs about 4 ms of main thread on a 25-30k-node DOM (Layerize alone about 70 ms per frame in a trace of the idle Phrase screen).
- Cost, measured by A/B in the page (CSS injected, 8 s windows, two repeats, main-thread CPU ms/s):
  - Phrase stopped: base 235 / 357 -> `.tcpu i{transition:none}` 49 / 42 -> `#tCpu` hidden 10 / 9.
  - Mixer stopped: base 468 / 327 -> transition none 106 / 100.
  - Song, MOD, FX with the stage hidden and transition none: 26-41. Compositor and GPU drop with it (e.g. MOD GPU 111 -> 1).
- When it runs needlessly: whenever the app is visible and the engine is running with nothing playing (the normal state on a phone with the app open; the engine never sleeps while visible, finding 2). Hidden, nothing runs (row 5b).
- Smallest safe fix: (a) compute the text, width (rounded to 1 %), class and title, and only touch the DOM when one of the four changed; (b) `transition:none`, or keep it only while `tp.on`. Round `v` to whole percent before comparing so noise does not count as change.
- Saving: about 200-300 ms/s main thread on Phrase / Mixer / FX / MOD while stopped and visible, plus compositor and GPU time; fewer 120 Hz wake-ups on the Fold.
- What could break: the bar looks steppy instead of smooth while playing if the transition is dropped there too; nothing functional (the CPU number, click handler and `warn` / `hot` colours are unchanged).
- Test: `tools/browser-check.mjs` style page load, then count mutations on `#tCpu` over 10 s stopped (expect under 1/s) and re-run the A/B above.
- Audio / timing: no.

### 2. The audio engine never sleeps while the app is visible (BIGGEST, MEDIUM RISK) **for audio review**
- Where: `bgWait` / `bgArm` / `bgIdle` index.html:21541-21562. The idle suspend only arms when `document.hidden` or Low power display is on.
- Cost: audio thread 373-445 ms/s with nothing playing, on every screen, desktop and phone profile; `ctx.suspend()` takes it to 0 (measured, ablation run). Playing is 577-699.
- Where it goes (ablation on a patched copy: each worklet's `process()` made a no-op, stopped Phrase, audio thread ms/s): none 404 / 392; tfx (7 nodes) 240 / 232; master 330 / 318; chains 350 / 358; core 356 / 374; bass+vox+mach 386 / 364; CPU probe 408 / 400 (no change); all six no-op 140 / 146. So worklets are about 260 of the 400; the other 140 is native nodes (436 live nodes: 244 Gain, 72 Analyser, 38 Delay, 36 StereoPanner...; analysers are pulled automatically, so disconnecting outputs does not stop the graph, only `suspend()` does).
- Smallest safe fix: arm `bgIdle` while visible too, after a longer silence (for example 60-120 s on phones; it already exists for Low power at 30 s), resuming through `audio()` as now. Resume took 9-42 ms in headless (8 trials); on a phone it will be longer and that is the cost: the first note after the sleep can start late (already documented under Low power display).
- What could break: first note after a long idle; MIDI clock / input is already excluded by `bgIdle`; anything that reads `ctx.currentTime` while stopped (clock log, `pbClock`).
- Test: the Worklets test on the Fold plus a timing test of first-note latency after sleep; `tests/hangs.test.js`, `tests/play-keys.test.js`.
- Touches audio engine start / stop: **for audio review**, not designed here.

### 3. Idle FX worklets that stay awake (part of 2) **for audio review**
- Where: `ThunderFx.process` index.html:18632-18705, sleep test at :18648 (`ip < 1e-7 && this.idle >= sampleRate && !this.clocked`), `clocked` set at :18599.
- Measured on the ELECTRO demo, stopped (debug message from each tfx node): 4 of 7 are asleep (idle >= 44100); 3 are not: node 0 and the master node have `clocked = 1` (a Pump Creative slot `js101`; Retrigger + Flex `js93` / `js95`), and node 3 never goes idle (its output stays above 1e-6 with silent input; its chain is glue, scramble, 2 chains modules). Removing all 7 tfx saves about 160 ms/s, so roughly 50 ms/s per awake node.
- Observation only: `clocked` is meant for tempo-locked slots that must hear the beat clock, but with the transport stopped there is no clock. The master worklet (about 75 ms/s idle: loudness meters and limiter on silence), the chains worklet (about 45) and the core (about 35) have no silence shortcut that I found. Not designed here.
- Saving if all four were fixed: up to about 300 of the 400 ms/s, without suspending.

### 4. Stage canvas redraws with nothing changing (Mixer, MOD, Song)
- Where: `stageTick()` index.html:27274-27290: for `piano` and `spec` stages it calls `stageCanvas(false)` every 45 ms (every idle tick, 5/s) regardless of sound; `stageSpec()` :27477-27490 clears and redraws six labels plus "PLAY TO SEE IT" and sets `#tStagePhT` text (a DOM write) each time. Counted: tStageC fillText 13/s and stroke 11/s on Mixer stopped, `#tStagePhT` childList 1.9/s.
- Cost (A/B, stage `display:none`, with finding 1 already applied; main ms/s): Mixer 111 / 122 -> 55 / 40; MOD 139 / 144 -> 40 / 41; Song 69 / 80 -> 26 / 29; FX no difference (37-40 both). Which stage kind runs on MOD and Song, I did not trace; Mixer is `spec` from code.
- Fix: like `deckScope` (`dkScopeIdle`, :28378): when not live, draw once and skip until live or the content / size changes; do not write `textContent` unless it differs.
- Saving: about 60-100 ms/s main on those screens while stopped. Risk low. Audio: no.

### 5. Per-frame DOM churn while playing (meters, Mixer text)
- Counted (above): 36 mutations per frame on Phrase+Arrange (about 2100/s), 180 per frame on Mixer (8200/s). Top targets: `B.gm` attrs 317/s and `BUTTON.mtr` attrs 282/s (the 16 track meters in the header), `BUTTON.` + `OUTPUT.` 123/s each, `I.` 120/s, `B.gp` + `#stVol` 70/s each; on Mixer `SPAN.mt` text 4707/s and `I.mfbar` 1158/s.
- `frame()` rAF callback time: 280 ms/s Phrase, 305 Mixer, 165 FX, 150 MOD. A trace of playing Phrase shows Layerize about 300 ms/s and forced style/layout 1704 calls/s (about 160 ms/s); JS inside rAF about 390.
- Fix: keep the last quantized value per meter bar / text span and skip the write when unchanged (meters move in steps of 1 % anyway; text spans on the Mixer only change when the value does). This is the same idea as `key === HM.drawn` in `hmDraw`.
- Saving: unmeasured (I did not build the fix). Upper bound is the share of the 150-300 ms/s that the writes and the style / layerize they cause take. Risk low for the writes; check the visual result per skin.
- Audio: no (display only). But `frame()` also drains `tp.q` for the playhead; do not touch that part.

### 6. Forced reflow in Arrange while playing
- Where: `arrRowH()` index.html:30046 (two `getBoundingClientRect` per call) is called inside `arrRowTop()` (:30049, plus `offsetTop` reads), which `arrRows()` (:29716-29717) calls in a loop for every visible row, and `arrRowAt()` (:30052) loops again. Counted with Playing + Arrange visible: 607 `getBoundingClientRect` and 563 `offsetTop` reads per second (about 50 + 47 per frame); trace: 1704 `UpdateStyleAndLayout` calls/s.
- Fix: measure the row pitch once per layout (invalidate on `fit()` / `arrLayout()` / font change) and pass it into `arrRowTop(y, rh)`; read `offsetTop` of the rows once per frame.
- Saving: I tried a 100 ms cache of `arrRowH()` in a patched copy: playing Phrase+Arrange main 753 / 743 (base) vs 551 / 497 (cache) in one pair and 526 / 472 vs 480 / 406 in the second pair. The box was noisy (fps 12-31), so call it **unproven, between 0 and 30 %**. Risk low. Audio: no.

### 7. waves and chains editors left alive after leaving the screen (desktop / Electron; phones hide them)
- Where: `waves/index.html` timers at :717 (90 ms), :1378, :3126 (400 ms), :3148 (120 ms), :3196 (200 ms) and a rAF `loop` (:3283); `chains/index.html` :733, :1394, :3624, :3688, :3718, :3787. The embed's `pause()` (waves :2966, chains :3419) only suspends its AudioContext. `leaveWaves()` index.html:16890.
- Measured on desktop (single run, stopped Phrase): baseline main 226; after visiting waves 316 and 289 (30 s later); after waves + chains 334. So about +60 to +110 ms/s, noisy. Nominal wake-ups from the waves timers alone: 11 + 8 + 5 + 2.5 per second. The waves context's audio thread only appears while the screen is open (15 ms/s) and stops when left.
- Fix: in `pause()`, set a flag that makes those timers return early (or clear them), and in `resume()` clear the flag; or remove the iframe after 30 s away (reloads from the song next time, as chains already does on a new song). Risk low / medium. Audio: no (the embed's own context only).

### 8. Start-up work for things a session may never use
- Fetched before the first touch (from the server log, bytes): index.html 3,250,780; wasm 4.2 MB compiled and instantiated eagerly (pump.wasm 1,599,108; pump-synth.wasm 921,464; thunder-dsp.wasm 836,159; tfx.wasm 674,341; lxr.wasm 151,220); ELECTRO.thunder 856,625 (first run only); `waves/waves-worklet.js` 593,878 as a blocking `<script>` (index.html:3429) and again inside the render Worker (`importScripts`, :8387); `lxr-engine.js` 41 KB and `pump-synth-meta.js` 158 KB + `pump-synth-engine.js` 30 KB also loaded by both page and Worker; `pump-meta.js` 269 KB; eleven `pump/ui/*.js` files about 460 KB (index.html:33700+); fonts about 280 KB. About 10.8 MB in all. After the first touch another 1.4 MB (chains-worklet 619 KB, seq-core 117 KB, master-worklet 21 KB, pump-synth-worklet 9 KB, waves-worklet again 594 KB; same file as an `addModule`).
- Also created at load: the render Worker (instantiates dsp + tfx + lxr + pump-synth wasm again: second copy of the memory, not measured).
- Fix candidates: load `pump/ui/*` and `pump-meta.js` on first opening of a pump window; load `lxr-engine.js` and `pump-synth-*` only when a kit uses those engines; do not run the Worker's `importScripts('waves-worklet.js')` until a pad uses waves. I did not build these, so **no saving is claimed**; the start-up totals above (desktop 2.14 s main-thread CPU, phone-profile DCL 4.3 s) are the before figure. Risk medium (init order: `LxrCore` / `PsynCore` are probed with `typeof` at :8344-8346 and :16805). Touches the render Worker and engine start-up: **for audio review** where it changes which engines exist at first PLAY.

### 9. Low power display, measured
- Playing Phrase: main 193 (normal) -> 161 (Low power); compositor and GPU 11 / 44 -> 9 / 29; DOM mutations 2208 -> 1934/s. The saving is small here because headless already runs the page at only 32-36 fps (the main thread is saturated), so the 24 fps gate hardly binds. On a real phone at 60-120 Hz it will bind more; not measurable in this setup.
- In Low power the engine also sleeps after 30 s of silence (that is finding 2 for everyone else).

### 10. Things checked and found fine (do not re-propose)
- Hidden and stopped (5b): no rAF, no mutations, no canvas draws, engine suspended; the idleTick runner is the only timer (3.3/s on desktop).
- Idle timers while visible and stopped: frame 5/s and hmFrame 5/s (200 ms), the idleTick runner 4-9/s (its sleeping ticks: psLive 3 s, pbCkOn 2.5 s, pbClock 4 s, wakeLock 5 s, arrLayout 3 s, glitchScan 1.5 s, chains meter 1.5 s). Their own CPU is about 5 ms/s; the cost is the DOM write in finding 1, not the wake-ups.
- `setInterval`s: 60 s sample trim (skips under 8 held samples), 180 s autosave (only when dirty and not playing), `?pbshow` only on request. Wake lock check is idleTick-slow while stopped.
- `arrLayout` once a second is a cheap key compare.
- Dancing dogs: not running in my Phrase view (`document.getAnimations()` showed only the CPU bar's width transition); `dogs.idle` CSS animation is infinite on desktop (`body.mob` caps it at 9 / 12 iterations, :2093); A/B with `.dogs *{animation:none}` changed nothing (402 / 296 vs 266 / 301). Not a cost today, but on desktop the idle dogs would add frames when that stage is up.
- The audio graph's 72 analysers: `getFloatTimeDomainData` is only called while `tp.on` or within 1.5 s of a sound (frame(), hmDraw); the analysers themselves are pulled by Chrome regardless (cost sits inside the 140 ms/s native part of finding 2).

### 11. Not measured, code-only (so no number)
- `bassViz()` (index.html:12542-12580): while the Synth page shows a bass pad it redraws every rAF forever with a full `BassCore` block, 4 `getComputedStyle` reads and a new `Float32Array` each frame, with no idle stop (the wobble phase comes from `performance.now()`, so it animates even when stopped). My headless run could not bring the bass panel up (`#bassWrap` stayed hidden). Candidate: cap at 30 fps, cache the colours, stop when nothing changes.
- `deckScope()` (:28378-28384): `getBoundingClientRect()` + `getComputedStyle()` + three `getPropertyValue` every 50 ms while the scope is shown (it returns early when `deck.fxbar` is on, which is the desktop default but off on phones, :28050 `fxbar:!isMobile()`). So on phones this is a forced style recalculation after the frame's writes, every 50 ms while playing. Candidate: cache the colours per skin change and the rect per resize.
- Service worker (`sw.js`): installs only on https, so it was not exercised. Code: the cache name changes every build (`thunderplus-v544`), and install fetches about 30 files with `cache:'reload'` (about 10 MB, including `waves/` and `chains/` copies of `tfx.wasm` and fonts) each time, then deletes the old cache; the page is fetched `no-cache` on every navigation. A once-per-build 10 MB download on mobile data matters more than any CPU number here. Candidate: keep the heavy files under a versioned URL (they already carry `?v=`) in a separate long-lived cache and only re-fetch changed ones.
- Embedded editors' iframes: none exist until their screen is first opened (`showWaves`, `showChains` create them lazily; 0 iframes at every state of the phone profile and before the visit on desktop).

## Suggested order
1. CPU meter (finding 1): one small function plus one CSS line, biggest idle win.
2. Stage canvas idle skip (4).
3. Meter / text write-if-changed (5), with a before / after count of mutations per frame.
4. Embed timers after leave (7), desktop only.
5. Audio review package (2, 3): idle suspend while visible, `clocked` nodes asleep when the transport is stopped, silence shortcuts in master / chains / core. Biggest absolute saving (about 380-445 ms/s of audio thread), and the only part that touches the engine.
6. Arrange row metrics (6), then `deckScope` / `bassViz` (11) once measured on a phone.
7. Start-up deferral (8), after the audio review; needs a measured before / after.

## Gaps
- No real-phone numbers; the throttled profile cannot give main-thread CPU (above).
- Phone-profile mutation / timer counts were not completed.
- Settings-open, "page hidden" with real Chrome visibility, and a real audio device were not covered; the first-pass wall-clock tables were discarded as contaminated.
- State 4 (playing hidden) audio thread 860 vs about 650 visible is a single run and unexplained.
