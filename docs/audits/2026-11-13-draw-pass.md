# Draw pass: screen drawing while a song plays (13 Nov 2026, build 574 base)

Branch `perf/draw-pass`. Method: `tests/sweep/draw-pass.mjs` (Fold profile as the wrap write-up: touch, Android UA, Mobile setup, DPR 2.5, 884x1020 or
412x915; ELECTRO restarted from row 0 per screen, 3 s settle, 10 s window; `draw()` and its children wrapped in the script with performance.now accounting,
long tasks from a PerformanceObserver, layout / style counts from CDP Performance metrics). Tables: `node tests/sweep/draw-pass-report.mjs --prefix=before- --after=<prefix>`.
Raw files are in tests/sweep/out (gitignored). The full "before" matrix (page and core, open and cover, 4x / 6x / 1x) was run on the base build.

## Where the time went (before, page sequencer, unfolded, 4x)

Main-thread CPU profile (1 ms sampling) and a timeline trace of Pattern view and the Mixer: about two thirds of the main thread is not script but the browser's
Paint and Layerize after each redraw's DOM writes (Layerize about 17 ms a frame at 4x, 18 frames a second), and the rest is `draw()`. Top three costs of `draw()` per screen:
- Pattern view: `pvLines` string building (17 ms a call at 4x), `busPlan` (hashes the whole chain patch on every call, asked per cell: 13 % of the thread), forced layouts (`innerWidth` in `pvRoom`, `clientWidth`).
- Mixer: `busPlan` (10 %), `mixFaders` rect reads, `paintMeters` (30 Hz meter text writes: Paint / Layerize, not removable without changing the meters).
- Inst: `instTracks` / `padUses` (a scan of every phrase for every instrument, on every redraw): 19 %.
- Song / Arrange, Phrase, Sect, FX, MOD, Project: the full `draw()` itself (about 5 ms a call at 4x) run for every row (17 a second) although these screens show nothing new for a row.

## Fix 1: redraws caused by the playhead only (`playTick` / `playLite`), busPlan once per redraw, Inst scans memoised

- `busPlan` is wrapped on the page (the core's copy in core/seq-core.js is unchanged) to answer once per `draw()` / `drawArr()`.
- `instTracks` / `padUses` are memoised on `songVer` + the song while a redraw runs (callers that decide something still scan).
- `pvRoom` reads a width cached on resize.
- `frame()` sends the playhead redraw to `playTick`. If nothing the screen shows changed since the last full redraw the frame made (stamp: cursors, phrase, sect, tempo,
  follow, sizes, Arrange state), Sect / Phrase / Pattern view move the playing-row marks in place (`litRows`, `pvPlayMark`), Arrange's side panel keeps its own rate, and
  Mixer / Inst / FX / MOD / Project draw nothing for a row. Song / Arrange (text carries the playing row), a selection, a drag, Arrange focus or any changed stamp take the full
  `draw()`. A full redraw also runs at least every 500 ms (self-heal for anything changed without its own redraw). On touch (`COARSE`) the playhead's drawing runs at most
  every 50 ms (about 20 a second); the frame that would draw sooner owes it (`plOwed`).

## Fix 2: the CPU panel measures the screen (item 3)

`scrAdd` adds the milliseconds spent in `draw()` (top-level call, two `performance.now` reads) and in the playhead-only update `playTick` does instead of a full draw (13 Nov review fix: it was left out; a full redraw is counted once, by `draw()`; the panel says "screen updates a second") and in the page sequencer's tick (`pumpTimed`, page mode) into a one-second
figure; `cpuMeasured` hands them to `cpuRank` as `screen` / `seqPage`. The panel shows a second short section under the audio list, headed "The screen (the page's own time,
a separate budget: do not add it to the audio engine above)", with "Screen drawing · N screen updates a second: N% of the page's time" and "Sequencer (page): N% of the page's time".
A figure older than 2.5 s reads as nothing. When nothing else is wrong and drawing takes 30 % or more of the page's time (and Low power is off) the tip suggests Low power mode.
Nothing on the audio thread is measured. Checked in headless Chrome: ELECTRO playing on a desktop window reads "Screen drawing · 18 draws a second, 10 % of the page's time".
Tests: tests/cpu-rank.test.js (three new).

## Decisions

- Playhead redraws: in-place marks plus a stamp check, rather than a rate cap alone: the redraw rate was already about 17 a second (below any sensible cap), the cost was per draw.
  The 20 a second cap (`PL_MIN` 50 ms) is for touch screens and faster songs; a desktop is not capped.
- A full redraw at least every 500 ms (`PL_BEAT`): any state that changed without its own `draw()` shows within half a second.
- `busPlan` is wrapped on the page only: the sequencer core's copy (core/seq-core.js, generated) is unchanged.
- The Mixer's meter rate (30 Hz) and the header meter were not touched (owner-visible).
- First PLAY press (item e): measured, not changed (below).

## First PLAY press (item e: measured, no change)

`node tests/sweep/first-play.mjs` (real touch on #kPlay, fresh page, Fold unfolded, 4x): the press's pointerdown handler runs 446 ms (`rtInit` 256 ms: starting the audio
engine, which must precede booking; `liveWarm` 58; the first full `draw()` about 60 to 80; `bgPlay` 92), then a second `tStart` runs from the worklet `addModule.then` (the
engine waits once for the live worklets and re-enters) and holds the thread 1.5 s (long animation frame) including another full draw. Moving `draw()` to a frame would
not shorten the stall (the pump tick that books the next events is a worker message that waits behind any long task), so the safe part is nothing to change; the real fixes are
in the audio start (`rtInit`) and the worklet hand-over (split `tStart`'s second pass over several frames), which touch the engine start, outside this pass.

## Item 4 (report only)

**Latency settings.** `latOf()` (interactive / balanced / playback) is used in two places: `new AudioContext({latencyHint: latOf()})` when the audio starts (index.html 8539; and a
probe context at 8496), and as text and checks (the audio-delay message exempts 'playback', the auto-suggestion that offers Safest does not run on it, `cpuRank`'s tips). It changes the
browser's output buffer (the hardware callback size and so baseLatency / outputLatency), takes effect only on restarting the audio ("Restart audio" row). It does not change the scheduler's lead,
the pump (25 ms worker timer), the core's 247 ms lead, or the render quantum.
**Can Safest make blocks longer than 128 frames?** Not from this app: it never passes a `renderSizeHint` (grep: none), so Chrome keeps the 128-frame quantum whatever the latency
hint says; `latencyHint` only makes the device buffer bigger. `tcChunks` (index.html 18958) is only reached if a browser delivers longer blocks (a future render-size hint).
**What `tcChunks` allocates per block (when it runs):** one `Q = {}` per chunk plus its `v` closure, two `.map` arrays for `ins` and `outs` with one inner array per group and one
`subarray` view per channel per chunk, the `P` copies for a-rate params (`subarray`), and the `one.call` argument arrays. At 512 frames that is 4 chunks x about 12 objects a block, 
~14 000 objects a second for one effect node, per node. **Allocation-free version:** keep per-processor scratch (`self.__tc`) holding, for each chunk index, nested `ins` / `outs`
arrays of views and a `Q` object, built once for a given host buffer identity (the first output channel's `buffer` and `byteOffset`) and block length N; later blocks of the same
shape only rewrite `Q`'s k-rate scalars (`Q[k] = A[0]`) and reuse the views (a-rate params get cached views the same way). If the host hands different buffers each call (the
identity check fails) rebuild the cache once for those buffers, falling back to today's path; no `map`, no closures, no per-chunk objects. The audio thread's `__tcOv` / `__tcPost` hooks stay as they are.

**Running while STOPPED and idle** (`node tests/sweep/idle-wake.mjs`, Fold profile, 1x, Song and Mixer screens): the main thread is busy about 2 to 2.7 ms a second (task time), no layouts or style
recalculations, three timers at 5 a second each: the frame loop's 200 ms idle timer (`frame`, 32613), the header meter's 200 ms sleep timer (`hmFrame`, 29879) and the generic
"idle sleep" runner (22183, `slow` interval). Also periodic but rare: the autosave backup (every 3 minutes, skipped while playing), the held-sample trim (13687) and `pumpTimer`'s
worker only while playing. No Resize / Mutation / Intersection / Performance observer callback fires while idle (the script counts them since the 13 Nov review fix: zero in 10 s on the Song and Mixer screens), no rAF loop runs, the pump worker is stopped. Cost: about 0.2 %
of the main thread, 15 wake-ups a second. They could all sleep: the first two could park until a pointer, key, MIDI or audio event (`frameWake` and `hmFrame` already have the wake
hooks), the third could back off to 1 s; saving a few percent of idle wake-ups, not a measurable CPU change.
