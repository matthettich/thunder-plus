## 1. Stutter with the screen off (1.1 / 4.1): the web path's own known weakness, not the native engine

What the report shows (WebAudio path, three plays with core / page sequencer):
- At every screen-off the clock misbehaves: `held the song: audio clock leapt +0.09 s` (6.09, 13.47, 56.01 +0.08, 57.61 +0.07), `held 3x (0.21 s)` at the 60.51 wake line, `least lead 0.06 s` at the first screen-off (5.85; lookahead down to 60 ms means JS timers are being throttled), page `longest gap 0.15..0.18 s`. `clock +1.11 s in 1.00 s` (56.05) and `+1.25 s in 1.20 s` (135.66): the AudioContext clock leaps and the page's `rsHold` (index.html on native, `rsHold`, ~line 23389, called from the clock-leap detector) deliberately **holds the song** (shifts every song time by d), which is an audible gap/stutter. This is the Fold's WebView audio clock running irregularly with the screen off (the 6 Nov owner's report quoted in the code: 0.8x, 1.4-1.6x, "RUNAWAY KICK" 14x).
- `stats ... underrun 0.06 ×3` is constant from t=12 s to the end: no new underruns are counted. The output is not starving by that counter; the glitches are scheduling/clock (page-sequencer and clock-hold), consistent with the owner hearing stutter that is "bunched", not dropouts.
- At screen-off with the core (worklet) sequencer the page runs `seqHandover()` (native-branch index.html ~23704; same code at beta 25657): it stops the core and restarts the song on the **page sequencer** (JS `setTimeout` pump, throttled when hidden) "after row 5 step 13", logs a second `PLAY song` (113.35, 190.58, 223.00). Page ticks while hidden: 1 then 205 (113.36 -> 118.54): the page sequencer is what plays the song during screen-off. A hidden WebView's JS is the thing the sound depends on = hypothesis (a) is TRUE for the web path.

Hypotheses for the **native engine** (not what ran, but the lead asked): 
- (a) NO. The song is sequenced and rendered inside the audio callback (`live_engine.cpp:68-92` render -> `thunder_live_process`); the page only sends messages (`LiveBridge.kt:34-37`, one JVM worker thread); the event pump is a JVM `ScheduledExecutor` (`LiveBridge.kt:166-176`, not WebView timers); the page receives via `main.post{port.postMessage}` (`Bridge.kt:68-70`), which a hidden WebView may delay but nothing audio waits on. The core's control thread (`live_engine.cpp:128-151`) and poller are plain C++ threads.
- (b) PARTLY. FGS type mediaPlayback is declared (`AndroidManifest.xml:30-33`) and started by `LiveEngine.start` BEFORE the first play only via `startForegroundService` at `LiveEngine.kt:72` right after `nativeStart` (stream is opened first, service after: a few ms; fine). No WAKE_LOCK: deliberate (manifest comment; WORKPLAN A3). A mediaPlayback FGS is enough to keep the process alive but does NOT stop the CPU governor from parking the little/big cores; if cores are parked a 5 ms-class callback can miss. Cheap hardening: a PARTIAL_WAKE_LOCK (needs the WAKE_LOCK permission; held from play to stop, Kotlin only) and `AudioAttributes` usage already media. UNVERIFIED that it matters.
- (c) Stream settings: `live_jni.cpp:140-147,247-254` and `jni.cpp:184-191`: miniaudio AAudio, `performanceProfile = low_latency`, `usage media`, period size 0 (device default), shared mode (miniaudio default: `ma_share_mode_shared`, `miniaudio.h:39531`), no exclusive. There is NO adaptation to underruns: nothing calls `AAudioStream_setBufferSizeInFrames` to grow the buffer on an xrun (`aaBuf` only READS it, `live_jni.cpp:374`). Low-latency AAudio default is ~2 bursts: on a loaded or throttled device with the screen off, a late callback = an audible glitch. This is the most plausible native-side cause IF the owner still stutters once the native engine is really in use. Fix (audio-stream setup, touches miniaudio config / audio path: lead approval): use `performanceProfile = conservative` while the page is hidden or always for playback of songs (latency matters less than not glitching; MIDI out clock map would need the latency), or grow the AAudio buffer by one burst each time `getXRunCount` increases (done from the poller thread, not the callback). No thread affinity / `ADPF` hints are set; none needed first.
- (d) NO for the shell: `MainActivity.onPause` removes only the panel refresh (`MainActivity.kt` onPause), `onDestroy` explicitly does not touch the engine, configChanges lists orientation/screenSize/... so a fold never re-creates the activity (`AndroidManifest.xml:25`). A fold can cause a device/route change that miniaudio handles by itself (`onDeviceNotification` -> `newStream()`), and `LiveSession.tick` rebuilds a stream that stopped calling back (1 s `StreamWatch`). That rebuild stops the song (`device reason:stream stopped:true`), so a fold that rebuilt would be heard as a STOP, not stutter. UNVERIFIED on the device.
- (e) Audio-thread work: callback has no lock/alloc/JNI/log (`live_jni.cpp:77-91`); one `monoNs()` pair + `rtlog` + AAudio timestamp every 20 ms only when MIDI out is on. `dataCallback` does not block. Not an issue by reading; if xruns show up in a real native run, `maxWorkMs` in the A5 snapshot says whether the callback itself is slow.

## 2. Sound continuing after Stop (1.7)

What the report shows: after each STOP, `1 s after STOP: level -39.3 dB` (first), then -77, -67, -87 dB and `3 s after: -46 / -78 / -77 / -97 dB`, `voices 0`: the sound after Stop is essentially silent in the report, except a tail of -39/-46 dB after the first STOP (an effect tail or something audible but quiet; the first play was the page sequencer with `core=0`). So the report does not reproduce "stuttered fragments of the song keep playing" at an audible level. The owner's 1.7 observation was a step *after folding* with nothing playing; the report's lines with `screen off` after STOP (66.91, 127.00, 209.74) show no level logged after the 3 s mark: NOT covered.
- `stray rows from the core` is the page's own counter of `rows` batches from the core worklet that arrive when `tp.on` is off or the generation differs (`coreMsg`, native index.html ~23785; beta 25723). After the hidden hand-over (the page stops the core with `{op:'stop', at:T0, rel:true}`, 23725) the core's already-booked rows keep arriving: gen 1 vs now 2 logged right at the hand-over (113.36, 190.58, 223.00), and `PB.stray` is **cumulative across plays** (0 -> 6 -> 11 -> 16 are the totals of rows batches since page load, never reset: `PB.stray` only `+=`). So the climbing count is a counter, not a growing backlog: each hand-over adds 5-6 late batches (about one second of rows). The core is told to stop at T0 (first page step), so these are rows from before the stop point. They are IGNORED for sound (`d.gen !== core.gen` -> return, 23800); the stray path only re-sends `stop` when the core is not playing. Voices are 0 at the 1 s mark, so no two-sequencer overlap is evidenced by the levels (levels -77..-97 dB).
- Two sequencers at once is therefore **not supported by the evidence** for the stutter: after hand-over the core is stopped at T0, and the page sequencer plays alone. What is real is the hand-over itself: two `PLAY song` log lines, "its first step 57 ms after the core's last" (a designed 57 ms seam at every screen-off) and, in the hidden state, a JS-timer-driven sequencer.
- "Stopped" path being starved: STOP from the page is a page call (`tStop`, immediate in JS) and `core.node.port.postMessage({op:'stop'})` to a worklet: a hidden/frozen renderer delivers it late. The page code already knows ("DEAF CORE, owner 6 Nov: the core kept stepping 18 s+ after STOP") and drops the core after 1.5 s and >=3 stray batches. Fragments after Stop (owner's 1.7) match that old DEAF-CORE class: the worklet sequencer still stepping because its message queue is not read while the device is in the fold/screen state; it was not reproduced in the report's timing windows (not captured: the exact fold-unfold with nothing playing).
- Native path for Stop: page -> `LiveBridge.handle` (worker thread) -> `nativeTransportStop` (`LiveBridge.kt:94`), then `LiveSession.afterUserStop`; not a throttled path (JVM executor). The native core stops via the control thread queue; stale buffers cannot replay: `render` zero-fills on null/empty engine (`live_engine.cpp:73`, `live_jni.cpp:79`) and has no ring of old audio. CONFIDENCE for "not a native bug": medium-high (reading only).
- CONFIDENCE for the web-path explanation of 1.7 (a worklet sequencer / page sequencer kept alive by throttled messaging): medium. To confirm, take a report right after a 1.7 repeat (see section 5).

## Hello fixes (26 Nov)

Cause list: `/home/claude/reports/HELLO-ROOTCAUSE.md` (the page's native client never got `on`; panel "native live engine: off"). Shell changes, Kotlin lifecycle only (no C++, no Oboe/AAudio callback, no `native/core`):

- **Port earlier.** The shim (`thunder_bridge.js`) posts `thunderPortAsk.postMessage('port')` once at document start, after its `message` listener is registered; `Bridge.install` registers that listener (main frame only) and it calls `attach("ask")`. `onPageFinished` stays as the fallback (`attach("pageFinished")`). `PortGate` (LiveDiag.kt, JVM-tested) allows one attach per page load (`onPageStarted` opens a generation), so a port the page uses is never closed and replaced.
- **Say why.** `LiveEngine.lastStartError` is set in `startOnWorker` (nativeStart rc, "a shutdown came first", exception text). `LiveBridge.hello` replies `{t:'reply', id, v:1, err:'live engine did not start: <reason>', ok:false}`; an exception anywhere in `hello` also yields an err reply with its text.
- **Stale state.** `startOnWorker`: `up` true and `active` false now runs `nativeShutdown`, sets `up = false` and starts again in the same call. The `shutdowns` generation checks (A1/A2) are unchanged and run after that cleanup.
- **Show it.** `LiveEngine.statusText` (also when off) adds: hello count, time since last hello, its result, `lastStartError`, and whether/how the port was handed over this load (ask / pageFinished). COPY RESULTS includes it.
- Tests: `HelloDiagTest` (PortGate once-per-load, HelloLog lines).
- Unverified on a device; CI compiles it.
