## Item 1b (limits and memory) - MEASURED (v34a/t_oom.cpp modes padlimit/songlimit; peak RSS by python getrusage; Release; host's own buffers included, baseline stated)
- Song bytes: 64 MiB exactly (valid JSON, padded with spaces in an ignored key) -> handle; 64 MiB + 1 -> NULL "song is over the size limit", no read of the bytes. vars: >16 MiB -> NULL (checked before parse). One-below / at / one-above all behave. (vars at 16 MiB not measured for RSS.)
- Pad: mono 2^27 frames = exactly 512 MiB -> rc 0; 2^27+1 -> E_LIMIT (-4) (and 2^28 mono is E_LIMIT by bytes before frames); stereo 2^26 frames at limit ok. MAX_PAD_FRAMES (2^28) is unreachable by itself (any mono pad above 2^27 frames trips the byte limit first); harmless.
- Peak RSS, host buffer 512 MiB included: host-only baseline 563 MB (the refused 2^27+1 case, incl. ~50 MB for the 48 kHz handle); pad at limit 1075 MB (handle = ~512 MiB pad + ~50 MB); REPLACING a pad at the limit (second set_pad of 2^27 frames on the same pad) 1587 MB: the new copy `tmp` is built before the old buffer is released, so a handle transiently holds up to ~1.05 GiB of pad data, twice the "512 MiB in all" budget.
- DEFECT D4 (budget not a bound on allocation): render_api.cpp:~145 (`std::vector<float> tmp(n)` before `store[pad].swap(tmp)`); the header's LIMITS / MEMORY text promises pad data <= 512 MiB; a hostile host can transiently make the handle allocate ~1 GiB for pads (+50-400 MB renderer). Cheap fix: count `padBytes + n*4` (not minus old) against the cap, or release the old buffer first.
- Hostile SONG at the 64 MiB limit: a song that is 32 M numbers in an ignored key ("zz":[0,0,0,...]) -> handle created, peak RSS 1195 MB (baseline of my process ~70 MB): ~17x the song size, kept for the life of the handle; arrays of `{}` / `[]` / `""`: 822 MB (~12x). Header says "about 3 to 10 times its size" (true for ELECTRO, false for hostile input). Worst measured for one handle: ~1.1 GB (song) + ~1.05 GiB transient (pads) + up to 385 MB (renderer at 384 kHz, fx + master) = ~2.5 GB from three limit-sized arguments. Deep nesting at the limit is refused by the parser ("nested too deeply", depth ~512), cheap.
