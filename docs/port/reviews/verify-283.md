# verify-283: independent review of PR #283 (U37 P2 LiveHost core)

VERDICT: MERGE AFTER FIXES. One blocking finding (F1: a backward frame0 leaves the song PLAYING and silent), four should-fix (F2 poll order, F3 critical-ring flood, F8 mix_set pan range, F9 play publish / push window), plus F4 (ENDED timer) before P4. Nothing found that allocates, locks or frees on the audio thread; the SPSC / SnapSlot hand-offs are sound. Read only: nothing was built or run (see the last section); every claim has file:line and a sequence from reading the code.

## Findings so far (partial 1)

F1 (BLOCKING) BACKWARD RE-ANCHOR HANGS THE SONG. live_host.cpp:490-499 reanchor() only restarts the quantum grid. The Seq's own time (seconds) is not touched, and nextClockAt_ / nextPosAt_ / nextLateAt_ (set once at :478), endStopAt_ and pend_ (timed commands) keep absolute frame values. Sequence: play; process(frame0 = 480000) ... then the shell restarts its stream and calls process(frame0 = 0). runner.h:64 steps only while `s->time() < now + lead`, and the catch-up skip fires only when the Seq is BEHIND (`time < now - 0.03`). Seq.time() is ~10 s ahead, so no step runs for ~10 s: PLAYING and silent (voices queued earlier ring out), no CLOCK / POS / LATE records for that time either, the ENDED timer (endStopAt_) and far `at` commands wait as long. A forward gap is fine (runner skip). Fix: on a re-anchor with skipped < 0, shift the Seq (`seq->shift(t0new + 0.02 - seq->time())` or equivalent), and reset nextClockAt_/nextPosAt_/nextLateAt_ = frame0 and rebase endStopAt_; document. Test: process to 10 s, then frame0 = 0, assert steps keep coming within 0.2 s.

F2 (should-fix) poll() CAN DELIVER OUT OF seq ORDER (live_host.cpp ~640-660). It peeks evCrit_ head, then evRing_ head, then picks the lower seq. Sequence: consumer loads evCrit_.head (empty); audio posts STATE (seq 5, critical) then ROWS (seq 6); consumer loads evRing_.head (sees 6) and delivers 6; the next poll delivers 5. The two ring heads are not one atomic view. Fix: after choosing a record from one ring re-load the other ring's head and re-compare (or take the critical head last; a second look at the first ring settles it).

F3 (should-fix) NON-FATAL ERRORs ARE ON THE CRITICAL RING. REANCHOR (:490) and CMD (:538) are `THUNDER_LIVE_EV_ERROR`, so post() (:773) sends them to evCrit_ (64 slots) together with STATE / HELD / SONG / PADS. A shell with a jittery counter re-anchors on every call (every 2.7 ms): 64 records in 0.17 s fills the ring if poll is not called that often, and then STATE (STOPPED / HELD) is the record that is refused (evCrit_ refuses the newest). A 65-command burst posts one CMD error per quantum, too. Fix: rate-limit non-fatal ERROR records (one per N quanta, count the rest in a field), or put non-fatal ERRORs on the ordinary ring.

F4 (note/should-fix, for P4) ENDED TIMER STARTS FROM THE QUANTUM THAT FINDS THE END (live_host.cpp:710-727, departure 7). `lead` accepts 0.05 .. 2 s (:309). With lead = 2 s the step that ends the song is stepped up to 2 s ahead of t0, so STOPPED (arg 1; later the MIDI stop) is posted at t0 + 0.3 = endT - 1.7 s: BEFORE the last notes sound. With the default lead the early amount is ~lead. Fix: endStopAt_ = max(t0, endT) + 0.3 (departure 7's "one line").

F5 (note) songPublish IDLE path returns E_BUSY (:131) AFTER replacing songCur_ / varsCur_ / songRev_ (live_host.h says a SongAck failure keeps the publish): contract ERRORS says "a failed call changes nothing". A caller that plays before its retry plays the new song. Either return OK and count the missing ack, or restore songCur_.

F6 (note) control state after HELD / ENDED->IDLE: controlPlaying_ stays true (only stop() clears it), so a songPublish after the song ran out still builds a successor snapshot on the dead session (session bytes grow; harmless but wasted; stats.session_full may fire). Accept or clear it from the STOPPED record in poll.

F7 (note) build-r.log (189 lines) is committed at the repo root of the PR.

F8 (should-fix) mix_set REJECTS NEGATIVE PAN. live_host.cpp:~330 `value < 0 || value > 255` applies to every key, but MixKey::Pan is -1..+1 (mix.cpp:354 clamps to [-1, 1], a left pan is negative). `mixSet(t, THUNDER_LIVE_MIX_PAN, -0.5, ...)` answers E_ARG, so the page can never pan left. live.h:402 itself says "value 0 .. 255" (a contract error copied into the code). Fix: per key ranges (vol / trim 0..255 or the mixer's own, pan -1..1, mute / solo 0 / 1, out as Mixer::set takes it), amend live.h. test_live_transport.cpp:135 pins the wrong range (it never tries a negative pan).

F9 (should-fix, rare) play() PUBLISHES THE SNAPSHOT BEFORE IT PUSHES THE Play COMMAND (live_host.cpp:~330-338: songSlot_.publish at one statement, cmds_.push a few statements later) and the audio side's step 2 adopts snapshots on its own (adopt() :619, seq_adopt). Sequence: song A is PLAYING; control calls play(): the new session's snapshot S_B is in the slot; the audio thread's quantum top runs between the publish and the push; adopt() -> seq_adopt: chain [S_A, S_B], different sessions so no takeOver, but `runner.rebind(S_B.seq)` re-points the RUNNING runner at B's unstarted Seq (rebind only checks that a Seq exists). That quantum steps B's Seq from its initial state at its default time (no setTime, hasBase false: no catch-up skip), up to 3 steps of events are dispatched and B's tracks advance. Next quantum the Play command arrives; tryStartPlay starts the runner on the same (already advanced) Seq with setTime(t0): the play starts 1..3 steps late, with a burst of already-fired events (mixer lane events, tempo) before it. Window is microseconds per play (about one in 1e3..1e4 plays on a busy control thread), but it is a wrong start with no error. Fix: push the Play command first (tryStartPlay already waits and retries when the snapshot is not there yet: stalledPlay_), or make adopt() skip a snapshot of another session while a Play is not yet applied (carry the snapshot's `ord` in the Play command and adopt only up to it).

F10 (note) STALE TIMED COMMANDS SURVIVE stop / play. pend_ (live_host.h:327) is never cleared by Stop or Play (live_host.cpp:547-557 Stop, tryStartPlay). Sequence: bpm(140, at = now + 5 s), stop, play (new song) 1 s later: the bpm lands in the new song 4 s in. Same for loop, perf, a stop(at) from the old session. live.h is silent; for a transport the page would expect Stop to cancel Seq-bound timed commands (Bpm, Loop, Perf). Decide and document; cheapest: Stop and Play drop waiting Bpm / Loop / Perf entries.

F11 (note) stats.seq_dropped: tryStartPlay calls seq_adopt first, which rebinds the runner to the NEW Seq, then dropSeq() adds `runner_.seq()->dropped()` (the new Seq's) to seqDropBase_: the old Seq's dropped count is lost on play-over-play (P_SEQDROP is a running max so the published value does not go down, but the old Seq's drops are not added). Read the old pointer before seq_adopt.

F12 (note) re-anchor FORWARD with booked notes: events the Seq booked up to `lead` (default 0.25 s, :310) ahead have times before the new t0 when the skip is shorter than the look-ahead, so Players start them all at once (a burst, flam) if they are less than 0.15 s late and drop them otherwise (notes_late). The remainder of the dropped quantum buffer is a hard cut in the output (a click is inevitable). Document in live.h TIME; nothing to fix beyond F1.

F13 (note) Seq-bound commands sent while IDLE (bpm / loop / perf with no Seq: applyOne :549-553 `if (runner_.seq())`) are dropped silently but count in cmds_applied. Document, or answer E_STATE from the control side when controlPlaying_ is false.

F14 (note) frame0 near INT64_MAX: `nextFrame_ = frame0 + frames` (:480) and `qFrame_ += 128` overflow (UB). Reject frame0 > 2^62 as E_ARG.

F15 (note) ROWS / HELD record buffers are `uint8_t buf[...]` cast to `thunder_live_ev_rows*` (live_host.cpp notePos ~:673, heldRecord ~:690): alignment 1 for a struct with an int64 (needs 8). UBSan did not flag it because the stack slot happened to be aligned; on 32-bit ARM it is a real misaligned 64-bit store. Fix: `alignas(8) uint8_t buf[...]`. The static_assert on LiveCmd (live_host.h:67) is 64-bit only; add size asserts for every thunder_live_ev_* (24 / 32 / 48 ...) so a 32-bit build checks the layout.

F16 (note, tests) the unit's own allocation guard never runs `stop` or a song END: rt_harness.cpp run_live_host (diff lines "k == ..") issues bpm, loop, perf, mix_set, publishes, hold, play, stop_track but no `stop()`, and ELECTRO loops so ENDED / Players::songOver / the timer never run under the guard. Add stop and an ending song (has_only = 1 as live_transport does).

F17 (note, P5) thunder_live_alloc blocks go to PadsHost::freeBuf as `delete[] mem` (pads_snap.cpp freeBuf). The contract promises 16-byte alignment; plain `new float[]` is 16-byte aligned on glibc / bionic 64-bit but is not guaranteed on wasm32 or 32-bit; if P5 uses an aligned new it must be freed with the matching aligned delete, or setPadTake must record how the block was made.

F18 (note, tests) live_step_dump accepts a golden prefix of 98 % (test_live_step_dump.cpp:152, `prefix * 100 >= grows * 98`), so a divergence from the golden in the last 2 % of a case passes; the reference (a Seq with the live options, test-driven) catches only differences against the same Seq code. See departure 9.

# Item 4: quantum buffer and time

- Call sizes 1, 64, 127, 128, 129, 4096, frames = 0: process() (:469-488) copies min(frames - done, 128 - qRead_) from q_; qRead_ starts at 128 so the first sample renders a quantum; frames = 0 only prepares (pe_prepare) and publishes. OK (the equals_render test covers 1, 64, 128, 480, 4096; 127 and 129 follow by the same loop). frames = 0 with null pointers is E_ARG (contract: null output is E_ARG: fine); frame0 < 0 is E_ARG even for frames = 0.
- Re-anchor: see F1 (backward), F12 (forward), F14 (overflow). The buffered samples are dropped (qRead_ = 128: a discontinuity, inevitable); voices keep their state; timed commands with `at` in the skipped range apply at the next quantum (due), later ones keep waiting in the new timeline; the sequencer's time is NOT touched (F1).
- Departure 10, the exact expression: voice.cpp:~299-300 `const double t = tb0 + i * dt; if (t < v.t0) continue;` with tb0 = qStart / sr (live_host.cpp:502) and v.t0 the note's booked time, which is the Seq time, which for the host is `(frame0_of_play)/sr + x`. With frame0 != 0 both sides of that comparison carry the offset, rounded differently from the renderer's `x`. A note booked on an exact sample boundary (very common: 120 bpm at 48 kHz is 6000 frames a step) then starts on the right sample in one and one sample later or earlier in the other. So it is NOT only a last-bit rounding of the audio: the note ONSET can move ONE SAMPLE. The test sees <= 1e-6 because ELECTRO's pads fade in from zero (the first sample is ~0); a pad whose first sample is not zero would show a full-size difference at that sample. A host whose counter starts at 1e9 (6 h) has ulp 3.6e-12 s = 1.7e-7 sample and flips on-boundary notes from the first sample, so the 0.001 % figure is only for the 40 s run at small frame0. Ruling: ACCEPT (a one-sample onset on a note timed on a boundary is inaudible and the JS engine has the same property), but state it in live.h TIME, and add a test at frame0 = 2^31 or 1e9 asserting a bound on the difference (not a bit count), and one with a pad whose first sample is non-zero.
