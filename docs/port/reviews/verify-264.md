- Stubbed: `performance.now` (virtual, 1 ms steps), `ctx` (currentTime, getOutputTimestamp, latencies 0), timers (setInterval virtual; `setTimeout` returns 0 and never fires), `document.hidden` = false, the port objects (`send` records `(ts, bytes)`; a native port also has `clear()` that drops not-yet-due messages and validates with the app's own `nmValid`), `pdcPlan` / `pdcModeOf` / `pumpSlotLat` (from the case), `tp` (a bare object). None of these can invent or hide a message from the MIDI code: `send` records everything; `clear` models the helper; a stubbed `setTimeout` is not used inside the cut MIDI section (grep: no setTimeout / rAF / Date.now / Math.random in index.html 16725-17197).
- NOT the app's code (COPIES in the harness): `pump`, `tStart`, `tStop`, `frame` (song-end check), the cable-change handler, `keyOn` / `keyOff` (preview / previewOff). The tool checks 14 lines of index.html verbatim, which covers the pump loop, the bookings, tStart / tStop's MIDI lines and the song-end line, **but not the live-key column naming** (see F1).
- Regeneration: `node tools/midi-ledger.mjs` against the PR's index.html (identical to native 1b7b99d, the commit the notes name): exit 0, all 53 files `ok`; two runs with `--out /tmp/a` / `/tmp/b`: `diff -r` identical; every generated file equals the committed golden (`cmp`).
- Against `origin/beta` (8549509d, after the 19-20 Nov web merges: index.html +2957 / -608 lines, seq-core.js changed): the tool still finds all 16 pieces and all 14 copied lines, `make-core --check` passes, and ALL ledgers regenerate byte-identical to the committed goldens. So no ledger would differ now (for these 24 small songs).
- **F1 (must fix): B11 is not a web bug; the harness invented it.** The harness's `keyOn` names a live key's column `'h' + (HELD.size + 1)` (a copy that is not in the verbatim check list). The real `preview()` (index.html:24184) uses `col = hold ? 'h' + (++pvHoldN) : undefined`, a counter that never goes down, so two held keys never share a column. With the harness line changed to `(++pvHoldN)` and nothing else, the regenerated `panic-keys` ledger has NO note-off at 1004 ms for key 0x40 (it ends at PANIC, 1300 ms, as native does). So the golden `panic-keys` (and its `-web`) is wrong, rules 14 and 15 (B11 drop / add) excuse a difference that does not exist in the real app, and the notes' "choice 2" (B11, "a web bug to fix there too") is false. Native behaviour is right (each key its own column). Fix: harness `pvHoldN`, regenerate panic-keys + panic-keys-web + index, delete the two B11 rules and the B11 mutant's reason, strike B11 from notes 4.3 / 4.5; add a COPIES line for the col naming.

## Item 2. Exact where it claims exact: CONFIRMED, no uncovered difference; two weaknesses (F2, F3)

Method: a small program (own code, uses only the test's fixtures to load a case and run it) dumps every native message (frame, port, cable, kind, bytes) for the 24 native cases; `cmp.mjs` (own comparator) parses both streams, pairs messages by (cable, bytes) within one frame, then classifies the rest as web-only / native-only / shifted. Result per case (web = native message count; exact pairs; differences):

- exact, no difference (15 cases): mono-notes, note-len, overlap-poly, cc-program, cc-ins, slide-arp, bend-fine, modes-mixed, column-switch, echo, lfo-cc, muted-solo (and their sizes 15 11 27 35 7 72 22 6 5 17 172 5).
- chan-share: 1 shifted (OFF 3c: web 833, native 708): rules 11 + 12 (B4 add / drop), counts 1 / 1: true.
- velocity: 1 shifted (OFF 40: 1333 to 1208): rule 13 (B1 move): true.
- two-ports: 86 ticks / Start shifted by the port's Gear delay (42 by -10 ms, 42 by +5 ms, 2 Starts) + 2 Stops: rules 9 (86) and 3 (2): true, counts exact.
- fx-latency: 31 (30 ticks + Start, -4.008 ms) + Stop (+67.6): rules 10 (31) and 8 (1): true.
- tempo-clock: 7 shifted (6 ticks 7 to 76 ms, all inside 2355..2570, + Stop +3): rule 22 (zone, 10 web ticks) and rule 4: true.
- tempo-live: 23 ticks in two zones + Stop: rules 23 / 24 (15 and 15 web ticks; native 14 and 16) and rule 5: true.
- start-stop / start-midway / loop: Stop moved to the stop time (B8, rules 2 / 0 / 1), 2 web OFFs of a note that never sounded dropped (B9), 1 explicit OFF of the note that did sound added (B9): rules 16-17 + 25 / 20-21 + 26 / 18-19 + 27: true, counts exact (web 74 / 158 / 271; native 73 / 157 / 270).
- song-end, clock-port-toggle: Stop +3 ms (B3, rules 6 / 7); clock-port-toggle's cable-change Stop (web ts null = 0, native at the change, 2600) is rule 28: true.
- panic-keys: see F1.
- Total: every difference found by my comparator is inside a rule and every rule's count equals the number of web messages it touches. No rule is a wildcard: `gear` and `stop` rules shift only messages of the named bytes / kind by the port's own Gear delay (and FX latency for Stop), each with an exact count; a native extra or missing message still fails the test.
- Weaknesses:
  - **F2 (should fix): the output is not in time order and the test is order-blind.** The ledger test matches as a multiset. In every case with a clock, native emits tick 0 BEFORE Start (and before the first note) at the identical frame (cases two-ports, tempo-clock, tempo-live, start-stop, song-end, start-midway [before Continue], clock-port-toggle, loop). Cause: `book()` runs `moClock` / `moLfo` / `moRamp` / `moEcho` (their messages are within the 60 ms lead, so `send` emits at once) BEFORE `flush()` releases the earlier pending messages (Start, notes). The web sends Start first (it ledgers `fa` then `903c7f` then `f8` at 583). A gear that arms on Start loses tick 0; LFO CCs also overtake the note at the same time (lfo-cc: 6 pairs) and ticks overtake earlier-timed pending notes (the stream is non-monotonic per cable: 14 / 21 / 58 inversions in tempo-clock / tempo-live / lfo-cc). A shell that sorts by timestamp with a stable sort still gets Start after tick 0 at the same frame. Fix: `flush()` first in `book()` / or insert everything in the outbox and flush once at the end, and add an order check to the ledger test (equal frames keep the web's order; Start before tick 0).
  - **F3 (note): the B2 zone rule is weak.** Inside a zone (up to 285 ms) native ticks are only checked to be monotonic with intervals between the two tempos' tick lengths; a wrong tempo map that is merely inside those bounds passes. See item 3 for my own oracle test.
- The 4 `-web` ledgers: they record the same four cases (start-stop, song-end, clock-port-toggle, panic-keys) on a browser port without `clear()`, with the web's outbox (messages held until 60 ms before their time, sorted, dropped at STOP) instead of the helper's clear. They would check the `set_lead(0.060)` outbox path of native against the web's MOB rule (R-M31) with the CLEAR marker not applied. Not running them leaves a gap only for a shell without `clear()`: Web MIDI, AMidi, WinRT, which is the default lead 60 ms path of every shell but the helper; i.e. the outbox is exercised only by unit tests and by the native ledgers' own use of lead 60 ms, but the "no clear" STOP behaviour (what a cleared outbox must NOT leak) is not compared to the web. Low risk because `release()` drops the pend array; note.
