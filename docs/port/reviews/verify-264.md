## Item 2. Exact where it claims exact: CONFIRMED, no uncovered difference; two weaknesses (F2, F3)

Method: a small program (own code, uses only the test's fixtures to load a case and run it) dumps every native message (frame, port, cable, kind, bytes) for the 24 native cases; `cmp.mjs` (own comparator) parses both streams, pairs messages by (cable, bytes) within one frame, then classifies the rest as web-only / native-only / shifted. Result per case (web = native message count; exact pairs; differences):

- exact, no difference (15 cases): mono-notes, note-len, overlap-poly, cc-program, cc-ins, slide-arp, bend-fine, modes-mixed, column-switch, echo, lfo-cc, muted-solo (and their sizes 15 11 27 35 7 72 22 6 5 17 172 5).
- chan-share: 1 shifted (OFF 3c: web 833, native 708): rules 11 + 12 (B4 add / drop), counts 1 / 1: true.
- velocity: 1 shifted (OFF 40: 1333 to 1208): rule 13 (B1 move): true.
- two-ports: 86 ticks / Start shifted by the port's Gear delay (42 by -10 ms, 42 by +5 ms, 2 Starts) + 2 Stops: rules 9 (86) and 3 (2): true, counts exact.
- fx-latency: 31 (30 ticks + Start, -4.008 ms) + Stop (+67.6): rules 10 (31) and 8 (1): true.
- tempo-clock: 7 shifted (6 ticks 7 to 76 ms, all inside 2355..2570, + Stop +3): rule 22 (zone, 10 web ticks) and rule 4: true.
- tempo-live: 23 ticks in two zones + Stop: rules 23 / 24 (15 and 15 web ticks; native 14 and 16) and rule 5: true.
- start-stop / start-midway / loop: Stop moved to the stop time (B8, rules 2 / 0 / 1), 2 web OFFs of a note that never sounded dropped (B9), 1 explicit OFF of the note that did sound added (B9): rules 16-17 + 25 / 20-21 + 26 / 18-19 + 27: true, counts exact (web 74 / 158 / 271; native 73 / 157 / 270).
- song-end, clock-port-toggle: Stop +3 ms (B3, rules 6 / 7); clock-port-toggle's cable-change Stop (web ts null = 0, native at the change, 2600) is rule 28: true.
- panic-keys: see F1.
- Total: every difference found by my comparator is inside a rule and every rule's count equals the number of web messages it touches. No rule is a wildcard: `gear` and `stop` rules shift only messages of the named bytes / kind by the port's own Gear delay (and FX latency for Stop), each with an exact count; a native extra or missing message still fails the test.
- Weaknesses:
  - **F2 (should fix; see summary): the output is not in time order and the test is order-blind.** The ledger test matches as a multiset. In every case with a clock, native emits tick 0 BEFORE Start (and before the first note) at the identical frame (cases two-ports, tempo-clock, tempo-live, start-stop, song-end, start-midway [before Continue], clock-port-toggle, loop). Cause: `book()` runs `moClock` / `moLfo` / `moRamp` / `moEcho` (their messages are within the 60 ms lead, so `send` emits at once) BEFORE `flush()` releases the earlier pending messages (Start, notes). The web sends Start first (it ledgers `fa` then `903c7f` then `f8` at 583). A gear that arms on Start loses tick 0; LFO CCs also overtake the note at the same time (lfo-cc: 6 pairs) and ticks overtake earlier-timed pending notes (the stream is non-monotonic per cable: 14 / 21 / 58 inversions in tempo-clock / tempo-live / lfo-cc). A shell that sorts by timestamp with a stable sort still gets Start after tick 0 at the same frame. Fix: `flush()` first in `book()` / or insert everything in the outbox and flush once at the end, and add an order check to the ledger test (equal frames keep the web's order; Start before tick 0).
  - The B2 zone rule is weak (F5): inside a zone (up to 285 ms) native ticks are only checked to be monotonic with intervals between the two tempos' tick lengths.
- The 4 `-web` ledgers (F9): I ran the native scheduler against them with a shell that ignores CLEAR (a port without `clear()`, default lead 60 ms, the outbox dropped at STOP): `song-end-web`, `clock-port-toggle-web`, `panic-keys-web` differ from native exactly as their native twins do (same rules). `start-stop-web` has TWO web-only messages the native twin does not: a clock tick at 1937.167 ms, after the Stop at 1900 (a browser port cannot recall a message already handed over), and the stray OFF 41 at 2084. Native sends neither. No rule covers them because the ledger is not run: an unlisted web leak, harmless, but "nothing may differ silently" is not true for the `-web` files. They record the same four cases (start-stop, song-end, clock-port-toggle, panic-keys) on a browser port without `clear()`, with the web's outbox (messages held until 60 ms before their time, sorted, dropped at STOP) instead of the helper's clear. They would check the `set_lead(0.060)` outbox path of native against the web's MOB rule (R-M31) with the CLEAR marker not applied. Not running them leaves a gap only for a shell without `clear()`: Web MIDI, AMidi, WinRT, which is the default lead 60 ms path of every shell but the helper; i.e. the outbox is exercised only by unit tests and by the native ledgers' own use of lead 60 ms, but the "no clear" STOP behaviour (what a cleared outbox must NOT leak) is not compared to the web. Low risk because `release()` drops the pend array; note.

## Item 3. Each fix (web code read, native tested with my own tests through MidiSched and the C API)

- **B1** web bug REAL (`moNote` returns at index.html:16927 before `moOff`; ledger `velocity`: OFF 40 at 1333 vs native 1208). Fix right and minimal: mono only (`if (!e.poly) moOff`), no ON sent. My test: silent mono note ends the previous note at its own time, no ON; poly column unchanged (same as web); a vel that is > 0 but rounds to 0 still sounds at vel 1 (web clamp): OK.
- **B2** web bug REAL (`moClock` :17062: ticks from the NEWEST anchor with the CURRENT bpm, backwards). Native: monotonic, regular, correct for a LIVE tempo change (my oracle: ticks vs the step grid, `tempo-live`: max error 0.43 frame) and correct past step 256 with a tempo change at step ~320 (0.49 frame, 451 steps). **But see F5**: after a TPO command ON A ROW, native (like the web) leaves the clock permanently offset from the notes.
- **B3** web REAL (`msendClk` :16844 passes `early=false`). Fix: Start / Continue / SPP / ticks / Stop get the port's Gear delay. With delay 0 nothing is shifted (all 22 cases without a delay are exact; my test: Start at 1000.000 / 960.000 / 1030.000 ms for delay 0 / +40 / -30). It changes behaviour the owner's gear may rely on only if a clock slave was tuned around the old offset: a positive delay now moves the clock EARLIER with the notes (intended by the ruling). Note: a positive delay of up to 200 ms puts ticks up to 80 ms of musical time past the STOP before the Stop message (all stamped before it): harmless.
- **B4** web behaviour REAL (MIDI has one note state per channel+pitch; offOne :16846 cuts the other track's note); fix = per-track ownership + a per port / channel / pitch count. My test (3 tracks, one pitch, offs at 1.3 / 1.4 / 1.5 s): 2 retrigger OFFs + the last holder's OFF at 1500; gear silent after STOP; collision counted. The count runs in emission order, not time order; a hang cannot result (an OFF is never emitted before its own ON).
- **B5 / B6** web REAL (`mx.ccv` and `mx.used` are only ever added to: :16641, :16746, :17007, :17009, :17184). Fix right (cleared in STOP after the All Notes Off). My test: run 2 sends All Notes Off only on its own channel; the first CSL glide after a STOP jumps to its start value. Side effect to know: :16641's comment says KEYS PLAY's CC thru is meant to seed a later CSL glide; after a STOP that seed is now forgotten (as ruled).
- **B7** web REAL (`moClock` cap 512 :17068; `moEv` runs before the pad's lateness test :23815 / :23827). Fix: no cap (loop bound 4096 per call, bounded), ticks more than 20 ms late dropped and counted, never clamped (phase kept). My stall test (400 ms and 3 s hosts): ticks strictly increasing, on the 1000-frame grid, min spacing 1000. Notes: (a) the page never drops a MIDI-ONLY (mo 1) note for lateness (it `continue`s before the test), native drops it with the shared flag: wider than "a late-dropped pad note drops its MIDI note" (F8); (b) F6.
- **B8** web REAL and harmless (`moStop` stamps after the last BOOKED tick, but `moRelease` cleared it first; ledger: Stop at 1938 vs last tick sent 1895). Fix right (stop time + FX latency - gear, never before the last tick sent).
- **B9** first part right (my test: STOP before a note's time: no OFF). **Companion incomplete (F3)**.
- **B11** NOT a web bug (F1).

### F3 (should fix): B9's explicit OFF is missing when the note's own OFF is already in the ring
`emit()` decrements the pitch count when the OFF LEAVES the outbox (within the 60 ms lead), not when it is due. A STOP in the last 60 ms of a note (OFF already emitted, frame after the stop) has count 0, so `releaseAll` sends no OFF, and the shell's CLEAR drops the queued OFF: the note hangs unless CC 123 is honoured. My test: note 1.000 to 1.500 (cut), STOP at 1.460: stream `1000 on, 1460 CC123` and the gear stays on if it ignores CC 123. The web sends an OFF now (the held entry has end > now). So the notes' "explicit OFF for every note that really sounds at STOP" is false for about 60 ms before each note end (about a tenth of the notes of a gate 0.5 s long). No ledger case or mutant covers it. Fix: keep the per-pitch sounding state by TIME (count a note until its OFF frame has passed), or in `releaseAll` also OFF every pitch whose last emitted OFF frame is after `nf`.

### F5 (should fix, owner's call): after a TPO command on a row the clock stays offset from the notes
`seq.cpp:736` (and the web's seq-core) adds `(t0 - btT_) * bpm_ / 60` with the tempo set BY the previous step's TPO, over an interval that step timed at the OLD tempo. `MidiSched::onStep` integrates the anchors the same way (`anc_[n-1].bpm` is the tempo AFTER the step). Result (my oracle: ticks vs the actual step times): tempo-clock (TPO 90 at row 16): every tick after the change is 2400 frames = 50 ms late relative to the notes' grid (swing 50 variant: 2000 frames = 41.7 ms), permanently, growing with each further TPO. The web has exactly the same offset (the ledger's ticks after the zone are exact), so this is not a regression, and it is why the "exact outside the zone" rule passes; but B2 was ruled as "integrating the tempo map". Fix: integrate each interval with the tempo in force when the step STARTED (the previous anchor's value), not after it. A live tempo change (setBpm between steps) is already right.

## Item 4. Real-time safety

- Audio-thread entry points (`thunder_midi_process`, `onStep`, `onEvent`, `book`): no `new` / `delete` / lock / I/O in the sources (read in full; the scan in rt_midi covers the same tokens); loops bounded: command ring 256 per block, ticks 4096 per call, LFOs 64 x 40, glides 64 x 40, echoes 512 (each scanned against 34 x 128 held notes: about 2 million operations worst case), release 8192, outbox 4096 (insertion is a memmove: O(n) per message, up to 160 KB; worst case O(n^2) per block, only at a full outbox, which is counted). Tempo map: 256 anchors; at step 257 the oldest is dropped (memmove), ticks older than the oldest anchor are counted late; my tests: 600 s at 131 BPM (1200 steps) and a tempo change at step 320: no error (0.49 frame).
- `rt_midi`: the guard replaces `operator new/delete`, glibc `malloc/calloc/realloc/free` and `pthread_mutex_lock` / `pthread_cond_wait` and aborts inside the audio region; `--selftest` forks a child that allocates and one that locks inside the guard and requires SIGABRT from both: both caught. It covers the direct C++ path (a MidiSched fed by SeqRunner, with panic, stop, start, port edits, live keys, a 0.4 s stall) AND `thunder_midi_process` of a handle (with posted commands, set_song hand-over); it does NOT cover spin locks / atomics (not needed). The handle's scheduler gets no sequencer events in that test (the C API has no event entry), so the C-API path is exercised for commands only.
- SPSC ring (`rt/spsc.h`): one producer, one consumer, release store / acquire load, correct. TSan (midi_api.cpp + midisched.cpp + test_midi_api compiled with `-fsanitize=thread`, rest from the Release library), `test_midi_api --threads` 5 runs: 0 reports, 3000 commands and about 51 000 records each. My mutant (`head.store(..., relaxed)`) is caught by TSan (63 reports) and NOT by the normal tests: so the TSan run matters and is not in ctest or CI (notes say so).
- Control-thread calls: each posts one command on a 256-slot SPSC ring (wait-free); only `set_song` allocates and parses; the audio thread returns the old song on a retire ring; at most 6 songs outstanding. Safe for ONE control thread, as the header says ("never more than one thread in each role"): two threads calling `thunder_midi_raw` (MIDI thru) and `set_port` (UI) would both be producers of one SPSC ring: a data race. A shell must serialise (F10).
- **F4 (should fix): ring full: nothing is protected.** `push()` drops the newest record whatever it is. My test: note ON, 9000 CC messages with no consumer (ring 8192 records full), then the note's OFF and a STOP: the drained ring holds 8192 records and contains no OFF, no CLEAR and no All Notes Off (ringFull = 812). The note is left on and the cable is not cleared. The counter exists, the policy does not (the check item "a NOTE-OFF is never the thing dropped while a note is on" fails). Fix: reserve the last N slots (say 512) for OFF / CLEAR / All Notes Off / Stop and drop low-priority messages (CC, ticks, LFO, echo, bend) first.
- Hostile input (my own test of every C entry point, plus 20 000 random control calls interleaved with process and drain): NULL handle, port -1 / 4 / 9, channel / note / key / instrument out of range, len 0 / 4 / mismatched, NaN / negative / 1e9 times, `drain` with cap 0 / NULL / negative, `stats_get` with a bad size, garbage / empty / NULL song, bad create rates: 50 calls all return an error code; extreme finite times (1e300 s, 1e-300 BPM) do not crash. (ASan + UBSan run: see item 7.)

## Item 5. Units and timing: CONFIRMED, one limit (F6)

- Sample rates: 44100 / 48000 / 96000 give the same messages (same bytes) with times within 18 us (< 1 frame of 44.1 kHz) on tempo-clock, slide-arp, lfo-cc, echo, start-midway.
- Block sizes 1 / 128 / 480 give IDENTICAL streams (frame, bytes, cable, order) on 11 cases (mono-notes, slide-arp, echo, lfo-cc, cc-program, tempo-clock, loop, two-ports, overlap-poly, start-midway, fx-latency; start at frame 61440 = lcm of the blocks, STOP at a fixed frame). **F6 (note): 4096 frames at 48 kHz (85.3 ms) does not**: it is longer than the 80 ms clock horizon plus the 60 ms lead minus the 20 ms late limit, so ticks booked in the 60 to 65 ms window are 20+ ms late at the next block and are dropped (6 to 11 of about 190 ticks in 4 s are lost; stats `lateTicks`), the Start / tick order differs and lfo / cc timing differs. The horizons are constants, not scaled to the block.
- Long runs: all frames are `int64` (`frameOf` = `llround(sec * sr)`); at 96 kHz and 7200 s the frames reach 6.9e8 (still below 2^31; int64 anyway); no float seconds accumulation: tick k is `anchor.t + (k/24 - anchor.b) * 60 / bpm` from a recent anchor. 10 minutes at 131 BPM (31 439 ticks): max |error| 0.4962 frame (the rounding), mean error of the first / last 1000 ticks 0.004 / 0.003 frames at 48 kHz (0.0002 / 0 at 96 kHz), spacing 916 / 917 frames: no drift, same result when the run starts at 7000 s. No late tick.
