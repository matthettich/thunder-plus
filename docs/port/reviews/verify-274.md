### F1 FIX BEFORE MERGE: test 9 does not prove equality with `runBlocks`; with the `Seq` at time 0 the first beat differs from the web
Evidence: `test_midi_glue.cpp:71-82` (`runDirect`: `Seq` at 0, `sched.start(.., 0)`), `:100-103` (case list: row-0 cases only; `start-midway` not in it), NOTES decision 3 ("It is the same loop"), `midi_drive.h:174-176` (`seq->setTime(now + 0.08)`), `midisched.cpp:495` (SPP at `e.t - 0.05`, Continue / Start at `e.t`), `midisched.cpp:80-84` (`send`: `at < now_ && kind != MK_CLOCK` -> `at = now_`), `render.h` (no way to set the `Seq`'s time: `seq_` private, `setTime` unreachable).
Reproduction: `native/tests/verify_274.cpp` (this branch; build line in its header). It renders each ledger song through `SongRenderer` + `setMidi` (Seq at 0, no FX latency) and through `runBlocks` (block 128, `fxLat` 0, same ports), and compares record by record with the frames moved by the Seq start of `runBlocks` (Play block's `now` + 0.08 s = 27904 frames at `playAt` 500 ms). Result at 4a9d9b94:
  - 14 of the 18 songs equal (first 13..219 records identical).
  - `two-ports`, `fx-latency` (Gear delay > 0 + clock out): runBlocks' first record is the Start (`FA` at 27424); the renderer's first record is a clock tick `F8` at frame **-480** (negative frame), and its Start is clamped to frame 0: **a tick goes out before the Start**, and the Start is the Gear delay late against the tick grid.
  - `cc-ins`, `cc-program`: first record 48 frames (1 ms, the Gear delay) late: `send` clamps `e.t - gear` to the block's start.
  - `start-midway` (row 2, clock out): runBlocks sends SPP `F2` at 25504 (50 ms before Continue); the renderer sends **SPP and Continue on the same frame (0)**: the 50 ms the web leaves the gear to find the position is gone. (Not covered by any PR B test: test 12 `spp_for` only checks the number.)
Why it matters: the web's `seq.setTime(now + 0.08)` is what gives `send` room for SPP's -50 ms, for Gear delays up to 80 ms, and for the first ticks. The audio-thread glue is correct; what is wrong is the claim and the missing hook.
Answer to "is the builder's equivalent fair?": for the *glue* (are the three calls made, in order, with the right arguments) yes: it is the same code on the same 128-frame cadence, and it catches a wrong `now`, `block_sec`, mask, latency (F7). For the *spec's requirement* (the stream equals `runBlocks`) it is not: it hides exactly the 0.08 s lead and what depends on it (Start / SPP / first beat / first Gear-delayed events).
What U37 must do: (1) start the `Seq` at `t0_of_the_first_block + 0.08` when it posts `thunder_midi_start` in the same block (so the audio starts 80 ms later too, as the web's does); `SongRenderer` needs an entry for it (a `startAt(double)` / a `Seq` time in the constructor options: it has none today); (2) post `thunder_midi_start` before that block, `clock_map` before the block (F6); (3) post `thunder_midi_stop` when `songOver()` has held for 0.3 s (spec 2.5; `render.h` does not say the renderer never stops the scheduler by itself) and before destroying the renderer, run one `midi_begin` / `midi_end` (or `thunder_midi_process`) after the stop so its CLEAR / note-offs are made: the renderer's destructor does nothing for the hook.
Fix: say it in `render.h` (`setMidi`) and NOTES decision 3; add the `Seq` start offset (or the sentence "U37 owns it" and the three points above) and extend test 9 with `start-midway` shifted by the lead once the setter exists. No change to the three calls.

### F2 FIX BEFORE MERGE (comments) / LEAD TO RE-RULE: the web does NOT drop late notes on the core's routes; the "web's rule for live engines and SoundFonts" is wrong
Evidence: `players.h:36-37`, NOTES decision 5, `players.cpp:37`. Web (`origin/beta`): `index.html:25325` drops `e.type === 'note' && e.t < ctx.currentTime - 0.15`, but only AFTER `if (e.core){ ... continue; }` (:25315-25321): the drop applies only to notes the **core did not play**. The core plays: sampler pads (`core-processor.js:559-566` `mine`, `startNote` :576, start at `t0n = Math.max(ev.t, currentTime)` :591), **SoundFont pads** (`mine`: `k.sf` -> `startNote` -> `sfNote`, `st0 = Math.max(ev.t, currentTime)` :447) and **live engines** (`liveNote` :694, `liveStart` :720). Everything else (stretched SYNC notes, MUT/GEN variations the core has not got, unprepared pads) is the page's and is the only thing `coreMsg` drops. Also, for those page notes the drop is a `continue` before `playEv`: **the previous voice is not ended**.
Gear: `moEv` (`index.html:18153`) is called at :25313, BEFORE the lateness test, and calls `moNote` with no lateness check: in the web a late OUTPUT 2 note IS sent to the gear (clamped to `now` by `msend`); only the pad side is dropped. Native (`midisched.cpp:522`, U35's B7/F8 decision, inherited, not new here) drops both.
Audible difference, precisely (setDropLate on, a note more than 0.15 s behind the quantum's start, i.e. only after the sequencer lags the audio clock: a stall, a seek, a host that advances `qFrame_` by wall time):
  - sampler, SoundFont, live engine, MONO: web plays the note at once, from the start of its sample, `currentTime` late, and ends the previous voice at `e.t`; native plays nothing and ends the previous voice (silence for that hit; the web's burst of late hits is gone).
  - same, POLY: web plays it late (cap / choke rules as usual); native plays nothing and touches nothing (a late poly note that would have choked its group does not).
  - page-played notes (rare): web drops the note and leaves the previous voice ringing; native drops it and, if mono, ends the previous voice.
  - OUTPUT 2 to the gear: web sends the late note; native does not (`late && I.mo != 1`); OUTPUT 1 (MIDI only): both send.
  - empty kit slot / refused note: a late MONO note takes the track over (`takeAll`) before the "no pad" return; an on-time one on an empty slot touches nothing (`players.cpp:36` runs after `:34` but the late branch precedes the `buf.data` test at :64). Minor.
  In steady playback with the `lead` of 0.25 s none of this happens (the lag cannot reach 0.15 s). After a stall the native behaviour is what the web's own comment says it wants ("dropped, not played at once in a burst"), which is the reason I do not call it wrong, only mis-described.
Decision for the lead: (a) keep "one rule, everything late is dropped, the previous mono voice still ends" (current), correcting the comments to say the web's core plays these notes at once and the web's gear path sends them; or (b) match the web: leave `setDropLate` off for core routes (it would then only mean something for a MIDI-aware page player that does not exist natively) and drop only MIDI. I recommend (a) with the comment fixed. A late mono note ending its predecessor is MidiSched's rule, not the web's pad rule (the web's drop of a page note does not).
Test gap: `test_midi_glue` test 11 only has a sampler voice as the "previous voice"; mutants that remove `live_.take` (M3b) or the SoundFont part of `takeAll` (M3c) pass every test. A test with a SoundFont / live previous voice would pin it (not written: the live node needs a node registration).

### F3 FOLLOW-UP: the ordering test is vacuous: `onStep` after the dispatch loop changes no output
Evidence: mutant M1 (below): `onStep` moved after the `dispatch` loop inside the step loop: all of `test_midi_glue`, `rt_midi`, `test_players`, `test_render_dispatch` pass. `SongRenderer::dispatch` / `Players::dispatch` take `const SeqEvent&` and never touch `Seq` or `MidiSched`, so within one step the order is unobservable; the spec's "whole step before its events are dispatched" (2.2) is satisfied by the code and not enforceable by a test unless `dispatch` ever writes. What IS enforced: `onStep` inside the loop, before the next `seq_->step` (the event buffer is reused). Say so in the comment ("the order midi_drive.h pins" is not a thing a test can pin here), or leave it.

### F4 NOTE: first block, quantum with no steps, end of song, begin failure, lifetime
Evidence: `render.cpp:96-107`, `midi_api.cpp:165-176`.
- Order and arguments are exactly spec 2.2: `t0 = qFrame_ / sr_` (`now`, the quantum's start, never `+ block`); `block_sec = kRenderQuantum / sr_`; `fxLatSec = clamp(latencyFrames() / sr_, 0, 2)` read every block (a NaN becomes 0: `std::max(0.0, NaN)` returns 0.0); `audible = mix_.audibleMask()` (`uint32 audible_` widened; high bits 0 = always heard, as `audibleT`). `players_->setTime(t0)` runs before `midi_begin`, so `Players::t0_` and `MidiSched`'s `now` are the same number (one lateness verdict).
- A quantum with no step: `midi_begin` and `midi_end` still run (`book` releases the outbox, clock, LFO, glide), as 2.2 says; the cadence test (`song-end`, tails after the last step) covers it.
- `midi_begin` can only fail for `blockSec` outside 0..1 (sample rate under 128 Hz: `SongRenderer` does not validate it) or a non-finite `now`; with the clamp it cannot fail in practice. If it did, `midi` is false for the whole block: `onStep` and `midi_end` are both skipped, so nothing is half-done in the scheduler, but the block's steps still advance the audio and their events (an OFF among them) are lost to the gear: a hung note is then possible. `midi_end` refuses a non-positive / non-finite `bpm` or `seqTime`: `Seq` keeps bpm in 40..300 and time finite, so it cannot happen. Both return values are ignored silently (no counter). NOTE.
- Song end: `book(.., alive=false)` ignores `seqAlive`; the clock keeps its ticks to `seqTime`. Nothing in the renderer stops the scheduler (U37, F1 point 3). Verified with `song-end`: the stream equals the direct drive.
- Lifetime: `midi_` is a raw non-atomic pointer: a handle freed while the renderer lives is a use-after-free at the next quantum; `setMidi(nullptr)` from the control thread while the audio thread renders is a data race (the header says "control thread, before the first block", like `setEffects`: enforce nothing, state it for U37 if it ever needs to detach live). The reverse (renderer destroyed, handle alive) is safe for the core and leaves the scheduler in whatever transport state it had (F1 point 3).
- Null hook, no behaviour change: `midi_ &&` short-circuits (neither `latencyFrames()` nor `audibleMask()` is evaluated), the two `if (midi)` are false, `setStem` gains `|| midi_` (null), the three `(uint32_t)` casts of the widened `audibleMask()` are value-preserving, `Players` adds one relaxed load + branch per NOTE and one store in `setTime`. Render goldens: in the full ctest (all render / stem / players / dispatch tests pass).

### F5 NOTE: `setMidi` / `setStem` refuse each other; no path found where a stem's mask reaches MIDI
Evidence: `render.h:147` (`h && stem_ >= 0` false), `render.cpp:45` (`|| midi_`). The only caller of `setStem` is `render_api.cpp:138`, which sets no hook (and ignores `setStem`'s return value: harmless today, but a future API that attaches a hook before the stem would silently lose the stem: check the return there when that day comes). `setMidi(nullptr)` on a stem renderer returns true (a no-op). `mixer().setHeard()` through `mixer()` bypasses the refusal (builder knows; no host does). `render_api` never sets a hook, so the offline API cannot lose stems.

### F6 FOLLOW-UP: midiport: gone token, races, and the hold
Evidence: `midiport.cpp:161-175` (`resolve`, `markGone`), `:184-198` (replay), `:323-345` (hold), `:333` (comment), `midiport.h:11-18`.
Gone token. `resolve` and `markGone` run on the pump thread only; control writes `cabTok`, `cabLive`, and clears `cabGone` (`set_devices`). The TOCTOU of #268 (compare with the current token, then store) is closed: the failed token is stored first, the mark after it (release), and `resolve` mutes only if mark AND token match the cable's current one. Walked: replacement between the failed send and the mark -> the old token is marked, the new one resolves (not muted); a stale mark of an old token is cleared by the next `set_devices` that touches the cable; an older failed token (replay of history) cannot move the mark off an already marked current token (`markGone` early return). Residual, documented: control clearing the mark just before the pump marks a failure that happened before the `set_devices` began leaves the same token gone until the next `set_devices` (NOTE; a shell that re-lists the unchanged device on every scan re-arms it). The test (`testGoneToken`) puts the replacement inside the failing send, which is the deterministic version of the window; note that the OLD code also passed that exact sequence (it compared with the new token and did not mark), so the test pins the outcome, not the old race. Mutant M4 (`resolve` ignoring the token) fails 2 checks.
Hold. Before the first map nothing is sent: step 3 returns at `:345` (`!map.valid`); a CLEAR still applies to the queue (`applyClear` is not map dependent); the epoch sweep still drops unlisted devices; evictions follow F4's order (note-off / Stop / CLEAR never victims; `may_hang` only if the queue is 4096 deep in them: not reachable). Mutant M6 (re-dropping at `!map.valid`) fails 7 checks of `testHold` / test 4. `dropped_nomap` is documented correctly in `midiport.h:12-14, :92` ("no longer counted, kept for ABI"); **stale**: `U36-SPEC.md:135/159` still says "frames before the first map are not sent (`dropped_nomap`)" and PR A's decision 6 / NOTES; add the 21 Nov ruling line to the spec.
What the first map does to a backlog: the queue is frame-sorted (stable), so order is kept (Start before notes: `testHold 1`); everything whose time has passed is sent in one pump call with a past stamp, counted in `late`; clock ticks more than 20 ms late are dropped (`dropped_late_ticks`); notes, Start, SPP are never dropped for age. Probe (`verify_274.cpp` `holdBurst`): 6 notes + 6 offs spread over 1 s, no map for 1.07 s, then the first map: **11 messages go out in one `pump` call, 10 of them stamped more than 150 ms in the past** (a stale burst, the "late burst" the lead accepted). That is fine for the 4 notes of the flake (microseconds) and wrong for a shell that forgets `clock_map` for seconds: consider dropping non-essential records (note-ons, CC) older than `kNoteLateSec` at the first map and keeping Start / SPP / note-offs / Stop.
Order of `clock_map` and `process`: the header now says "BEFORE `thunder_midi_process`". With the hold the "before" order is no longer needed for correctness, and it costs something: the floor (`midiport.cpp:~289`, `midi_last_now`) reads the previous block start when the map comes first, so when the floor is active (`imp < fl`) the offset is one block (one 128-frame quantum = 2.67 ms in the renderer) later than with the map after `midi_end`; the header's "after the first map the order does not matter" is therefore not exactly true (CodeRabbit's open comment on `midiport.h`, 13:03, makes the same point). And with the map AFTER the block the first map would get the floor too (CodeRabbit's withdrawn first-map comment). Recommend: document "after `midi_end` of the block, and before PLAY for the first one", now that nothing is lost either way.

### F7 NOTE: real-time safety of what the hook adds (audio thread)
Read: `midi_begin` (`blockBegin`: `setFxLatency`, `setAudible`, pops at most `kMidiCmdCap` = 256 commands, `setBlock`), `MidiSched::onStep` (loops bounded by the step's `n`, 32 tracks, fixed arrays; `releaseAll`'s 4x16x128 sweeps run only on STOP / PANIC / cable edits), `midi_end` (`book` + 28 relaxed stores). No allocation, lock, exception (core is `-fno-exceptions`), I/O or unbounded loop.
`rt_midi` covers the path: it renders `SongRenderer::block` with a hook, `setDropLate(true)`, PLAY / STOP / cable / clock / keys / panic / new songs between blocks, under the `operator new` / `malloc` / `mutex_lock` guard. I put `::operator new(16)` / `operator delete` in `quantum()` right before `midi_end` (mutant M5, local): `rt_midi` aborts with "operator new inside the audio callback". Notes: `rt_midi --selftest` only checks the guard itself (a child that allocates / locks), not the glue; the guard does not cover `pthread_mutex_trylock`, spinning, I/O syscalls; `scanSource` does not scan `render.cpp` / `players.cpp`; the renderer in `rt_midi` has an empty `RenderPads` and a steady clock, so `Players`' new late branch is never executed under the guard (it only calls `takeAll` / `live_.take`, which the normal path runs).

### F10 NOTE: the flake explanation (`midiport_threads`: posted 2996, sent 2992, dropped_gone 0)
Verified from the code: every record the pump removes without sending is counted: no map -> `S_NOMAP` (the only uncounted-looking branch, because the failure message did not print it), unlisted / gone -> `S_GONE`, failed send -> `S_ERR` + `S_GONE`, CLEAR -> `S_CLEARED`, full queue -> `S_QFULL`, late tick -> `S_LATE` + `S_LATETICK`; late notes are still sent. With `dropped_gone 0` and `send_errors 0` the only branch left that can lose 4 records is no-map, and the old order (`clock_map` after `process`, sender polling every 200 us) opens exactly that window for the first block's posts. The ledger check (`made == sent + gone + cleared + nomap + late_ticks + queue_full`) is sound for the non-TS threads run: no CLEAR, `ring_full` 0 checked, `sent` counted only on acceptance; for CAP_TS or CLEAR runs messages are counted twice, as the builder says. I could not reproduce the loss here: the builder's "deterministic" `midiout_flake` (old order, 3 ms gap) printed `posted 2964, sent 2964, no-map 0` on 428248ea's own test on this loaded machine, so that test was itself timing-dependent (the test is now "nothing is lost", independent of timing). With the hold the loss cannot occur whatever the order, which makes the explanation moot; it stands as the best reading, not as proof.
