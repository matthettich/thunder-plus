## Findings

* **F1 (must fix): the idle skip is not bit-identical.** It drops the last `lat` samples (about 26-31) of a voice's last block. The shell runs `lat` samples ahead of the mixer; when the core goes idle the ring still holds rendered-but-undelivered samples, the node is skipped from the next quantum (`runNode`), and `fastForward` zeroes the ring (all of it once `nb*kBlk >= kRing`). Reproducer (my `vfy_pool`, delta-debugged): ONE bass note at t=1.726963 (rate 0.612, col 2) + its off at 1.795206, default pad, track 0: skip ON vs `setIdleSkip(false)` differ in 26 consecutive samples at frame ~182272, skip gives 0 where processing gives -2.19e-06 ... -9.8e-08 (smoothly decaying tail). Second: mach pad, note t=0.629775 track 1 + `stopAll(2.241293)`: 15 samples, max 8.2e-07. Over 300 random scripts 14 differ (bass 6, acid 3, mach 5, vox 0), every one a tail of 1e-7..2e-6 (-114 dBFS and below), stats identical. Inaudible, but the bar is "no sample". `test_live_idle` (305 pairs, passes) does not see it. Scratch fix (not committed): skip only after the core has been idle a whole quantum (`idleSeen`): 14 -> 1 differing script; the one left runs at host block 1 (quantum < lat), so the rule must be "idle for at least lat + kBlk samples", not "one quantum".
* **F2 (must fix): the vox "held" parity fix is not a fix, and the stated cause is wrong about the page.** The PR changes no engine code for it: the pool's rate lane still starts at 0 (`AutoN<kAutoRate> rate{0}`) and the failing scenario `held` was moved from `on(10), eng(10,...)` to `on(0), eng(0,...)` so the difference no longer shows. The notes say "the page's AudioParam default is 0". It is **1**: `index.html:22571` (bass), `:22656` (vox), `:22738` (acid/mach) `{name:'rate', defaultValue:1}`; the builder's own table (LIVE-ROUTE-NOTES 2a) says `rate a 0..256 (1)`; nothing sets `rate` before a node's first note (node made at `:21685`, `rate` touched only in `bassNote`). THUNDER CORE's `__tcOv` (core-processor.js:157) feeds the node, for every sample before the override's first event (`A.from`), the node's own AudioParam value = 1; the core's `Auto(0)` list only holds the lane's own events. So seqRender (idle default 1) = the page, and the pool is the odd one. My experiment (scratch, reverted): restore `held` to `on(10)`, regenerate the golden, run `test_live_jsparity`: with the PR's `rate{0}` ALL EIGHT `seq_eng_*_held` cases (4 kinds x init/alt) differ, not only the two vox ones; with the pool's initial rate 1: 139 of 139 equal with the original scenario. A bare `rate{1}` breaks `test_live_decisions` (the lane list is compared with the JS lane list, which starts at 0: 35 failures), so the right fix is "before the lane's first event the shell reads 1", not changing the list. Affects any first note of a node that is not at sample 0 (vox: pitch glide start; all kinds: the rate read by blocks before the first note).

## Item 2 (resume exactness)
* The builder's `test_live_idle` passes (160 shell fast-forward cases, 305 pairs) and reproduces. `vfy_idle` (N = 1 .. 1e6 quanta x variants x offsets) was written but NOT RUN. F1 shows the resume side is exact for the vox (0 of 120 vox scripts differ) and that the loss is at the sleep boundary, not the wake.
* What decides "silent": the node's `curLive` false or `done` (gate off and 4096 samples under 1e-5, or 4 s), `ntl == 0`, the core's own idle flag (bass `stage_==0`, acid/mach `stage_==0 && env_==0`, vox `env_==0 && envT_==0`), the rate lane constant from `clock - 2(lat+1)`, and no tap. There is no amplitude threshold in the skip itself, so a long quiet release tail cannot be put to sleep while the core is still producing it; the case that is lost is the final tail (F1).
* Cost: `test_live_idle --bench` (Release, shared 2-core machine): silent vox pad on 33 tracks (165 nodes), 20 s: skip OFF 5277 ms / 5571 ms (0.26x / 0.28x real time, never played / one note per track), skip ON 3 ms / 191 ms (0.00x / 0.01x). The builder's "3x real time before" (task text) was a loaded-machine figure; ratio about 1800x / 29x.

## Coordinator's (c): the skip is OFF while a tap is set
`LivePool::setTap` is used only by `test_live_jsparity` (the 139 JS-parity sequences), so those never run the skip; `test_live_u26` / `decisions` / `reset` / `pool` / `tracklist` / `review` / `idle` / rt_harness / the C API tests run with it on. Skip-on is compared with skip-off only in `test_live_idle` (305 scripted pairs, hand-picked) and with itself across host blocks in `test_live_pool`; nothing compares skip-on with the JS. That is why F1 passed. Cover it by making the tap not disable the skip (the tap can read zeros for a skipped node) and running the JS parity with the skip on, plus a randomised skip-on vs skip-off pairs test like `vfy_pool` in CI.
