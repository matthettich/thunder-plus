# verify-281: independent review of PR #281 "Chains C1: ChainsHost offline" (head e2dcb4c, base `native`)

Reviewer: an independent verifier (did not write the code). Method: reading, plus small numeric checks in node (no C++ was built or run; see "could not verify"). Line numbers are of `e2dcb4c`.

**VERDICT: MERGE AFTER FIXES.** Nothing found that changes the sound of the 22 golden cases or of an ordinary song; the design is sound and the tests are strong where they exist. But there is one real
resource-safety hole (an abandoned or failed plan leaves `ctlNode_` pointing at freed nodes), a fixed event array that a plausible tracker song overflows (stuck BYP switches), the D7 memory ruling not done,
and two page-parity gaps that no golden pins. None is hard to fix. F1 to F3 should be fixed before C2 builds on the plan/commit API; F4 and F5 before the offline renderer is called page-equal.

## Findings

### F1 (should-fix; becomes blocking for C2). `ctlNode_` is left dangling when a plan is abandoned or fails
`chost.cpp:27-47` (plan), `:9-13` (`~ChainsPlan`), `:50-53`.
- Sequence A (bad_alloc): a song with CHN tracks 0..4 heard; `plan()` makes fresh nodes for tracks 0 and 1 (`ctlNode_[0] = n`, `ctlNode_[1] = n`, line 43), then `new ChainsNode` throws `bad_alloc` for track 2: `catch` does `delete n; return nullptr;` (line 41). `unique_ptr pl` deletes the plan, whose destructor deletes `trk_[i].fresh` (tracks 0, 1). `ctlNode_[0]`, `ctlNode_[1]` still hold the freed pointers; the `saved[]` restore (line 50) runs only on the `refused_` path, never on this `return`. The next `plan()` call does `ctlNode_[0]->engine().preparePatch(...)` on freed memory.
- Sequence B (no commit): `p1 = host.plan(...)` (fresh node for track 3), `delete p1` without `commit` (user cancels, a newer edit supersedes it, SongRenderer::setChains on a failed path). Same dangling `ctlNode_[3]`; the destructor comment says it "frees anything it never adopted" but the host's control view is not rolled back. `plan()` + `plan()` + `commit(second)` first: `node_[t]` is null in `commit` line 59 `node_[t]->engine().swapPatch` (null deref); the header says "plans are committed in order" but nothing checks it.
- Sequence C (commit twice): `commit(p)` sets `p->nOldNode_ = 0; p->nOldPatch_ = 0` at line 56. A second `commit(p)` therefore forgets the nodes and patches the first one retired: they are never freed (leak). No double free (fresh/patch are nulled).
- Fix: make `ctlNode_` change only at commit (the plan keeps its own working copy while it plans), or have the plan hold `saved[]` plus a host pointer and restore in the destructor when not committed; restore `saved` on the bad_alloc return too. Guard `commit` with `if (!node_[t]) continue;` in the swap branch and with a `committed_` flag. Add a test: plan, delete, plan again, and a bad_alloc-style refusal with a removal in the same plan.

### F2 (should-fix). 256 pending events is too few for BYP cells; the newest (the "release") events are dropped silently
`chost.h:20` (`kChainsHostEvents = 256`), `chost.cpp:93-96` (`put`: a full array drops the newest).
- Sequence: a song with BYP `0Y` (X = 0 means all 15 switches, `seq.cpp:655`: 15 events per cell, 30 when Y >= 2 because each gets a `-1` restore at `at + Y*line`) on 9 CHN tracks in one row = 270 events. Or BYP 02 on 4 tracks on four consecutive rows (lead is 0.25 s and the restore events sit up to 15 lines ahead): about 480 pending. Events 257 onward are dropped; `-1` restores are the newest, so the switches stay bypassed for the rest of the render. The page has no such limit. The step itself may hold 12288 events (`kSeqStepEvents`).
- The golden and the tests never exceed 6 events, so nothing sees it; `thunder-render --chains` does not report `droppedEvents` (see F6).
- Fix: size the array for the worst case (15 * 32 * 2 per step times the rows in lead, say 4096; `Ev` is 40 bytes), or coalesce per (track, switch, quantum) (the later wins, as the page's setValueAtTime does). `put` is an O(n) insertion: fine at 4096 with stable order, or keep a per-quantum ring.

### F3 (should-fix). D7 (one total memory budget per host) is not done
`chost.cpp:33-37`, `chains.h:53` (`kDefaultMemoryBudget` 1 GiB per patch), `cmem.inc`. The lead's ruling D7 (a) is one total budget per host (1.5 GiB). C1 builds one full patch per heard CHN track, each checked against 1 GiB separately, and `plan()` makes every node's patch (and on a swap a second patch per node) before anything is freed.
- Figures (`cmem.inc`, 48 kHz, margin included): resample 27.7 MB, space 23.4 MB, reverb 1.26 MB, delay 1.66 MB, repeat 1.8 MB, gdelay 2.4 MB; chains.h:53 says convolve 66 MB, pgrain 57 MB. A patch with space + resample + convolve + reverb + delay is about 120 MB; 20 CHN tracks = about 2.4 GB resident; a swap plan (all 20 prepared patches alive beside the old ones) = about 4.8 GB at peak. A light patch (8 modules, about 5 MB) x 20 = 100 MB. Nothing bounds the sum: 20 x 1 GiB is accepted by each check. On the Fold (the stated target of the ruling) this is an out-of-memory kill, not a refused patch; on the desktop `bad_alloc` hits F1.
- Fix: `ChainsHost` sums `chains_module_bytes` over the patch x node count in `plan()` before building anything and refuses the plan (refused path, no-op) over the host budget; a swap plan counts old + new.

### F4 (should-fix; page parity). Offline heard set is `audibleMask()`, the page's is "audible AND has notes", so a note-less CHN track gets a node
`render.cpp:60-67` (`heardMask() = audibleMask()`), page `index.html:25909` (`keepT`: `audible(t) && notes.some(e => e.track === t)`), tool `chains-song-dump.mjs:250-251` (`has` = tracks with an input).
- Construct: track 7 CHN on, no notes in the song, patch `osc -> chainOut(7)` (or `wnoise`, `bytebeat`, `blipdrum`, `clock`->gate: the chains library has generators). The page's offline mix: no node, silence. Native: a tone on the master. Also a tempo-synced LFO-gated generator would run. It also makes the plan differ in memory and CPU (a node per silent track).
- The golden cannot see it: every case's tracks that have CHN on and a Chain Out also have an input, and `test_chains_song.cpp:60` masks the plan check with `heard & (inMask | nodes)`, which would hide a heard-but-input-less track. Add a golden case (CHN track, Chain Out, no input, generator patch) and, here, an assertion on the plain `heard`.
- Fix: give `setChains` (or the heard computation) a `noteTracks` mask from the song (tracks with any note in the played phrases; stems keep the forced mask) and use `audible & (noteTracks | busClosure)` for the plain mix. If the lead decides the page's behaviour is a page bug (live plays them), record that as a ruling and keep native as is, but then pin it in a case.

### F5 (note-to-should-fix). `setChains(true)` failure is silent; no way to read the host's counters through the C API
`render.cpp:62-66`, `render_api.cpp:139`, `render.h` stats. If `plan()` returns null, `chains_` is reset and the render is created dry; a hostile `chainPatch` gives a no-op plan (a host with no nodes). `thunder_render_create` returns success either way. `thunder_render_stats` has no chains counters, so `thunder-render --chains` cannot show `failedBlocks`, `droppedEvents` (F2), `badEvents`, `chcNoNode`, or `refused`.
Fix: `E_MEMORY` when `plan()` is null; surface `refused` as an error or a stat; add `chainsBlocks/Failed/Dropped/Refused` to the stats struct (append, `size`-guarded like the opts) and have thunder-render print them to stderr.

### F6 (note). Tempo: three smaller things
1. (item 6a) A tempo event whose `ceil(t/q)*q` is at or past the render length is, in the page, sent at once (`index.html:23229-23231`, "before quantum 0"): the page's chains then run at that LAST tempo from sample 0 until an earlier event (the initial `{tempo: S.bpm}` message is posted before `pl.play(e)` in `pass()`, so the early-sent one wins). Native never applies it (and the sequencer is not even asked to dispatch events beyond the render end). Real song: a frames-limited preview render (`use_frames` 30 s of a song whose tempo changes at 60 s), or a full render whose final row holds a TPO: the page's tempo-synced LFO / delay in a chain runs at the later tempo for the whole render, native at `S.bpm`. Fix: do NOT replicate it for an unknown-length render. For a known `use_frames` it would need the Seq pre-run for tempo events beyond the end; recommended: declare it a page quirk (it is: a trailing event retunes the whole render), pin it in `C1-NOTES.md` as a known difference and do not chase it. The test at `test_chains_song.cpp:68` applies the page's rule only to compute `eventQuanta`, and `expect` agrees, but native itself has no equivalent: the test passes because the golden's own events lie inside the render.
2. `tpSet_` (`chost.cpp:55`): only the FIRST plan's `song_` transport is ever kept in `tp_`; a later plan's `P.song_` (a different song BPM when C2 re-plans after an edit) is used for `EngineOptions` of a fresh node but then overwritten by `applyTransport(tp_)`, i.e. the first song's tempo. Fix: take `p->song_` at every commit unless a tempo event has already moved `tp_`.
3. No hooked node: events are queued but `tp_` is not updated; with no node (all CHN off, or before the first one in C2) they pile to 256, the newest drop (F2), and a node made later is created with the stale `tp_`; on its first hook the replay ends at the 256th oldest tempo, not the latest. Fix: in `event()` update `tp_` for tempo events immediately (it is the song's transport) and keep only chc in the queue.

### F7 (note). Exceptions: the mix is the same as cengine.cpp, and safe on the CMake targets, but not guarded
`core/CMakeLists.txt:8-13` adds `chost.cpp` to the `-fexceptions` list, so `try/catch (std::bad_alloc)` at `chost.cpp:38-42` compiles on GCC/Clang. The bad_alloc is thrown by `ChainsNode`'s constructor (in `cengine.cpp`, `-fexceptions`) or by `operator new` in `-fno-exceptions` frames (`cmods*.cpp`); as `CMakeLists.txt:36-37` already says, those frames have unwind tables so it propagates (the same assumption as cengine.cpp, not new). `render.cpp`, `render_api.cpp`, `mix.cpp` are in the same list. Not safe: an Emscripten / `-fno-exceptions` build of `chost.cpp` (try/catch is a compile error without `#if defined(__cpp_exceptions)`, which cengine.cpp has at `:200`, `:121`) and wasm `-fno-exceptions` code that throws (aborts). No wasm or Android build script in the repo compiles chost.cpp today (only `core/CMakeLists.txt` and `mutate-u31.sh` name core sources), so: guard with `__cpp_exceptions` as cengine does, and note for the wasm unit that `plan()` must then treat allocation failure as a refusal.

### F8 (note). Tests and claims
- `testSeqEvents` (`test_chains_song.cpp:157-171`) is the only proof of the `dispatch` cases (`SEV_CHC`, `SEV_TEMPO`): it checks `eventsApplied >= 2`, the node's tempo == 90, `eventsIgnored == ign0 - 1`. It never checks which switch moved, its value, nor the quantum, and has no hash. The seven event cases are not run through `SongRenderer` because the renderer cannot inject a made-up time (true), but `host.event(e)` or `r.dispatch` with the golden's SeqEvents could be called on the renderer's host and the hash compared: do that, it proves the two glue lines `render.cpp:35-36` with the golden's own times.
- `runMixer` pre-queues every event before block 0 (`:112`), so no golden case exercises an event arriving while rendering (the live order of dispatch, then hook). The renderer path does (testSeqEvents).
- `runMixer` re-implements `SongRenderer::setStem`'s rule (`:99-103`); only `runRenderer` calls the real `setStem` (fine, the stem cases have no events so all run there).
- `setStem` returning false after `setChains(true)`, and `setChains(false)` after `true` (which restores the plan with `bus_plan`) have no test at all.
