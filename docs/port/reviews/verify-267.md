## Findings

### F1 (FIX BEFORE MERGE): the N1 derivation of `bpmStart` is wrong after a stall skip (`Seq::shift`), where `bpmPrev_` was right
- Evidence: `native/core/src/midi/midisched.cpp:537-539` (the formula `(v - beatV_) * 60 / (t - beatT_)`); `native/core/src/seq/runner.h:53` (`SeqRunner::pump` calls `s->shift(...)` whenever the sequencer is more than `kRunSkipBehind` = 30 ms behind the audio clock, i.e. in live play, between two steps); `native/core/src/seq/seq.cpp:708-713` (`shift` moves `time_`, `base_` and `btT_` by d).
- Mechanism: `Seq::step` counts `bt_ += (t0 - btT_) * bpm_ / 60`, and `shift` moves `btT_` together with the time, so `v` does NOT include the shift. The host's `beatT_` is the previous step's t0 BEFORE the shift, so `dt` includes it. With shift s, a row distance of `dt0` and tempo B the derived value is `B * dt0 / (dt0 + s)` (example: 120 BPM, one row per beat, s = 0.2 s: derived 85.7 BPM). The check `|d - bpmPrev_| <= 1e-9` fails, so `bpmStart = d` is used: a wrong tempo for the interval after the TPO step, and the tempo map's anchors stay bent from there (the N1/B12 class of bug, now in a different, larger form). The PR notes say "those calls are not used while a song plays" (FOLLOWUPS-20NOV-NOTES.md, Decisions): false, `runner.h:53` does exactly that on any 30 ms stall. Only reachable when the step right after the shift has a TPO (or ticks) event, so rare, but the magnitude is 30 to 60 % of the tempo for one interval and it is a regression, not a pre-existing gap.
- Fix: do not derive. Have `Seq::step` put the tempo in force at step start (`bpm_` before `nb` is applied) into `SeqStep` (e.g. `bpm0`) and read that in `onStep`; delete `beatT_` / `beatV_` / `hasBeat_`. If `Seq` must stay untouched, make `SeqRunner::pump` read `s->bpm()` before each `step()` and pass it to `onStep` (the live host owns that call). A guard that only skips the derivation when `s->skips_` changed would also work but is more fragile.
- Test that shows it: in `test_midi_sched.cpp` `tempoOracle`, add a parameter `shiftAt` and call `h.q->shift(0.2)` just before step `shiftAt` (as the runner does), with `shiftAt = 16` (the TPO row) and no `setBpm`. The oracle "tick 24 j at row j's time" for rows after 16 fails on the current head and passes with `bpmPrev_` (and with the fix above). The shift moves all later row times by 0.2 s equally, so the expected grid (`h.grid`) already includes it.

### F5 (NOTE): item 1 (`pump()` end condition) is correct; details checked
- Same clock: `raw` counts every quantum pulled from `SongRenderer::block`, including the latency skip, so after each `pump` `raw == qFrame_`, and the sequencer is stepped against `t0 = qFrame_ / sr_` (`render.cpp:92-95`). `seqTime()` is `Seq::time_`, which starts at 0 (`SeqOpts` has no offset; `render.cpp` never calls `setTime` / `shift` on it) and, once the song is over, is `base_ + rel0` = the start of the last row (`seq.cpp:998`). Same rate (`r->sr` is the `SongRenderer`'s `sr_`). `avail = raw - skip` is the output index; the PDC delay puts audio of clock time x at output index `x*sr - skip`, so `raw >= seqTime*sr` is `avail >= seqTime*sr - skip`, exactly `length_estimate`'s `llround(seqTime*sr) - skip`. Since `raw` is an integer, `raw >= x` gives `raw >= ceil(x) >= llround(x)`: real >= estimate holds to the frame.
- Cannot hang: `seqTime()` is constant once `alive()` is false (the step loop stops), `raw` grows by 128 a pump, `max_frames` (default 1260 s) still cuts, and a song that never ends (loop, `alive()` stays true) is cut by `max_frames` as before. A song that is empty from the start has `time_ = 0`: the condition is true at once, same as before.
- `use_frames` is untouched (the whole block is under `!r->useFrames`). Stems share `pump`: a stem now also waits for the sequencer end; tails still decide (voices() of the stem's heard set).
- Web comparison: the page's offline render (`index.html` ~25921-25925, beta) ends at `ceil((max(seq.time, last note end) + 0.05) * sr)` (`seq.time` stepped without the lead, same start-of-last-row value), plus the 8 s tail rule and a trim with another 0.05 s. Native ends at `max(seq end, voice end)` rounded up to a quantum, with no 0.05 s: it was already shorter before this PR, is still, and is now closer to the web (the early cut of up to 0.25 s is gone). No golden or test fixes an unknown-length length: the length checks in `test_render_api*.cpp` compare against the same render's own output; the only exact-length goldens use `use_frames`. `thunder_render_drain` (`render_api.cpp:374-375`) keeps the old test `songOver() && voices() == 0` without the clock wait; that is right for a "tails" measure and `test_render_api.cpp:50` (`drain == 0` after the end) still holds, but the header could say that drain does not wait for the sequencer clock.
- Header comment (`include/thunder/render.h`): true when the render is not cut. When `max_frames` cuts, the estimate returns `max_frames` and the real length is `max_frames`: true ("unless the render is cut" is the stated exception). The parenthetical "(Before FU1 this comment said ...)" is history inside a public header: move it to the notes (NOTE, cosmetic).

### F7 (NOTE): item 2 checks (everything except F1)
- `SEV_BEAT` is pushed once per `Seq::step`, first, before any other event (`seq.cpp:740`), `v = bt_`, a running beat count since the first step (`bt_ = 0` at the first step, then `bt_ += (t0 - btT_) * bpm_/60` with the tempo in force at step start, `seq.cpp:739`); `t = t0`, the row clock before swing / per-row delay (those move event times, not t0), so swing and delay do not enter the formula. `bt_` is not reset at a song loop / JMP / wrap (only `takeOver` copies it), so `v` stays monotonic across loops. The formula is therefore exact: it returns the `bpm_` the sequencer had when the step began, which is also what N1 needs.
- First step after `start`: `hasBeat_` false, falls back to `bpmPrev_` (-1 -> `S_->bpm`), as before. Two TPO rows in a row: the second step's derived tempo equals `bpmPrev_` (the tempo applied by the first), kept bit for bit. A TEMPO event without a BEAT event (event cap 0): falls back to `bpmPrev_`, as before. A TEMPO event emitted for a ticks-only change: `d == bpmPrev_`, kept. Two steps at the same t0: `dt <= 1e-9` gives `d = 0`, rejected, fallback. A fresh `Seq` while `hasBeat_` is still true (no `start()`): `v` lower than `beatV_` gives `d <= 0`, rejected, fallback. `setTime` after the first step moves `time_` only, not t0: no effect.
- `hasBeat_` is reset exactly where `bpmPrev_` is: only in `start()` (`midisched.cpp:563`); `stop`, panic and release reset neither (same as before; the next `start()` resets both). Consistent.
- Rounding: for a very long song (t ~ 1e5 s) with tiny row distances the relative error of `db*60/dt` can exceed the 1e-9 window, so `bpmStart` can differ from `bpmPrev_` by ~1e-9 relative: harmless, but the "bit for bit" claim in the comment is only exact for normal songs.
- The N1 tests themselves can fail: `tempoOracle` checks 24-tick-per-row timing to 1 frame against the sequencer's own grid; with `liveAt` the `setBpm` lands before the TPO step (live tempo 163.3 / 148.9 differ from `bpmPrev_`), so the old code takes `bpmPrev_` and is off by 8-16 ms, as the notes say (not re-run here). Note the live tests never call `Seq::shift`, which is why F1 is not caught.

### F8 (NOTE): item 3, the "swap take and capPoly" claim is right
- `VoicePool::take` / `SfPool::take` (`voice.cpp:132-139`, `sf_live.cpp:81-87`) for a poly note do two things only: drop dead voices of this track (what `liveOnTrack` inside `capPoly` also does, idempotent) and kill choke-group voices of OTHER tracks (`k != e.track`; the cap counts only `e.track`). For a mono note `capPoly` returns before counting (`if (!e.poly ...) return`, after the serial stamp, which is order-independent). The two operations touch disjoint voice sets, and voices are reclaimed by a scan of `alive_` in render (`aliveErase`, `voice.cpp:84`), not in kill order, so even the free-list order (hence the summation order) does not depend on the call order. The claim is right at the voice-list level and, by that argument, at sample level, though the test only observes voice lists and counters (it does not compare rendered samples).
- Otherwise `test_players` is able to fail: the cap checks use 4 s pads and ask at t = 2 s, so a voice not released is still live and counts; P3 (a refused 1-sample pad touches nothing) fails if `capPoly` is made unconditional (releases a voice, 4 -> 3); the SF-first case fails if age were per pool. Cost: each `Rig` loads and decodes `sounds/FluidR3Mono_GM.sf3` (about 20 rigs in one process): possibly slow under the sanitizer job (check its time when CI ends; FOLLOW-UP if it is over a minute).
- `test_render_stems.cpp` S8 / S9 / S10 and `test_midi_api.cpp` T2 / T3 are not vacuous (S8 compares bit for bit with a muted-song render; S9 requires the stem to differ from the no-choke stem; T2 needs 0 released at block 0 and 1 at block 0.08). Cosmetic: S9 leaves a debug `printf` ("S9 diag"), and the S8 / S9 / S10 tags `FU2 / FU3 / FU1` do not match the notes' item numbers (notes: items 2 and 3).
- `test_render_stems_bus.cpp` (FU3): the single-pass mutant fails case 1 (0 -> 5 -> 2 gives the list {6} (bus 5) instead of {3} (bus 2)); case 3 (muted middle bus) pins the "add only when audible" rule. Valid.
