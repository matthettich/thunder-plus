Source: `n1/n2-h2` @ 1310bdd3 (the four PRs read as one diff against `native`). PARTIAL REPORT (written while the host builds and sanitizer runs were still in progress; see the end for what is still open).

## Findings (by severity; file:line are on n1/n2-h2 @ 1310bdd3)

### F1 (HIGH, #312) JNI entry points read and reset `g.eng` without `g_life`: use-after-free / null deref against shutdown, engine.reset, reopen failure
`live_jni.cpp` `ready()` (l.340) and every unlocked entry (nativePlay l.274, TransportStop l.286, Bpm, Loop, MixSet, SetDuck l.224, Status l.304 when the try_lock fails, Stats l.319, DrainEvents l.~509, PlayEx, Hold, Lead, Perf, MetersWant, FxPlan/Commit/Param, MasterConfig, ChainEdit, PdcSet, PadChop, PadsPublish, VarSet, EngineOffset) test `g.deviceInit && g.eng` and then dereference `g.eng->` with no lock, while `teardownLocked()` (l.162-178, under g_life) does `g.deviceInit=false ... g.eng.reset()`. `g.eng` is a plain `std::shared_ptr` written by one thread and read by others: a data race by definition, and the window is a real crash: thread A passes `ready()`, thread B resets `g.eng` (destroying the LiveEngine, which `destroy()`s the live host), thread A calls `->call()` on a null / freed object.
Who is the other thread: LiveBridge's 20 ms pump (`LiveBridge.startPump`, timers thread) calls `nativeDrainEvents` all the time and is NOT stopped before `LiveEngine.shutdown()` (LiveBridge.reset() cancels it with `cancel(false)` but the running tick can still be inside the JNI call); `LiveSession.tick` (main thread, nativeStreamState l.216 reads `g.eng->audioCalls()`, `g.device`); MediaSession / notification callbacks; `ThunderService.onDestroy` -> `LiveEngine.shutdown()` on the main thread; `engineReset` runs on the bridge worker but the pump and the ticker run beside it.
Fix: take a `std::shared_ptr<LiveEngine>` copy under a small mutex (or `std::atomic_load`) in one helper `eng()` and use the copy for the whole call; `teardownLocked` resets under the same mutex. nativeStreamState / nativeStatus must copy `g.device` fields the same way (they read `g.device` while reopen re-inits it in place; `g_reopening` is a check-then-act, not a lock).

### F2 (HIGH for the gate, #315) the A5 gate on the live callback never receives the xrun count, so "0 underruns" is vacuous and the gate can PASS with xruns
`live_jni.cpp` creates `g_lrt` (l.58) and calls only `rtlog_begin/end/reset/read` on it (l.71, 76, 149, 324, 327). `rtlog_host_underruns(&g_lrt, ...)` is never called (N0's `jni.cpp:128` does call it with `under - g.xrunBase`). `nativeStatus` reads AAudio's xrun count (l.310) but only hands it to `setHostStats`. So `rtlog_snapshot.underruns` is always 0 and `pass` (rtlog.h: ratio, underruns == 0, late == 0) cannot fail on an xrun; only `late` (callback longer than its period) and the ratio can. WORKPLAN H1's gate says "0 underruns". Fix: in nativeStatus (or a poll in nativeRtSnapshot) call `rtlog_host_underruns(&g_lrt, x - xrunBase)` with a base taken at `nativeRtReset`.
Also `Aborted` cannot be overwritten to PASS except by the race in F7a.

### F3 (MEDIUM, #312) the poller stores the STATE record's `state` (THUNDER_LIVE_ST_*: 1 playing, 2 stopped, 3 ended) and the rest of the shell reads it as THUNDER_LIVE_STATE_* (0 idle, 1 playing, 2 ended, 3 held)
`live_engine.cpp:162` `st_.state = s.state` (a `thunder_live_ev_state`, live.h:596-602 ST_*), emitted by `statusJson` (l.188) and parsed by `LiveModel.kt` `LiveState.of` (IDLE 0, PLAYING 1, ENDED 2, HELD 3). Consequences: a user Stop (ST_STOPPED=2) shows as "song ended"; a natural end (ST_ENDED=3) shows as HELD, which `LiveButtons.canPlay`, `LiveSession.onFocusChange/tick` (`playing = PLAYING || HELD`) and `notificationText` treat as PLAYING until the STOPPED record arrives ~0.3 s later (live.h:597). The `stateHook` in `live_jni.cpp:138` compares with `THUNDER_LIVE_STATE_ENDED` (2), i.e. it fires on ST_STOPPED, not on ST_ENDED (3): the MIDI clock box goes quiet only by that accident, 0.3 s after the end. The host test checks `"state":1` only (test_android_live_engine.cpp:166), which is the one value the two enums share. Fix: map ST_* to the STATE_* values in the poller (1 -> 1, 2 -> 0, 3 -> 2), or have the poller call stats_get for `state`.

### F4 (MEDIUM, #315) focus decisions are made on the main thread from `armed` / `ducked`, which are set later on the exec thread: a quick DUCK then GAIN, or a transient loss then GAIN, can leave the output ducked or the transport armed forever
`LiveSession.kt` `onFocusChange` computes `act = FocusPolicy.decide(change, playing, armed, ducked)` on the main handler, then `exec.execute { ... ducked = true / armed = true ...}`. `exec` is the single worker that also runs `reopenStream` (hundreds of ms) and `gateTick`; a second focus callback that arrives before the first body ran sees the old `armed` / `ducked`: `GAIN` with `armed == false` -> NONE, so after the delayed body the song stays stopped and `armed` stays true (focus never abandoned: tick only abandons when `!armed`), or the gain stays at 0.25. Fix: set `armed` / `ducked` on the main thread in `onFocusChange` before posting, or run `decide` inside the exec body.
Also: RESUME replays with `nativePlay(row)` (mode song, no loop / sect / phrase / only / seed of the page's own play) and sends the page no `device` event for the resume, so the page's transport stays "stopped" while the shell plays; the `device` event of the stop carried `resume:true` but nothing says "playing again" (page-client: check what it does with `resume`).

### F5 (MEDIUM, #313) `PutStore`: a missing chunk is not detected (`last` completes the buffer, zeros are played), a header with a repeated pid but another id reuses the first id, an abandoned pid is never released
`BridgeTranslator.kt` PutStore.chunk: there is no received-bytes accounting per channel; `last` alone finishes the buffer, so a lost / dropped chunk, or a stereo put whose R chunks did not arrive, becomes silence with `put.done ok:true`. `parts[pid]` is created from the first header; a later header of the same pid ignores its `id`, `sr`, `ch`, `n`. An unfinished pid (page timeout, error) stays in `parts` with its bytes counted in `held` until `clear()` (engine.reset / shutdown), so repeated failures exhaust the 256 MB cap ("too much audio held"). `header()` while `cur != null` returns an error but leaves the OLD header, so the next ArrayBuffer is assigned to the stale header. Fix: count bytes per channel, answer `put.done ok:false` when `last` arrives with a gap; drop `parts[pid]` on any error; replace `cur` on a second header.

### F6 (MEDIUM, #313) SongFit answers `ok:true` for songs the core cannot play (false negatives)
`songfit.cpp` checks: too-big, no-effects, unreadable, no-chains, sidechain (scin/scout), stretch (sync 2/3, sx), font (engine sf), no-lxr, engine (not renderable), pad-effect. It does NOT check what N2-PLAN.md:40 and :80 list as fallback conditions: `lxp` use, a Resample take, a pump module in a live chain, MIDI clock follow (`midi.cfg.clockIn` is "read and ignored", BridgeTranslator.kt:140 / N2-NOTES:83: nothing implements the fallback). songfit.h says so ("WHAT IT DOES NOT CHECK"), but G11 in CORE-BRIDGE section 7 says "a song using [lxp] falls back" and nothing makes it. Also the verdict in the `song.load` reply is computed with the kit text of an EARLIER kit.load (`g.kitText`, live_jni.cpp:386) or with no kit at all (voices unchecked, `kitJson.empty()`), and the page sends kit.load after song.load: the reply `ok:true` can precede a `fit ok:false` event that the page may no longer be waiting for (the ask resolved). Fix: have the page re-ask, or make the ask wait for the kit (song.load carries the kit), and add the missing checks.

### F7 (LOW-MEDIUM, #315)
a. `LiveEngine.gateTick` writes `gate = Finished(...)` after reading `rt` with no check that the gate is still `Running`; a `gateAbort` from another thread in between is overwritten and an aborted run can end as PASS. Use a compare-and-set on the state.
b. The watchdog (`LiveSession.tick`) rebuilds the stream when `calls` has not changed for 1000 ms from the moment `LiveEngine.active` is true: a stream that is slow to deliver its first callback (> 1 s after `nativeStart`), or a legitimately paused one, is torn down and reopened; the page gets `device reason:'stream'`.
c. A stale `hasFocus == true` after an unplayed `AUDIOFOCUS_LOSS` (decide returns NONE when not playing/armed) makes the next `beforePlay` skip the request (`if (hasFocus) return true`) until the 3 s idle abandon in `tick`.

### F8 (LOW-MEDIUM, #316) MIDI-in parser: a truncated message followed by F7 / F0 turns the next data bytes into a phantom message
`midi_in.cpp:27-33`: a status byte >= 0x80 sets `inSysex_ / skipping_ / have_` but does not clear `need_`; for F0 and F7 (and F1/F3..F6) `status_ = 0` yet `need_`/`cur_` keep the open message, so `96 F7 3D 07` emits note-on `96 3D 07` (and `A7 36 F7 5A 3C` emits `A7 5A 3C`). Fuzz: `/tmp/fz/fz.cpp` (2,000,000 random streams in random split sizes, ASan+UBSan, against a spec reference): 15,546 mismatches, ALL of this kind; with `need_ = 0;` added in the same line (`inSysex_ = false; skipping_ = false; have_ = 0; need_ = 0;`) 0 mismatches. Running status, interleaved realtime (F8/FA/FB/FC pass at once, FE/FF dropped), truncation by a new status, and a 1 MiB SysEx are otherwise correct and ASan/UBSan clean. A phantom note-on / note-off can hang a note in the page.

### F9 (LOW, #313) `nativePadTake`: `b` leaks when the control task is abandoned before it starts
`live_jni.cpp` nativePadTake: on `rc == -1000` the comment says the task "owns b"; when the wait timed out and the task is dropped (`abandoned` before start, or `stopThreads` drained the queue) nobody frees `b`. `nativePlay` captures `[&]` (`row`, `seed`) into a task that can outlive the call (call() returns -1000 at timeout +500 ms while the task may be running): use-after-return in the narrow case where one fn runs > 500 ms past its deadline. Capture by value.

### F10 (MEDIUM, #312) `LiveEngine`'s any-thread getters read `L_` with no guard against `destroy()`: SEGV under TSan in the adversarial test
`live_engine.h:69` `engineOffset()` and `live_engine.cpp:196` `statsJson()` (also `nativeEngineOffset`, `nativeStats` over them) read the plain `thunder_live* L_` while `destroy()` (l.66) writes `L_ = nullptr` and frees the host on another thread. Adversarial test (/tmp/adv/adv.cpp, 4 hammer threads + render thread + 13 reset / reopen cycles) died on the FIRST reset with `SEGV in thunder_live_engine_offset` / `LiveHost::statsGet` (TSan run 1 and the suppressed re-run), reproducible. Same family as F1 (the JNI threads are Kotlin's: the pump, the 500 ms ticker, the notification). With the getters gated by a reader lock (the shell's `g_life` does not cover them) the same test was clean (below).

### F11 (LOW-MEDIUM, #316) the MIDI control runner falls back to running the function on the caller's thread after a 2 s timeout, beside the control thread
`midi_out.cpp` `viaControl`: `rc == -1000 ? fn() : rc`. `-1000` is also what `LiveEngine::call` returns on a timeout (1500 ms + 500 ms), e.g. while the control thread is inside a long `song_publish` (parse of a big song on a phone) or a `kit.load` publish; then `thunder_midiout_set_*` / `thunder_midi_set_*` run on the JNI thread beside a `thunder_live_*` control call, which is exactly what the runner exists to prevent (live.h: ONE control thread). The abandoned task is skipped if it has not started, but if it has, fn runs twice (once on each thread). Fix: distinguish "no control thread" (`run_ == false`) from "timed out"; on a timeout return an error.

### F12 (LOW, #312/#316) shutdown stalls: a poller blocked in the state hook, and a stale task
`pollLoop` calls `stateHook_` -> `host().setPlaying(false)` -> `viaControl` -> `LiveEngine::call` (live_jni.cpp:138). `stopThreads()` joins the control thread first, then the poller: if the hook's task was queued after the control loop's last pass, nobody completes it and `call` waits its full `timeoutMs + 500` (2 s) before `-1000`; `teardownLocked` (g_life held, main thread via ThunderService.onDestroy) is blocked meanwhile. Also `call()` can push a task AFTER `stopThreads` drained `q_` (run_ was true when checked): it sits in the queue for good (leak of its captures, and the caller waits the timeout). Not a crash; a stall.

### F13 (LOW, #313) hello `caps.engines` is a hard-coded list
`LiveBridge.kt` ENGINES contains `lxdrum lxsnare lxcym lxhat` even when the app is built with `-PthunderWithLxr=false`; the page shows those engines as "rendered" while the core renders nothing (SongFit does say `no-lxr`, so no song plays wrong, but the caps lie). Build the list from the host (or drop the lx names when `thunder_lxr_api()` is null; `nativeCaps` has no bit for it).

### F14 (LOW, #313) `padFxApplies` is not the page's `engFx`
`pad_filler.cpp:96` is a hard-coded `!(bass, vox, acid, mach, wavesl)`. The page rule (index.html:4967) is `isBlipV || (isXEngV && !XENG[engine].live)`. The …pump synths' LIVE twins (`pump/synth/pump-synth-engine.js:233`, `live:!!LIVE[k]`) are `live:true` too and are dry on the page, but the shell would count a pad effect on them as a `pad-effect` reason (they already fail `engine` today, so no wrong verdict yet; after U33 it is a false positive). Read the flag from the page's data instead of a list.

### F15 (LOW, #312) event shapes differ from CORE-BRIDGE section 4
`pos` carries `cr` and no `pat` (spec: `{f,row,pat,step}`); `meters` is `{seq, at, a:[...]}` not `{f, tr, m, fx}`; a `state` record of the ENDED / STOPPED kind maps through ST_* only (no `held`); `clock` adds `voices`, `dropped` (additive, fine). If N2-PAGE-CLIENT.md specifies these shapes the doc and CORE-BRIDGE should say so; I did not find the section 4 shapes anywhere in the shell.

### F16 (LOW-MEDIUM, #313/#315) while the live engine is down (engine.reset, a failed stream reopen) a page `play` / `open` goes to the N0 test core
`Bridge.kt:86`: `if (LiveBridge.liveMode)` is `flag && LiveEngine.active`; `LiveEngine.shutdown()` clears both (LiveBridge.reset(), active=false) for the ~1 s of an engine.reset and for good after a failed reopen (`reopenStream` -> `shutdown()`). Messages that arrive then fall through to `ThunderHost.command` (ThunderHost.kt:122): `open` / `play` call `ensureRunning`, i.e. the N0 test core opens the output. After a failed reopen the page is told `engine up:false` but a press of Play still starts the N0 test core; during a reset the N0 core can start after `LiveEngine.start` has run `ThunderHost.shutdown()`, giving two engines on the output. Fix: keep a `liveSession` flag that survives reset, and answer `err` instead of routing to N0 until the page says `hello` without `live`.

### F17 (LOW, #313) the ask id and the rev of a song.load are read by regex from the last 200 characters of the message
`LiveBridge.kt` `idOf` / `revOf`: `Regex("\"id\"...").findAll(raw.takeLast(200)).lastOrNull()`. On a `send` (no id) whose tail contains an `"id":N` of the song or vars, a `reply` with that id is emitted and can resolve an unrelated pending ask (thunder_bridge.js `pending[m.id]`); `rev` missing gives 0 while the core was given `++g.rev`. Fix: take them from the top level the way `extractMember` does in C++.

## Audio thread (check 1), line by line
`live_engine.cpp` render (l.74-103): `setFlushToZero`, two relaxed stores, `thunder_live_process`, an interleave loop, the duck ramp, one `fetch_add`. No allocation, lock, JNI, log or blocking; `l_`/`r_` are sized at create and `destroy()` clears them only after the stream stopped (the order in teardownLocked guarantees it; but see F1/F10 for the callers that are not ordered). `dataCallback` (live_jni.cpp:67-80): `monoNs`, `rtlog_begin/end` (atomics only), `hostFrameNow` (audio thread's own field), `audioBlockLive` -> `publishMap` -> `thunder_midiout_clock_map` (wait-free: a test-and-set flag and relaxed/release atomics, midiport.cpp:330-346; `AAudioStream_getTimestamp` through a dlsym pointer at most every 20 ms) -> no lock, no allocation, no JNI, no log. The duck gain: `duckTarget_` relaxed load, `duckCur_` private to the audio thread, correct ramp, applied after the core's limiter (as documented). NaN passed to `setDuck` would be stored (the clamp's comparisons are false for NaN) but cannot spread: a NaN target makes neither branch of the ramp fire. The load figure: `g_load` single atomic double, peak-hold with decay: fine. Shared fields: `calls_` (release/acquire, control side waits on it), `cbFrame_/cbNs_` (two relaxed stores, read by the MIDI-in thread as an independent pair: the pair can tear by one callback, harmless), `duckTarget_`, `outLat_/under_` (relaxed). `lv->midiOn` is a plain bool read by the callback and written by the control thread before `ma_device_start` and after `ma_device_uninit`: ordered by the stream start / stop, fine. `liveTsRead` reads `g.device.aaudio.pStreamPlayback` on the audio thread; `nativeReopenStream` re-inits `g.device` in place only after `ma_device_uninit` stopped the callback: fine.

## MIDI order (check 6)
nativeStart: `thunder_live_create` -> `thunder_live_midi` -> `engineStartExternal` (`thunder_midiout_create`, devices, ports, clock / gear, on the starting thread = the control thread, before `startThreads`) -> `startThreads` -> `setControlRunner` -> `ma_device_start`; the poller's first `host_stats` precedes the first callback. Per callback `process` then `audioBlockLive` with engine frame = host frame at block start - `engineOffset()` (read after process); `thunder_midiout_pump` is called only in `senderMain` (midi_out.cpp:433, 446; the second is the shutdown flush on the same thread). Shutdown: stop, two callbacks, `ma_device_uninit`, `stopThreads`, `engineStop` (sender delivers Stop, `thunder_midiout_free`), `destroy`: the U37-P5 order. Reopen: `remap()` makes the next callback publish the map again; the pair algebra in `publishMap` reduces to `pos - written + coreFrame`, independent of the host frame count, so a new stream's restarted AAudio counter does not matter.

## What I could not check
- Anything that needs a device: AAudio callbacks, `AAudioStream_getTimestamp` semantics (the `written - hostFrame` offset comment says UNVERIFIED), AMidi partial writes, the real WebView message path, focus / noisy / device callbacks, the notification and MediaSession, foreground-service start rules, ANR risk of `onDestroy -> shutdown` on the main thread (teardown can take ~1 s: stop 500 ms + callbacks 500 ms + MIDI Stop up to ~0.5 s).
- Kotlin at runtime (read only; CI's APK job compiled it, and the JVM tests were not run here). The Kotlin-side claims in F4, F5, F7, F16, F17 are from reading.
- The TSan / ASan runs instrument the shell, not the core (see the results table); `live_jni.cpp` itself is not built on the host (it includes `android/log.h` and miniaudio's AAudio), so F1 is from reading the code, not from a run; F10 is the same defect one layer down, reproduced.
- The Android CMake configure with `-DTHUNDER_WITH_LXR=OFF` was not run (needs the NDK): the Gradle switch is read, not executed.
- `docs/port/N2-NOTES.md` / `N2-PLAN.md` claims were not taken on trust; those I did not re-check: the notes' list of owner decisions (D-numbers), and the page client's handling of `device` / `fit` events (N2-PAGE-CLIENT.md was not read in full).
- Not run: the 10-minute A5 gate itself (device only).
