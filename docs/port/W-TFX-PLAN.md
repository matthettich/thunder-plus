# W-TFX: tfx track effects (and the rest of dsp/) on Windows. PLAN ONLY (Sonnet planner, 26 Nov 2026)

Branch `plan/w-tfx` from `origin/native` (4b646448). Nothing in `native/`, `dsp/` or `.github/` is changed by this file. Fable judges the approach before a builder starts.

## 1. Why MSVC has no effects library today

Three CMake gates, all of the same kind ("MSVC cannot compile the upstreams"), and nothing else:

1. `native/core/dsp/CMakeLists.txt` lines 7-10, the gate that matters:
   ```
   if(MSVC)
     message(STATUS "thunder_dsp: skipped on MSVC (the upstream sources need clang or gcc)")
     return()
   endif()
   ```
   So `thunder_dsp_tfx`, `thunder_dsp_mods`, `thunder_dsp_pe` and `thunder_dsp_w` are never made.
2. `native/core/CMakeLists.txt` 47-56: `THUNDER_HAVE_TFX=1` (and `THUNDER_ENGINE_PE`, `THUNDER_MODFX_MODS`) are set only `if(TARGET thunder_dsp_tfx)` (resp. `_pe`, `_mods`), so on MSVC the macro is unset and every `#ifdef THUNDER_HAVE_TFX` block (fxhost.cpp, fxsong.cpp, padfx.cpp, wmods.cpp, live_api.cpp: `THUNDER_LIVE_CAP_EFFECTS` off) compiles out. A tfx-class slot then hosts nothing (PFX-NOTES: pad effect parses as `Kind::Other`; track fx_plan hosts no slot).
3. Same pattern for pump: `native/core/pump/CMakeLists.txt` lines 10-13 `if(MSVC) ... return()` ("pump's wasm build needs clang or gcc"), and `native/CMakeLists.txt:37` `if(THUNDER_WITH_LXR AND NOT MSVC)`. **Adjacent gap, not this unit:** a Windows app also has no pump (MASTER, pump slots, pump synths: `THUNDER_HAVE_PUMP` unset). Whatever W-TFX chooses should be chosen so pump can follow with one more `return()` removed (see 3, "pump next").

The CI job is `.github/workflows/native.yml` `windows` (line 156: `cmake -S native -B build -A x64`, VS generator, cl.exe, Release, ctest) and `native-desktop.yml` `windows` (builds the core the same way, plus the WebView2 shell).

A real `--target=x86_64-pc-windows-msvc` syntax check is NOT possible here: the machine has clang 18 but no MSVC/UCRT headers (`<cmath>` not found), and I did not install anything. So the list below is "what a pedantic clang flags + what I read", not a cl.exe transcript. cl.exe would have to confirm it; that is itself an argument for not choosing a plan that depends on cl accepting the upstreams (see 2b).

## 2. Options

### (a) Build dsp/ with clang-cl in a separate step, link into the cl-built core
Mechanically: the Visual Studio generator picks ONE toolset per solution (`-T`), so per-target compiler = a second CMake tree (Ninja + `clang-cl`, via `ExternalProject_Add` or a CI step run before the main configure) producing `thunder_dsp_{tfx,mods,pe}.lib`, imported with `add_library(... STATIC IMPORTED)`.
- ABI: clang-cl targets the MSVC ABI (same name mangling, vtables, `/EHsc` unwinding, UCRT, MSVC STL headers), so `Fx*` with virtuals, `std::bad_alloc` thrown out of `thunder_fx_malloc` and `std::string` across the boundary work. Must match `/MD` (CMake default `MultiThreadedDLL`), the same VS STL version, and `_ITERATOR_DEBUG_LEVEL` (Release only in CI: fine; a Debug core would need Debug dsp libs).
- LTO: neither side uses `/GL`; keep it that way (clang-cl LTO objects are not linkable by link.exe).
- Costs: two toolchains to set up on every dev machine (the owner builds on a Windows PC), two configure trees, config mapping (Debug/Release/RelWithDebInfo) by hand, a clang-cl version/VS-STL compatibility matrix, CI time = dsp build serial before the core.
- Keeps cl.exe as the compiler of the core + shell (smallest change to the 100+ already-green Windows tests and the WebView2 shell).
- Verdict: works, but it is the most plumbing and the least reproducible for the owner. Keep as the FALLBACK if the desktop shell cannot be compiled by clang-cl (see 3, step 7).

### (b) Patch the sources so cl.exe compiles them
Needs: B1 (3 upstream files rewritten with fixed buffers: Beads' `size` bound must be proven, e.g. host block 128 and `size / ratio`), B2 (replace the packed bit-field pair with explicit 3-byte pack/unpack that reproduces GCC layout, in two structs plus the code reading them), B3 (a force-included `#define __attribute__(x)`), B4 (a macro or `#ifdef __wasm__` in `dsp/tfx/tfx.cc` and the exports, i.e. editing the web's sources, or force-including a shim), B5 (4 tables), B6/B7 (force-included shim), plus every cl-specific error I cannot see from here. Roughly 12 upstream patches + 3 web-source touches + 2 shim headers, each a new `prepare.sh` heredoc against pinned commits (the pin file lists 8 patches today; this would more than double it and break "the same sources as dsp/build.sh").
- The decisive problem is B9, not the typing: the whole port's guarantee is "the same samples as tfx.wasm built by clang" (test_fx gate -80 dB vs the wasm; two cases already needed a documented individual gate). cl.exe changes unspecified-order evaluation, constant folding of libm, and contraction rules relative to clang; the U14 notes record GCC alone cost three open cases. We would be re-doing that investigation on the compiler we know least and cannot run here.
- Verdict: reject unless clang-cl turns out impossible.

### (c) Build the whole Windows native with clang-cl (`cmake -T ClangCL`)
Same one configure, one toolchain, MSVC ABI and UCRT, `if(MSVC)` is still true in CMake (frontend variant MSVC), so every existing `/W4 /GR- /fp:precise` line keeps working and the gates need only a "is it clang?" test. The upstreams then compile with the SAME compiler front end as Mac, Linux-clang and the wasm reference, so B1, B3, B4, B5 (clang accepts them as extensions), B9 vanish, and B2 reduces to a layout check (clang-cl honours `__attribute__((packed))` but uses MS bit-field layout rules; Step 4's `static_assert` decides). What remains: B6 (`_USE_MATH_DEFINES`), B7 (shim), B8 (flag translation), B10.
- Risks: (1) the H6 desktop shell (WebView2, C++/WinRT-style headers, WIL) and miniaudio (H7) must compile under clang-cl: unknown until tried; (2) we lose cl.exe coverage unless we keep a job for it; (3) runner needs the VS "C++ Clang tools" component or LLVM (`windows-latest` ships both, verify with `clang-cl --version` in the first step); (4) core files behind `THUNDER_HAVE_TFX` compile for the first time on Windows (clang-cl: low risk, they are clean under clang).
- CI time: a full -O3 build of the 145 upstream TUs plus the 4 libraries: my estimate (not measured) is +10 to 20 minutes on a 4-vCPU runner (the Mac job's two-arch build took 41 minutes on 3 cores, so give the job 90 minutes).

### (d) Others considered
- Ship the Windows app on the Linux/GCC toolchain through MinGW-w64 (`gcc`/`clang` + mingw UCRT): no MSVC ABI, breaks the WebView2 shell and the existing MSVC test coverage: no.
- Keep MSVC without effects and have the web page's tfx.wasm run in the WebView on Windows: that is the pre-native behaviour, defeats the native audio thread: no.
- WASM-in-native (wasmtime) for tfx: adds a runtime and a 10x slower inner loop: no.

## 3. Recommendation and build plan

**Recommend (c), staged: add a clang-cl core job, make it green with full DSP, then move the desktop Windows build to it. Keep the existing cl.exe job as it is** (it still proves the portable core compiles with cl; its tests keep skipping the FX parts exactly as today, which is the honest statement of what cl builds have). Fallback (a) only if step 7 fails. Pump is the next unit with the same switch (below).

Why: one compiler for all platforms' upstream DSP (B9 is the only risk class that hurts silently), no second toolchain, three-line-class changes in CMake, no patch of pinned upstreams, no edit of the web's sources.

### Steps for the Sonnet builder (branch `n4/w-tfx` from `native`; small commits; never touch `dsp/` or `prepare.sh` unless a step says so)

1. **Probe first (no code):** in a scratch workflow run on `windows-latest` print `clang-cl --version`, `cmake --version`, `where sh sed python3 git`, and run `sh native/core/third_party/prepare.sh` after `fetch.sh` into temp folders. Record the result in `docs/port/W-TFX-NOTES.md`. If `prepare.sh` fails on path conversion (B10), fix it with `cygpath -m` guarded by `command -v cygpath` (no change on other OSes).
2. **CMake gate** (`native/core/dsp/CMakeLists.txt`): replace the `if(MSVC) return()` by
   `if(MSVC AND NOT CMAKE_CXX_COMPILER_ID STREQUAL "Clang")` ... message "thunder_dsp: skipped on cl.exe (configure with -T ClangCL)" ... `return()`. cl.exe builds are unchanged byte for byte.
3. **Flag translation** for `CMAKE_CXX_COMPILER_FRONTEND_VARIANT STREQUAL "MSVC"` (clang-cl) in the same file. Do not pass GNU flags bare: use `/clang:` or the native spelling.
   - `-O3` -> `/clang:-O3`; `-ffast-math` (wasm/web-parity `OPT_FX`, `OPT_MOD` only where the existing code uses it) -> `/clang:-ffast-math`; strict groups: `/clang:-fno-fast-math /clang:-ffp-contract=off`; `-w` -> `/w`; `-fno-rtti` -> `/GR-`; `-ffunction-sections` -> `/Gy`; `-fno-lifetime-dse` stays GCC-only (clang keeps the zero-fill, `test_fxzero` proves it).
   - **Exceptions: do not pass `-fno-exceptions` to any group** (clang-cl default `/EHsc`, the same as the core's MSVC build, which has no `-fno-exceptions`); `thunder_fx_malloc` throws `std::bad_alloc` through the effects' constructors on host builds (U34a), and tfx needs unwinding. This also removes FX1's Darwin-style "no unwind tables" worry on Windows x64 (tables always emitted).
   - `SHELL:-include X` -> `SHELL:/FI X` (keep the order: `cstdio`/`stdlib.h` first, then `fx_alloc.h`, `wasi_rand.h`, `host_std_shim.h`).
   - `-std=c++14` stays (`CMAKE_CXX_STANDARD 14`, extensions OFF -> `/std:c++14`). Add `_USE_MATH_DEFINES` (B6) to every dsp group (and to `-DTEST` groups).
   - Keep `set(CMAKE_CXX_FLAGS_<cfg> "")` (directory scope, same as other platforms: it drops `/DNDEBUG` as intended, so upstream `assert`s behave as on Linux). CRT stays `MultiThreadedDLL` (CMake default; do not set `CMAKE_MSVC_RUNTIME_LIBRARY` here: must equal the core's).
   - **No `/arch:AVX*`, no `/fp:fast`, no `/GL`** anywhere in dsp (see 5).
4. **CloudSeed `strcpy_s` (B7):** drop `CS_OPTS` on the clang-cl frontend and instead put, in `native/core/dsp/host_std_shim.h` (already force-included for host builds of that group): `#include <string.h>` then `#define strcpy_s(a,b,c) strncpy(a,c,b)` (after the header, so the UCRT declaration is untouched; same truncating semantics as the wasm/Linux build). Include the shim for the cloudseed group on clang-cl too (`CS_PRE` is currently `host_std_shim.h` for all host builds: already true).
5. **Layout/regression guards that cl-vs-clang-cl cannot hide:** add one tiny test `native/tests/test_dsp_layout.cpp` (built when `thunder_dsp_tfx` exists) with `static_assert(sizeof(beads::Item<beads::RESOLUTION_12_BIT, 2>) == 3)` (B2) and a runtime check that Beads in 12-bit mode renders (`test_fx` already covers `e_beads_*`). If clang-cl gives 4, **stop and report** (decision for Fable: replace the two structs with explicit 3-byte pack/unpack through a `prepare.sh` patch, host builds only, `#ifndef __wasm__`, as the other host-only patches do); do not guess.
6. **Core:** nothing to change in the `THUNDER_HAVE_TFX` source files unless clang-cl rejects something (then fix in the core, in portable C++). `native/core/CMakeLists.txt`: the `/fp:precise` block gets `/clang:-ffp-contract=off` added for the clang-cl frontend (clang-cl's `/fp:precise` defaults to `-ffp-contract=on`; the goldens need off; without AVX2/FMA ISA on plain x64 nothing could fuse anyway, so this is belt and braces; keep it consistent with the `-ffp-contract=off` of the other platforms).
7. **CI** (`.github/workflows/native.yml`): new job `windows-clangcl` ("Core (Windows x64, clang-cl)"), copy of `windows`, with `cmake -S native -B build -G "Visual Studio 17 2022" -A x64 -T ClangCL` (or Ninja + `-DCMAKE_CXX_COMPILER=clang-cl` if the VS toolset is missing), `timeout-minutes: 90`, `cmake --build build --config Release -j 4`, `ctest ... -C Release --output-on-failure`, and an explicit assertion step `ctest -C Release -R "^(fx|fxzero|padfx|live_meters2|live_chlvl|live_masterm|fxsong|modfx)$" --output-on-failure` followed by a check that none of them printed `not run` / was skipped (`ctest --no-tests=error` plus grep for "skipped" in the `-V` output; the summary line "tests passed, 0 skipped" for this subset). Upload `thunder_core-windows-clangcl-x64` (lib + `thunder_dsp_*.lib`). The old `windows` job stays unchanged (cl.exe, no TFX) and is the cl portability check.
   Then `native-desktop.yml` `windows`: add `-T ClangCL` once the core job is green; if the WebView2 shell (H6) or miniaudio (H7) does not compile under clang-cl, STOP: report the errors, and switch to fallback (a) (build `thunder_dsp_*` in a Ninja/clang-cl sub-tree and import the .libs), for Fable to decide.
8. **Second commit, same job:** pe and mods come with the same directory (`THUNDER_ENGINE_PE`, `THUNDER_MODFX_MODS` become 1 on Windows): this turns more skipped tests into run tests (Plaits/Elements layers, Marbles/Tides, `modfx`). They are strict builds pinned by committed hashes; if a hash or a -100 dB gate differs on Windows, that is a libm difference to be reported with figures, not waved through (see 5). The thunder_dsp_w library is not linked into the core and is only built for the wasm modules: make it `EXCLUDE_FROM_ALL` on host builds if its compile time matters (measure first).
9. Notes file `docs/port/W-TFX-NOTES.md` (what ran, figures, the flags that clang-cl accepted/ignored: look for "argument unused" / "unknown argument ignored" warnings in the first build log and fix each; a silently ignored `-ffp-contract` would be a bug), PICKUP line, `PINS.md` unchanged (no new pins, no new patches unless step 5 fails).

**Pump next (separate unit W-PUMP, same recipe):** `pump/CMakeLists.txt` has the same `if(MSVC) return()`; with clang-cl in place, change it to `NOT Clang` the same way (C++17, `-O3 -ffast-math -DNDEBUG`, pffft vendored). Not done here; but tests that need both libraries (`live_fxvalues`, `live_fxvalues_alloc`) will keep skipping on Windows until then. State this in the notes.

## 5. Risks for the audio thread and for the goldens
1. **Denormals / FTZ:** the tfx/mods/pe groups are built WITHOUT fast-math on host builds, so the compiler adds no FTZ startup code on any platform (a `/fp:fast` link would, via `fpinit`; do not use it). The core sets FTZ+DAZ per audio callback with `ScopedFtz` (`core/src/rt/ftz.h`: `_M_X64` branch covers MSVC/clang-cl) through `_mm_setcsr`, which is the CPU state and so applies to clang-cl-built effect code called inside it. Offline tools and tests do not set it (same as Linux). Verify with a 30 s reverb-tail case under `ScopedFtz` vs without in the notes (CPU time), not just by reading.
2. **`/fp` and contraction:** keep `-fno-fast-math`, `-ffp-contract=off` (`/clang:`), default x64 SSE2 scalar math; never `/arch:AVX2` for these groups. clang-cl's default for `/fp:precise` allows contraction in newer clang; pass the explicit flag (step 3/6) and check the first build log for ignored arguments.
3. **libm:** UCRT's `expf/exp2f/cosf` round differently from glibc, Apple's and wasm's musl (U14: Autowah and Beads moved -50..-64 dB between libms). The Mac build passes the -80 dB gate with Apple's libm, so there is precedent, but Windows is unmeasured. If a case misses -80 dB on Windows, report the per-case figure; the lead decides (a per-platform figure like `e_pshift_def`, never a blanket allowance). `libm-dump.mjs` / `fx-clk-dump.mjs` bit-exact checks (the core's own JS-libm functions) already run on the Windows job.
4. **Alignment:** no SIMD types, no `alignas` in the compiled files (grep), `Fx::operator new` uses `malloc` (16-byte on Windows x64). `delay_line.h` packed items are byte-addressed: covered by the layout test (B2). The core is x64-only on Windows (no 32-bit x86, no x87).
5. **Exceptions on the audio path:** none thrown there; `thunder_fx_malloc` throws only on control-thread plan building (U34a). With `/EHsc` unwinding from `-fno-exceptions`-style code is safe on Windows x64 (table-based), but do not mix `/EHs-c-` anywhere.
6. **Stack:** Windows threads default to 1 MB (audio callback thread by miniaudio/WASAPI is system-sized); Beads' VLAs were up to `block/ratio` floats (a few KB): fine, but the build log should be checked for `/analyze`-style stack warnings (clang-cl: `-Wframe-larger-than`, not needed).
7. **Build/time:** configure now needs git + network + python3 + GNU sed on the runner (same as Linux/Mac, new for the Windows job); a failed fetch fails the configure, as on the other jobs.
8. **cl.exe coverage:** the existing job keeps the cl build compiling, but without TFX. If a clang-cl-only construct creeps into the core, the cl job catches it; do not remove it.
