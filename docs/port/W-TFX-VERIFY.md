## Findings

### MEDIUM
- **M1. `live_meters2` on Windows is not gating at all, not just for the 3 pump checks.** `native.yml` (windows-clangcl job): `ctest ... -E "^live_meters2$"` for the main run, then a separate `continue-on-error: true` step whose pipeline ends in `grep | cut`. The 3 failures are pump-only: `test_live_meters2.cpp:167` (slots mask 7 needs the pump slot), `:185` (type id `kPumpT0+1` = 201), `:186` (the pump COMP slot's gain reduction); log lines `FAIL ...:167`, `:185`, `:186` and `live_meters2: 615 checks, 3 failed` (windows-clangcl job 140274987901, step "live_meters2 ..."). Other platforms still gate it: Linux GCC `206/271 live_meters2 Passed`, Linux clang `207/273`, macOS `151/212` (all Passed; the test file is only changed by the `TFX:` print). But on Windows the other 612 checks (the FXLVL / FXDYN parts for the effects, which the plan listed as the named proofs) can regress with the job staying green. Fix: have the step fail unless the FAIL lines are exactly those three (`:167`, `:185`, `:186`) and the total is 615 checks / 3 failed; also count `TFX: yes` there (plan section 4 wanted it printed by three live tests; the hard-coded `-eq 2` covers only chlvl and masterm).
- **M2. `desktop_input_capture` is a pre-existing race, not caused by this PR, but it makes this PR's Windows jobs flaky.** Failures on this PR: MSVC job 140228869500 (269de6ad ... 17d5ef06 per the notes) and clang-cl job 140262804716 (270a2d07), always `test_input_capture.cpp:47: meters: one peak per armed channel` (2.6 to 2.7 s into the test). Passes on the head (`171/173 ... Passed 2.70 sec` in the MSVC job; `10/12 ... Passed 2.20 sec` in the desktop job). Mechanism, read in the code: the test calls `ic.readPeaks()` (line 47) after `stop`; `readPeaks` is read-and-reset (`input_capture.cpp:108`), and the drain thread also emits the `rec` meter event ~15 times a second and zeroes `peaks_` each time (`input_capture.cpp:166`). If an emit lands between the last drained block and line 47, the test sees 0 (needs `pk[0] > 0`, `pk[2] > 26.9`); Windows' coarser timers make that window likelier. Not seen in the failed runs of other branches that I opened (those failed in rt_core / census / live_host / live_chlvl, all different), and the code is untouched by the PR. To make it robust (not done): poll `readPeaks()` in a loop while feeding and keep the per-channel maximum, or assert on the `rec` event the test already collects (`pk` in `events`), or give the capture a test hook to stop the periodic emit before the check.
- **M3 (LOW, MEDIUM if the owner builds Debug): fallback (a) is Release / x64 only and nothing says so.** `core/dsp/CMakeLists.txt` (prebuilt branch) sets a single `IMPORTED_LOCATION` and checks only that the three `.lib` files exist. A Debug configure of the shell (`/MDd`; the generated vcxproj files carry `MultiThreadedDebugDLL` in 157 places, log line 7149) would link Release effects: LNK2038. Windows arm64 configures the same way and fails at link (or worse, at run) because `-A x64` is hard-coded in the workflow, not checked in CMake. Add `FATAL_ERROR` for a non-Release shell build or for `CMAKE_SYSTEM_PROCESSOR` not AMD64, with a line in HANDOVER.

## 4. The Beads patch (prepare.sh)
- Byte order: slot 0 = bits 0..11 of `b[0] | b[1]<<8 | b[2]<<16`, slot 1 = bits 12..23: the GCC little-endian bit-field layout (harness above, 0 mismatches).
- Sign extension: `v >= 0x800 ? v - 0x1000 : v` on a 12-bit field; store masks `unsigned(v) & 0xfff` (negatives wrap as the bit-field store does).
- Stereo item: `l` = slot 0, `r` = slot 1; mono item: `odd` = slot 0, `even` = slot 1 (`thunder_put12(raw, i ? 0 : 1, lr)`), matching the original field order.
- No out-of-bounds: every access is `raw[0..2]` of a 3-byte member; sizeof is 3 (static_assert in `test_dsp_layout`, and the upstream `assert(sizeof(ItemType) == 3)` at `delay_line.h:247/250`, live because the dsp builds carry no `-DNDEBUG`); buffer arithmetic is `sizeof(ItemType)` based (`delay_line.h:273,277`), unchanged. No unaligned access: byte loads and stores only, alignof 1. The `thunder_get12/put12` helpers are `inline` in a header: no ODR problem.

## 5. RAND_MAX
`wasi_rand.h`: after `<cstdlib>`, `#if defined(_MSC_VER) && defined(RAND_MAX) && RAND_MAX != 0x7fffffff` then `#undef` / `#define 0x7fffffff`. `thunder_wasi_rand` returns `(int)(s >> 33)` of a 64-bit LCG: 31 bits, 0 .. 2^31-1, so `rand()/(float)RAND_MAX` is in [0, 1], the same expression and range as wasm and glibc; no modulo, no bias introduced. Compiled where RAND_MAX is 32767 only (UCRT); glibc / Apple / wasi are 0x7fffffff and skip the block. The only RAND_MAX users in the prepared trees are `cs/DSP/ModulatedDelay.h:68` and `ModulatedAllpass.h:70` (Cloud Seed). The `space` effect now sits at -127.7 dB (fx_space_def) from -13.7 dB.
