# MIRROR-684: the native core follows web builds 617 to 684

Unit F1 / MIRROR-684, branch `n2/f1-page-from-beta` (PR #344 into `native`). `beta` (page build 684) was merged into `native` (page build 616, merge-base 14 Nov)
so the Android APK bundles the current page; 15 core tests that compare the C++ with the web then failed. This unit makes the C++ reproduce the web again.
Rule kept: the C++ was changed to match the web; the committed "current" goldens and tables were regenerated only with the project's own tools, and only where the web's
own files changed (list at the end). No test was weakened (one test's constant moved with the format, see "Tests changed").

## NOT mirrored / left for a later unit

* `web-ref/chains-worklet.js`, `mix-excerpt.js`, `chains-wiring-excerpt.js` are still the 20 Nov pin: `web-pin-chains.mjs` cuts `index.html` by line number and fails loudly on a new `index.html`. The chains song golden (`chains_song_*`) therefore still records the 20 Nov worklet; nothing in it uses knobs / send / recv. Re-pinning means redoing the line ranges in that tool.
* The page's core RESUME replay of the last BYP / KN values (`chaseRun`, `core-processor.js`) and the `knSt` replay for waves live nodes made later: native has no silent-step chase of engine / chc events at all (its mid-song start rebuilds chance seeds only), so this is a gap of an older kind, not new here.
* The sequencer's KN1-KN8 events reach the chains host. They are not routed to a waves live node: native has no waves live host in the render / LiveHost path (`WavesLive` exists and now accepts `Knob` events, covered only by the build, no test).
* OLDSCHOOL stretch (660), SYNC TO LINES / C-4 pitch (655): see WEB-FOLLOW-20NOV-NOTES.md "stretch port needs"; nothing new here.
* Page-only changes (UI, Drive, startup song, FX presets, resize, native-core client `thunder-core-client.js`) need no C++.

## For the lead's review: live-path items

None changes DSP of the audio thread beyond a straight mirror, but these touch live types:

1. `ChainsHost::event` (queue of tracker events, audio side): the accepted `p` range is 1..23 (knobs p 16..23); the `Ev` struct and `due` rule are unchanged. `ChainsEngine::setBypassSwitch(16..23)` is a float store.
2. `ChainsLive` (`clive.cpp`): `byp_` is 23 long, `ChainsEvent::Bypass` accepts 1..23, `NodeIn::kn` points into it. Nothing else changed.
3. `WavesLive::apply`: a new `Knob` kind (float store). `WavesEngine` has `knobs_[9]`.
4. **Allocation on the calling thread**: `ChainsEngine::setParam(lab)` / `setText` and the waves equivalents recompile the graph when the module is a Send / Receive (the JS does too, on its audio thread). If a live runner posts a `lab` Param for a send / recv it allocates on the audio thread. Edits through `preparePatch` (the page's `chain.edit`) are not affected. A guard (drop such a live Param and let the page swap a patch) is a one-line change if the lead wants it.
5. `Seq` emits up to 8 more `chc` events per row (KN1-KN8, no end events); worst case 33 x 8 = 264 inside the 1793 spare of `kSeqStepEvents` (comment in `seq.h` updated).
