# H6 verification (PR #339, head 46c7e51, `n4/h6-desktop-shell` into `native`)

Independent read by a verifier who did not write it. Read-only review of the diff (`git diff native...HEAD`, 3,288 lines) plus the Android shell it mirrors. NOT built, NOT run: this box cannot build WebView2 / WKWebView, and the host tests were not re-run here (the notes say 7/7 in CI). Everything below is from reading the code. Windows / Mac behaviour on real hardware is unverified.

NOTE ON BASE: the branch is based on 97e8d30; `native` has since moved (M4 #332 merged at 65e97ef). Rebase before merge (see C-1).

## Verdict: MERGE AFTER FIXES

The app:// resolver is sound, the threading split is correct, teardown order is correct, and the caps do not over-claim. The blockers are the unauthenticated file channels (S-1), the `S:` message that exits the process in a normal run (S-3), and the missing origin check (S-2). All three are small fixes.

## HIGH

- **S-1 (HIGH, security; inherited from electron/main.js but a native shell should not copy it)** `shared/desktop_api.cpp:112,113,139` (+ `readProj` 44-50, `writeProj` 53-61, `writeOut` 63-71): `file-read`, `file-save` and `out-write` take the path from the page and check only the extension. Any script in the page (a malicious shared .thunder with an XSS payload is enough; the CSP is report-only with `'unsafe-inline'`, see S-5) can read any `*.json` / `*.thunder` on the disk, overwrite any `*.json` / `*.thunder` (e.g. editor settings, package.json; the temp-then-rename makes it a clean replace), and write `*.wav` / `*.zip` / `*.mid` anywhere. Fix: keep a set of paths the user chose in a dialog (`file-open`, `file-saveas`, `out-pick`, the `open-path` hand-off, the pending command-line path) and let `file-read` / `file-save` / `out-write` touch only those (the page's save flow already goes saveAs, then save on the returned path). Add a test: `file-save` to a path never returned by a dialog is refused.

## MED

- **S-2 (MED, security)** `win/main_win.cpp:141-145` (WebMessageReceived) and `mac/main_mac.mm:168-169`: the sender is never checked. WebView2: `a->get_Source()` is not compared to `app://thunder/`; `SetAllowedOrigins(1, {"*"})` at `:181-185` and `Access-Control-Allow-Origin: *` at `shared/app_scheme.cpp:91` let any origin read the bundle, and `AddScriptToExecuteOnDocumentCreated` injects the bridge into every frame, so a cross-origin iframe would get `thunderCore` / `thunderDesktop`. (A subframe's navigation does not pass `NavigationStarting`, which is main-frame only: use `FrameNavigationStarting`.) WKWebView: the script message handler is registered for all frames (`:120`; only the user script is `forMainFrameOnly:YES`); check `m.frameInfo.isMainFrame` and `securityOrigin` (scheme `app`, host `thunder`). Fix: drop messages whose source is not `app://thunder/...`; allowed origins `app://thunder` only; ACAO to the same origin or none.
- **S-3 (MED, wrong behaviour / DoS)** `shared/shell_core.cpp:141`, `win/main_win.cpp:247`, `mac/main_mac.mm:109`: an `S:<json>` page message always calls `onSelfTest`, and both shells set that callback unconditionally to a function that ends the process (`ExitProcess` / `exit`). In a normal run any page message `S:{"ok":true}` quits the app at once, unsaved work and all, with no close hand-off. Fix: only wire `onSelfTest` (and handle `S:`) when `--selftest` is set; drop `S:` otherwise.
- **S-4 (MED, security)** `win/main_win.cpp:151`, `mac/main_mac.mm:182`: top-level navigation to `data:` and `blob:` is allowed. A page (or an injected script) can navigate itself to a `data:` document that still gets the injected bootstrap and full bridge, outside the app:// origin. Allow only `app://thunder/` (and `about:blank` if needed); refuse the rest.
- **R-1 (MED, resource safety)** `shared/bridge_session.cpp:59-62`, `shared/text_util.cpp:21-32`, `shared/desktop_api.cpp:138`: the contract's caps are not enforced in the shell. No limit on the `B:` message length (the spec says 24 M chars): `raw.substr(2)` and `base64Decode` allocate whatever arrives before `PutStore` can say "past the end". No limit on a `song.load` text (`maxSongBytes` is advertised as 16 MiB at `bridge_session.cpp:177` but nothing refuses a bigger one) or on `out-write` / `file-read` size. The message queue `q_` (`:29`) is unbounded. Fix: refuse `B:` > 24 M chars, `song.load` > 16 MiB (err and `{ok:false}` reply), `out-write` b64 > a stated cap, `file-read` > a cap; bound the queue (or drop with an err).
- **R-2 (MED, crash)** unguarded exceptions on the UI thread. `shared/app_scheme.cpp:17,77,80` `fs::u8path` on percent-decoded bytes that are not UTF-8 (`app://thunder/%ff`) can throw on MSVC, inside the WebView2 `WebResourceRequested` callback / the `WKURLSchemeHandler` (no try/catch: process terminates). `desktop_api.cpp:44-50` reads a whole file into a string and then a second quoted copy (`bad_alloc` on a huge .json); `mac/main_mac.mm:23` `S()` builds `std::string` from `UTF8String`, which is nil for a string with a lone surrogate (UB / logic_error). `BridgeSession::run` has a `try`; `DesktopApi::handle`, `resolveAppUrl` and the two page callbacks do not. Fix: catch `...` in `resolveAppUrl` (return 404), `handle` (reply `{error}`), `onPageMessage`, and null-check in `S()`.
- **T-1 (MED, UI thread blocked)** `shared/desktop_api.cpp:111-141` runs on the UI thread by design (dialogs need it), but so do `readProj`, `writeProj`, and `writeOut` (base64-decoding and writing a render that can be hundreds of MB), and `onResourceRequested` (`main_win.cpp:127`, `readWholeFile`) reads each bundled file there. During a render save the page, the 20 ms event flush and the 100 ms tick stall (audio is unaffected: callback and worker are separate). Fix: do the disk IO (not the dialog) on a worker and reply from there (`toPage` is already thread-safe).
- **C-1 (MED, contract parity / merge order)** `shared/bridge_session.cpp:164,179`, `bridge_translator.cpp` (no `fx.values`, no `recovery.*`, `meters.want` reads `rate` only): the hello caps say `meters2`, `fxValues`, `recoveryPut` are absent, and that is true and correct (nothing is claimed that is not built). But on `native` the Android shell now reports all three (LiveBridge.kt:163-164, M4 #332), so the page on desktop has no FX meters, no `fx.values` knob path and, importantly, no `recovery.put` (so no "Restore unsaved changes?" after a crash). This is a feature gap, not a bug, but it needs a line in the "Decisions for the lead" and a follow-up item (H7/H8 or its own). Rebase onto `native` so the in-place Android files (live_events.*, live_jni is not used) are M4's and the tests run against them.
- **C-2 (MED, wrong behaviour)** `shared/bridge_session.cpp:213-222` `engineReset`: if `host_.start` fails the page has seen `{t:'engine', up:false}`, then only an `err`; it never gets `up:true` and the transport stays dead until the next `hello`. Android's `engine.reset` has the same shape, but on desktop a failed reopen is likelier (device busy, unplugged). Fix: emit an `engine` event with an error flag, or a fatal `err`, so the page can tell the user.

## LOW

- **L-1** `shared/bridge_session.cpp:20-27` vs `:184-190`: `shutdown()` touches `pump_` without `pm_` while `startPump()` (worker thread, on a late `hello`) can assign it: a data race on a `std::thread` and, if a hello lands between the pump join and the worker join, a pump thread that outlives the first `shutdown()` (the second `shutdown()` from `~BridgeSession` does join it, so no terminate). Narrow (closing the window during a hello). Fix: take `pm_` around the join/assign, set `stop_` first.
- **L-2** `win/main_win.cpp:217,256-258`: `WM_DESTROY` runs `g_core->shutdown()` on the UI thread, which joins the worker; a worker inside `songLoad` (20 s timeout) delays the window closing by that long. Order is right (engine and output stopped before the process and WebView go), but the WebView2 controller is never `Close()`d, and the COM globals (`g_ctrl`, `g_web`, `g_env`) are released by static destructors after `CoUninitialize()` (`:257`). Fix: `g_ctrl->Close()` and release the three before `CoUninitialize()`.
- **L-3** `win/main_win.cpp:138,177`, `mac/main_mac.mm:116,127`: DevTools always enabled; `--cdp-port` opens `127.0.0.1:N` with `--remote-allow-origins=*`, so while it runs any web page in the user's browser can attach to the app (and S-1 makes that a file read). Dev flag only; say so in `--help`/notes, or build it out of Release.
- **L-4** `shared/app_scheme.cpp:47`: the CSP is Report-Only, so it blocks nothing (this is stated in the notes). `'unsafe-inline'` in `script-src` is needed by the page today. Fine for the skeleton; make it enforcing with a plan, because S-1 leans on it.
- **L-5** `shared/bridge_translator.cpp` (`ival`, `(int)v.asNum()`), `put_store.cpp:201` (`(int)j.num("pid")`, `(int64_t)j.num("o")`): casting a double outside the int range is undefined behaviour (value garbage, no crash seen). Clamp first.
- **L-6** `shared/text_util.cpp:27`: `base64Decode` accepts whitespace and any number of `=` anywhere; harmless, but `put` should reject a chunk whose decoded size is not a multiple of 4 before decoding (it does, after).
- **L-7** `win/main_win.cpp:130-132`: whole file in memory per request, no Range support (audio `<audio>` seeking on big `sounds/`), 404 gives no CORS header. `mac/main_mac.mm:45` `stopURLSchemeTask` is empty (fine, the task completes synchronously).
- **L-8** `shared/live_host.cpp:86` `audioName()` reads `out_` without `life_`; used for status only.
- **L-9** selftest exits with `ExitProcess` / `exit` while worker and audio threads run (`main_win.cpp:74`, `main_mac.mm:109,137`): CI only, but can hang or crash at exit and fail a green run.

## Checked and fine

1. **app:// resolver** (`app_scheme.cpp:51-95`): host must be `thunder`; query and fragment cut; percent-decoded ONCE (`%2e%2e`, `%2f`, `%5c`, `%00` caught: `..` segment, `\`, `:` (drive letters, ADS), NUL all refused); absolute paths, `//`, and trailing `/` handled; double encoding stays literal; the file is canonicalised and checked to lie under the canonical root (a symlink cannot lead out); directory returns index.html only inside the root. `percentDecode` bounds are right. I found no way out of the bundle. The bundle itself (`cmake/copy_web.cmake`) is a fixed list, no repo-wide copy.
2. **Navigation**: main-frame http(s) goes to the browser and is cancelled; `NewWindowRequested` / `createWebView` likewise; `file:` and everything else is cancelled (except data/blob, S-4).
3. **Threads**: engine calls only from the session worker (`BridgeSession::worker`, control) via `LiveHost::call`, with timeouts (5/10/20 s); the miniaudio callback only touches `audioEng_` (atomic) and `render`, no allocation or lock; the event pump only drains events (no engine call); `toPage` is mutex-protected and batches to the UI thread; `DesktopApi` is UI-thread only. Teardown: `LiveHost::teardownLocked` stops the transport, lets two callbacks run, closes the output (no callback after), nulls `audioEng_`, THEN stops the threads and destroys the engine; `ShellCore` destructor order (session, api, host) is safe because `shutdown()` already joined everything.
4. **Hello**: a second `hello` is idempotent (`LiveHost::start` returns the existing rate, `startPump` guarded): no thread or engine leak. `engine.reset` clears `puts_`, `lastSlots_`, songs, kit.
5. **Parity**: message names and refusals match `BridgeTranslator.kt` for the ones present (hello, song.load ask with the SongFit reply and `pending`, kit.load -> `kit` + `fit`, put / buf.use / buf.free / pads.commit, play ... pdc.set, engine.reset with `up:false/true`, meters.want clamp 0..30, mix.set tr 0..32 / 'm' / key refusal of `send`, fx.set exactly 12 finite numbers). Unsupported messages answer `err` (and an error reply for an ask). `files:false`, `midi:false`, `link:false`, `inputs:false`, `render:false` are true to what is built. Hello without `live` does not start anything.
6. **PutStore** limits: channels 1..2, `n` <= INT_MAX/4, `frames == n`, whole floats, 256 MiB held, 30 s stale sweep, pid dropped on every error, chunk past the end refused, completeness checked at `last`. JSON depth is limited to 256 (`rt/json.h`). `pad_take` copies from the store's own sizes, not from the message.
7. **Audio callback**: stereo f32 at the device rate; `render` chunks by `maxBlock`, so a larger device period is safe.
