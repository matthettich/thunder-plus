# U31 notes: the ...chains engine in the core

Branch `n3/u31` (based on `native`). Source of truth: `chains/chains-worklet.js` outside the shared module block (ChainsEngine, Graph, ChainsProcessor, ThunderChains, the chains-only modules). THE JS IS THE SPECIFICATION, quirks included; what is decided differently is listed under "Deviations". Not in scope and not done: wiring into the mixer, `xeng_render_voice` or the bridge (see "Conditions for the wiring").

## What is here

| Piece | File |

Modules are the MODFX ones, the 33 track-effect wrappers and control modules U30 ported, plus the chains-only ones. All chains modules are mono-scope (one slot, no voices).

## Fuzz findings at raw parameters

Using parameters as set (the JS's behaviour) lets a hostile value reach code that the clamp had hidden. The ASan + UBSan fuzz found three, all fixed; each is a place where the JS itself does not return or its wasm traps:

1. Harmonizer: with a window parameter of -Infinity the final search `for (L = c0 - 5; L <= c0 + 5; L++)` never ends (in the JS either). It is now a counted loop of the same eleven candidates (same numbers wherever the JS's loop ends). A deviation: native returns where the JS hangs.
2. Tides: a shape outside 0..1 becomes an out-of-range float-to-int conversion and an index of `shape * 1025` into the wavetable (signed overflow, then a read far outside it); the wasm traps or reads garbage. Library-backed modules (the tfx effects, Marbles, Tides) therefore keep the value HELD INSIDE its range (a NaN takes the default), as U30 held every module's: `heldInRange` in `waves/graph.h`. Inside the range nothing changes; the golden over-range rows do not include these types. The pump modules keep their own staging of values.
3. Rings FM voice: the table read described above (a value of exactly 1.0, in range): `prepare.sh`.



## Design points

- Run list (focus): the Chain Out of this track, the Sidechain Out at the lowest-track Chain Out of its connected component, with telemetry `scin` and probes, and every ancestor through `inc`. Computed on the control thread by `prepareDerived`; allocation-free after `compile()`.
- Bypass: numbers 1..15 (own `_bn`, else the lowest free, in patch order); switch rule `want = sw < -.5 ? own : sw >= 1.5 ? !own : sw >= .5`; a crossfade over a full 128 block; a module settled in bypass runs on silence. Dry copies live in `ModNode.dry`.
- Sends (Sidechain Out / In): standalone engines copy `sendOut` to `sendPrev` at `endStandaloneBlock`, one block of delay as the JS; with host sends (`setSendIn`) the host's are used. Source keys: 0 Self, 1..8 sends, 9 and up taps (through `tapMap`).
- Spare pump instances (decision (e)): a pump module's instance and its spare are made in `prepare()` on the control thread. A bad block (output outside +-8) is silenced on the audio thread, which swaps in the spare by atomic exchange and puts the dead one into a `dead_` slot; `service()` (control thread) frees dead handles and makes the next spare. Offline `process()` services inline (`setInlineService(true)`, the default) so offline matches the JS's new-instance-at-next-block. Counters `chains_pump_swaps/bad/dry`. Tested: with every parameter at maximum and a +-7.9 input, ptube, pgate, pvox, ptune, pcrush, pswirl, pstutter go bad; 634 of 637 bad blocks were followed by a spare and none ran dry.
- Resample: two preallocated buffer pairs; finished takes go through a 16-slot SPSC ring (`popTake` / `releaseTake`); a full ring releases the take at once.
- Expression: its text is compiled at `prepareText` (patch preparation), never at the first audio block.
- Live runner: events in an SPSC queue (1024) plus a pending array (1024; see "Lead review, 18 Nov" G); blocks are cut at events; input and output rings of 512; patch swap by mailbox (8 slots) and retired slots (at most 6 patches in flight, see D); offline render = the same loop with no queue and no latency (`ChainsLive::renderOffline`).
- Live queue rules (U31 second round): the last 256 places of the queue (now 1024 events, see the lead review) (`kChainsReserve`) are for events that must not be lost (Playing, Bypass, Tempo, Patch); a Param event is refused first. When the pending array is full a Param coalesces with the earlier value of the same (module, parameter); an event that must be kept makes room by removing the oldest Param, else a Tempo / Bypass that a later one of its kind replaces anyway; only when nothing can give way is an event dropped (counted, `droppedEvents`), and a dropped Patch event hands its patch to the control thread (`retired_`), so its mailbox slot is free again after `service()`. `preparePatch` returns false when no slot is free, when 8 patches are in flight (prepared and not yet swapped in, or swapped out and not yet collected: the audio thread needs a retired place for each swap) or when the queue cannot take the swap event (the patch is freed). `ChainsLiveStats` counts `coalescedEvents`, `deferredPatches`, `refusedPatches`, `droppedEvents`, `lateEvents`. [Lead review 18 Nov: the queue and pending array are 1024 each; an incoming Tempo / Bypass / Playing removes the earliest pending one of its kind (the last posted wins) so a Playing flood cannot hold a Patch event out; at most kChainsSlots - 2 = 6 patches are in flight.]

## Deviations from the JS (decided)

1. Track In with a track out of range gives NaN in the JS; here silence.
2. Scope's `show()` (display) is not ported; its audio is.
3. Telemetry data output and the quality-shed load meter are not ported (the run list for telemetry is).
4. The JS's tapmap / busmap accept fractional entries (JS index quirks); fractions are dropped or truncated here.
5. A live Param event's module id is limited to 39 characters (name 23); a longer one is refused by `post()`.
6. The live runner has no text event: an Expression's text changes arrive by a patch swap.
7. A patch swap does not carry module state over (the JS `loadPatch` resets state too).
8. Library-backed modules (tfx effects, Marbles, Tides) hold a parameter inside its declared range; every other module uses the value as set, as the JS (see "Fuzz findings at raw parameters").
9. Harmonizer's final search is a counted loop: it ends where the JS's never would (a window parameter of -Infinity).
10. Where the JS throws in `loadPatch` (a null module, a null / number cable, a `modules` / `cables` that is not iterable, a module `type` that is an Object property) its engine is left half built; native refuses the patch and keeps the playing one (a decision, as in U30).
11. The dry state of a pump module: in the JS a module whose instance went bad makes a new one on the audio thread at the next block (`pump_new`, the block that went bad is silent), so the JS is never dry. Native cannot make an instance on the audio thread: the dead one goes to the control thread, and a spare made in advance takes over at the next block (no dry block; the spare is made with the module's parameters, as the JS's new instance is). Only when no spare is ready (a second bad block before `service()` has made the next spare) the module is DRY: its output is silence for the block, counted by `chains_pump_dry()`, until `service()` runs. This matches the JS's own bad-block output (zeros) for that block; it differs from the JS only in that the next block is silent too. See the `service()` rate in "Conditions for the wiring".

## Lead review, 18 Nov (clive.cpp, cengine.cpp at f421b6f)

A. **Stats race: fixed.** `ChainsLiveStats` was a plain struct written by both threads. Every counter is now a relaxed `std::atomic<uint64_t>` (`chains.h` `ChainsLive::Ctr`, bumped by `bump()` in `clive.cpp`); `stats()` returns a snapshot by value (readable from any thread; the numbers of one snapshot are not one instant). `enginePos()` is a published copy (`posPub_`, relaxed), `bypassSwitch()` is documented as diagnostics for when `process()` is not running. TSan (K) is clean.
B. **Single producer: stated and checked.** `chains.h` above `post()`: post / postParam / preparePatch / service / loadPatch from ONE thread or serialised by the host. A debug build (no NDEBUG) keeps the first caller's thread and aborts with a message on a second (`ChainsLive::ctlCheck`, `clive.cpp`). Release builds are not checked (the check is not free enough for every post, and the host contract is the rule).
C. **`service()` fallback removed.** The engine now keeps `curA_` (atomic, `ChainsEngine::currentPatch()`), set in the constructor, `dispose()` and `swapPatch()`, i.e. wherever `p_` changes; `ChainsLive::cur_` is gone and `service()` uses `currentPatch()` only. A patch loaded straight into the engine before start (`node().engine().loadPatch`, as the tests do) is covered by the same atomic; `ChainsLive::loadPatch` is a convenience for it.
D. **Patch hand-over bound: fixed, with a larger margin than the review asked for.** Counting what the places must hold: R (in `retired_`) + S (waiting in `slot_`) + 1 (the patch the audio thread holds between `slot_[k].exchange(nullptr)` and `retired_[r].store`, in neither count) + 1 (the new patch) <= 8. So `preparePatch` refuses from R + S >= `kChainsSlots - 2` (6 patches in flight; `clive.cpp` preparePatch), not -1 as proposed: with one spare place the in-between patch and the new one would still be one too many. With the bound neither "(cannot happen)" path can happen; comments corrected (`clive.cpp` `dropPatch`, `apply`; `chains.h` `patchesInFlight`). Tested: `test_chains_live.cpp` (c) (6 delivered, the rest refused, one `service()` gives all back) and (b).
E. **Honest counters.** `victim()` removing a pending Param of ANOTHER parameter is counted in the new `droppedParams` (not `coalescedEvents`; `coalescedEvents` is now only a value replaced by a later value of the same thing, or a Tempo / Bypass / Playing replaced by a later one of its kind). Test E in `testQueueRules`. A Param refused for lack of room stays in `droppedEvents`.
F. **Playing = 0 always lands.** The incoming event is the later one in posting order, so when the array is full an earlier pending event of its own kind (Playing; Tempo; Bypass of the same switch) gives way to it (`victim(e)` in `clive.cpp`, after the oldest Param). A Playing flood therefore never fills the array with unremovable events. Test F: 4200 Playing events, then Playing 0: the engine ends stopped, nothing dropped. Cost, stated: the intermediate states of the removed events are lost; the last one posted wins. Consequence: a Patch event can no longer be dropped by a full array (the other unremovable kinds are at most 6 patches), so `dropPatch` is unreachable by construction and is kept as a guard; the former test (b) that dropped a Patch is now "a Playing flood loses no patch".
G. **Size.** `sizeof(ChainsEvent)` = 96 bytes. Before: 2 x 4096 events = 786 KB + rings, 32 tracks about 25 MB. Now `kChainsQueue` = `kChainsPending` = 1024 (reserve 256 kept): `sizeof(ChainsLive)` = 211,000 bytes, 32 tracks = 6.75 MB (printed by `test_chains_threads`).
H. **Bypass crossfade on cut blocks: fixed.** `ModNode.fade / fadeTo` (`waves/graph.h`) carry the 128-sample ramp across segments; `ChainsEngine::setCarryFade(true)` is set by the live runner only (`cengine.cpp` render): the engine API keeps the JS's per-call fade, so every golden is unchanged (`chains`, `chains_golden_current` pass; a full block with no fade in progress runs the same arithmetic, `f0 = 0`). Test `testBypassCut` (`test_chains_live.cpp`): Bypass on / release at sample S, a harmless Param event (the value it already has, another module) 10, 10 + 77 and 127 samples later: output bit-equal to the run without it, and no jump; it fails (4 checks) with carrying switched off. **Waves:** `ModNode.bypOk` is set by the shared `graph.h`, but the waves engine has no bypass at all (no use of `bypassed` / `bypOk` in `waves/engine.cpp` or `waves/live.cpp`), so there is no analogous fade; waves was not touched. Not checked: other per-block state in modules that a cut block changes (the JS has only whole blocks; the live == offline test holds because the offline path cuts the same way).
I. **`setParam(track | _bn)` on the audio thread: measured and bounded.** The scout search in `prepareDerived` was O(scouts x modules x cables) with two `P.find()` per cable (`P.find(const std::string&)` allocates nothing: a hash lookup of an existing string; confirmed, 0 allocator calls in `test_chains_param_cost`). I did NOT measure the old code before changing it. It is now index-only and O(modules + cables) whatever the number of scouts: the cables are kept as undirected CSR adjacency built by `compile()` (`waves/graph.h` `uaS / uaL / cmp / cmpLow`), the connected components are labelled once, and a scout runs here when the lowest Chain Out track of its component is this node's. Worst case measured (`tests/test_chains_param_cost.cpp`, ctest `chains_param_cost`: 1023 modules, 16002 cables, 510 Sidechain Outs, Release GCC, 2 cores shared, thread CPU time): median 0.125 ms, p99 0.19 to 0.33 ms, max 0.25 to 0.34 ms over 300 calls (under 0.5 ms; the test fails above 2 ms at p99 and on any allocation). (ctest runs it with 4000 cables, median 0.08 ms, max 0.30 ms; the 16002-cable figures are `test_chains_param_cost` with no argument. Finding: loading such a patch takes about 35 s because `compile()` runs after every cable, quadratic in the cables; control thread only, and a normal patch is far smaller.) Wall-clock showed a 4.2 ms spike every ~100 calls: the scheduler's 4 ms time slice on this loaded machine, not the call. Goldens: the scout / send scenarios are bit-exact as before.
J. **Resample take queue full: no free on the audio thread.** `resample_release` is `Resample::release`, which only clears `lent_[which]` (`cmods2.cpp:174`): nothing is freed. The full-queue path (`cengine.cpp` `onTake`) is therefore a drop in place; it is now counted (`Stats::droppedTakes`) and audited: `test_chains_alloc.cpp` block J (18 Resample modules, nobody pops, 900 blocks): 16 takes popped, 2 dropped, 0 allocator calls (counted malloc / calloc / realloc / free). I did not add an overflow list: a dropped take is the module's recording thrown away, the same as when its two buffers are both lent.
K. **ThreadSanitizer: run, clean.** `tests/test_chains_threads.cpp` (also ctest `chains_threads`, 3 s, any build): one thread runs `process()` in a loop (host blocks 128 / 64 / 100 / 17 / 300), one posts Param / Bypass / Playing / Tempo events, `preparePatch` every 40 iterations and `service()` every third, and reads `stats()`, with a Pump module that goes bad. ## Conditions for the wiring

1. One `ChainsLive` (or `ChainsNode`) per track; the host feeds exactly what `ChainsLiveConfig` declares (taps, sc, sends, feeds) every block, each input `n` frames long, pointer arrays at least that long.
2. A control thread MUST call `ChainsLive::service()` at least once per engine block of 128 frames (every 2.67 ms at 48 kHz; once per host callback is the natural place; faster is better) for as long as a pump module can go bad. It frees the patches the audio thread gave back and makes the pump spares. Measured (`test_chains_live`): called every block, no pump block runs dry (0 of 400); every third block, a third of the bad blocks find no spare; never, a pump module is silent from its second bad block on (`chains_pump_dry()` counts it, `chains_pump_overflow()` stays 0: the handle of a dead instance is never leaked). The patch side needs no rate: while fewer than 8 patches are in flight (`patchesInFlight()`) `preparePatch` works whenever it is called; at 8 it returns false until `service()` has run.
2b. Memory: a patch is refused, with `lastError()`, when its modules would take more than the budget (default 1 GiB per patch, from a measured per-type table; the host sets it with `ChainsLive::setMemoryBudget` / `ChainsEngine::setMemoryBudget`), and an allocation that fails anyway (`std::bad_alloc`) is caught at the preparation boundary and refused the same way, never on the audio thread. `cengine.cpp` alone is built with `-fexceptions` for this. The host must treat `preparePatch() == false` as a refusal and keep the playing patch; `ChainsLiveStats::refusedPatches` counts them.

3. `post()`, `postParam()`, `preparePatch()`, `service()` and `loadPatch()` are all called from ONE thread, or serialised by the host with its own lock (the queue is single-producer; a debug build aborts on a second caller). The audio thread calls only `process()`. A setParam of `track` / `_bn` on the audio thread costs, in the worst patch (1023 modules, 16002 cables, 510 Sidechain Outs), a median of 0.13 ms and at most 0.34 ms of thread CPU time (Release, this machine); it allocates nothing.
4. The host compensates 127 samples of latency (report it to the delay compensation of the mixer) and sums the node outputs with `chains_mixdown`-compatible soft clipping if it wants the JS's ChainsProcessor sum.
5. Sidechain sends to other tracks arrive one host block late, as in the JS.
6. Pump and tfx effect modules exist only where the libraries are in the build (`chains_have_lib`); the closed build refuses those patches' modules (silent module), the rest runs.
7. Not wired here: mixer, `xeng_render_voice`, bridge, state persistence.

## Choices for the lead

- State across a patch swap: reset (as the JS) or carried over for modules whose type and id are unchanged.
- Offline inline pump servicing (one thread, JS-like) versus the live runner's control-thread servicing: both implemented; confirm the live one for the app.
- Limit of 39 characters for a Param event id: raise it (costs a bigger event) or keep it.
- Telemetry data output and the shed load meter: port with the bridge or leave to the UI.
- The 16 effect cases left out by name: accept, or have a pump/tfx owner look at the ones near -47 dB (ladder stressed is the largest).
