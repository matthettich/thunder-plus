# RENDER-SF NOTES: the SoundFont route into the offline song renderer

**IN THE MIDDLE OF: the fixes for verify-242 (F1 to F4, F6 done and tested; F5 / F7 noted below); final sanitizer + full ctest run, push, waiting for the PR's CI.**

Branch `n1/render-sf` (from `native` 8a33138). Spec: `DISPATCH-NOTES.md` rows 5-6 and section 2 ("SoundFont"): "the piece to add next is a host input for the font (`set_pad_sf`) and a `SfPool` member rendered into `mix_.inputs` next to `pool_`".

## What was built
* `SongRenderer` holds an `sf::SfPool sfpool_` next to `pool_`; both render into `mix_.inputsL/R()` (the pool adds; the mixer clears the inputs after use). `RenderPads::sf[pad]` is the pad's `sf::SfPad` (font, preset, PCM, params; `font == nullptr`: none prepared).
* Routing in `dispatch` (all of it follows `core/core-processor.js`):
  * `ROUTE_SF` pad, preset prepared, `SfPool::covers()` (a zone exists for the note's key / velocity: `sfNote`'s `if (!picks.length) return;`): the track's SAMPLER voices give way (`pool_.take`), then `sfpool_.note` (which does the SoundFont voices' own takeover, choke, poly). Counted in `notes_sf` and, when a voice was made, `notes_sf_played`.
  * `ROUTE_SF`, prepared, no zone for the key (or the key's zones were not decoded: the key list): nothing happens, no takeover (the JS returns before it).
  * `ROUTE_SF`, nothing prepared: SILENT, `notes_sf`, takes the track over in both pools (as before this change).
  * every note that takes the track over from the sampler's side (a played sampler note, a live note, a missing variation, a reversed + shaped note) now also takes the SoundFont voices over (`takeAll` / `sfpool_.take`): the JS has ONE voice list per track.
  * `stp`, `off`, `mod` go to both pools. `voices()` (song end, `voices_active`) counts both.
* `SfPool::covers(e, pad)` (new, `sf/sf_live.h|cpp`): the same validity and key / velocity code as `note()`, without side effects. Nothing else in `sf/` changed.
* A test-only tap, `SongRenderer::setInputTap`, on the mixer's per-track inputs (one null-checked function pointer per quantum).
* Stats: `notes_sf_played` (appended to `thunder_render_stats`). It is NOT part of `notes_played` (that stays "the sampler played").

## The C API (render.h)
```
int thunder_render_add_font(r, bytes, n);                     // copies + parses once; returns font id 0..15 (THUNDER_RENDER_MAX_FONTS) or < 0
int thunder_render_remove_font(r, font_id);                   // E_ARG for an unknown id or a font a pad still uses
int thunder_render_set_pad_sf(r, pad, font_id, bank, prog, const thunder_render_sf_params* params, const uint8_t* keys, size_t nkeys);
int thunder_render_clear_pad_sf(r, pad);
typedef struct { uint32_t size, reserved0; double trans, velo, atk, rel, level, len; } thunder_render_sf_params;   // NULL = defaults (0, 0.7, 1, 1, 0, 0)
```
Same style as `set_pad` / `set_variation`: copied input, all validation before anything changes, only before the first read or drain (`E_STATE` after, and on a dead handle), one shared 512 MiB budget (`THUNDER_RENDER_MAX_PAD_BYTES`): the font copy + the parse tables of every font, plus every pad's decoded PCM (4 bytes a frame), count with the pads and variations. New code `THUNDER_RENDER_E_FONT` (-7): "not a SoundFont". Parsing and decoding happen in `add_font` / `set_pad_sf`; `read` allocates nothing (test: zero allocations over 60 reads, a counting `operator new`).
The decoder's budgets (`sf::DecodeOpts`: 256 MiB PCM per preset, 512 MiB PCM and 2^29 work units per font, 2^28 per call) apply too, with the per-font counters kept in the handle (a pad's share is given back when it is replaced, cleared; a refusal leaves the counters alone).
`keys` are the MIDI keys the song and the pad can play, AFTER the pad's `trans` (what `SfPool::note` computes: `clamp(round(60 + 12 log2 rate + trans))`; tracker note 48 is rate 1 = key 60). `NULL` = the whole preset (a full piano: 191 MB). A note on a key that was not decoded is silent.

## Choices for the lead
1. **API shape.** Weighed: (a) font bytes inside `set_pad_sf` (simplest, but 8 pads = 8 copies and 8 parses of a 23 MB font); (b) a font handle (chosen): `add_font` returns an id, pads name it, a font is parsed and held once; (c) a no-copy view of the host's bytes (an Android host maps the asset; `sf::parse` can take a view): NOT done, because a C API that keeps a borrowed pointer for the life of the handle is a trap. The cost of the copy is the font's size against the 512 MiB budget (GM SF3: 23.7 MB + 1.7 MB tables). If the Android host needs the mapped asset, add `add_font_view(r, bytes, n)` (the host keeps the bytes alive until free); the rest is unchanged.
2. **Decoded PCM is per PAD, not per (font, preset, keys).** Eight pads on the same preset decode it eight times and hold eight copies. A cache keyed on (font, bank, prog, key set) would share them; it needs reference counts against the budget. Left out: a song with several pads on one preset and different key lists is the common case and a plain key-union is not always what a host wants.
3. **Replacing a pad's preset needs room for both copies** (built first, so a failure leaves the pad as it was). When the budget cannot hold both, call `clear_pad_sf` first (a failure after that leaves it removed: the host's choice). `set_pad` (ERRORS (3)) releases the old copy first instead; kept apart here so that no call of the SoundFont family ever fails with a half-removed pad.
4. **JS core vs page player.** (i) The page's `sfNote` (index.html:22066) moves only the FIRST zone of a layered preset with a bend / arpeggio / vibrato; the core's (`core-processor.js:434` comment) and so `SfPool` move every zone. The port follows the core, as U32 did. (ii) A note on an SF pad whose font is missing: the page prepares the font and plays nothing, WITHOUT taking the track over; the core's `mine()` returns false and the page does the same. This renderer takes the track over (as it did before this change, "approximate"), because DISPATCH-NOTES said the unprepared SF pad "stays as now". A host that wants the page's exact behaviour can say so and it is a one-line change in `dispatch`. (iii) The page's `sfNote` takes the gain `ev.gain * 10^((level + 6) / 20)`; `SfPool` does the same (`P.level`), checked by the U32 goldens.
5. **POLY cap across pools: FIXED (verify-242 F3, the lead's ruling: JS parity).** A poly track's cap of four is shared by the sampler's and the SoundFont's voices, oldest first, as `core-processor.js` :442-443 and :582-583 (one list per track). `SongRenderer::capPoly` stamps each new voice with a serial from one counter (`VoicePool::stamp` / `SfPool::stamp`), and before a poly note it drops the track's ended voices in both pools (`liveOnTrack`) and releases the oldest across both (`oldestOnTrack` / `releaseOldest`: `T.shift()` + kill 0.006) until fewer than four remain; the pools' own caps then find room. No allocation; one pool alone behaves as before (the voice goldens and `render_sf` are unchanged).
6. **`notes_played` does not include SF notes** (`notes_sf_played` is separate). If a host's "notes that sounded" is `notes_played`, it must add the two.
7. **SfPool's 32 voices.** `dropped()`, `tOverflow()` and `autoDropped()` are now in the C stats (`sf_voices_refused`, `sf_voice_track_full`, `sf_voice_auto_dropped`, verify-242 F6), with `peak_voices_all` (both pools together; `peak_voices` stays the sampler's).
8. **Memory.** The `SfPool` is allocated for every renderer, SF or not (32 voices, a few KB each): not measured against the figures in render.h's MEMORY paragraph; small next to the mixer's delay lines.
9. **Pad `bank` / `prog` are ints** in the API (the JS rounds them with `Math.round` first); `trans` etc. are doubles with the ranges in render.h. The ranges (trans +-128, atk / rel 0..100, level +-200 dB, len 0..3600 s) are mine, wide enough for any page value; the player clamps / bounds the rest.

## Known, not fixed
- **F5.** Every `SongRenderer` builds an `SfPool` (32 voices, `sizeof(Voice)` 53,608 bytes: 1.7 MB zeroed) even for a song with no SoundFont pad, and `autoDropped()` walks it. Fine on the control thread; not free. (A lazy pool would need an allocation at the first SF note, which the read path may not do; it would have to be made when a pad's SoundFont is set.)
- **F7.** `add_font` parses before the budget check on the tables, so its peak memory during a parse can exceed the 512 MiB by the parser's own table limit (zones / gens / mods bounded at a few hundred MB by the `kMax*` limits; transient, freed on refusal). The `shrink_to_fit` inside `parse` swallows `bad_alloc` by library design: a failure injected there returns a valid font id (the last four allocations of `add_font`), which is fine. The per-pad `StreamCache` map of a `prepare_preset` call (one node per decoded stream) is transient and not counted either.

## Found by the full ctest (and fixed)
`render_api_oom` failed on the first full run: a create that failed at allocation 66 / 67 leaked the 1.7 MB of the new `SfPool`'s voices. Cause: `sf/sf_live.cpp` was compiled `-fno-exceptions` like the rest of the core, so its constructor had no cleanup when a later allocation threw (the files that make a handle are built WITH exceptions: `core/CMakeLists.txt`). Fix: `sf_live.cpp`, `sf_parse.cpp` and `sf_decode.cpp` joined that list (the first because `SongRenderer` now builds an `SfPool`, the other two so that an `E_MEMORY` from `add_font` / `set_pad_sf` frees what the parse / decode had built). Nothing throws on the audio path; the audio code is the same. After the fix: the 16 render / sf tests pass, including `render_api_oom` and `render_api_noexc`.
