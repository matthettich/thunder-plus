## Decisions (where the spec was wrong or silent)
1. **Cable id = a STICKY slot, not the index in the list.** The spec (3.2) says the cable id is the device's index in the current list and that "a re-plug that renumbers the list cannot re-route queued messages". Both cannot hold: after a renumbering a queued record's old index names another device. A device id gets a slot 0..199 the first time it is listed and keeps it for the session (when all 200 are used the slot longest unlisted is reused); a port with no device gets `200 + port` (as the spec says). A record's destination is its cable's device in the CURRENT list; a cable whose device is not listed is dropped (`dropped_gone`). Two letters on one id share the slot (one clock stream, one CLEAR), as the spec wants.
2. **Unplugging: the old cable's Stop does not reach the sink.** Spec 3.3 says the core sends Stop to the old cable and "the sink returns < 0". After `set_devices` without the device there is no sink index for it, so that Stop (and everything queued for the cable) is dropped and counted in `dropped_gone`. The other way round is covered: if the SINK fails first (the OS knows before the scan), the first failed send counts `send_errors`, marks the device gone until the next `set_devices`, and the rest of its messages are `dropped_gone` (no retry storm). Both orders are in test 5 (`list-loses-B`, `sink-fails-first`).
3. **CLEAR and what the OS already holds (CAP_TS).** With stamps a message is in the OS up to 20 ms before it is due, and a sink's `clear()` (MIDIFlushOutput) drops EVERYTHING the device holds, including messages BEFORE the marker's frame that must still sound (the output latency makes that a real window, 26 ms on the N0 phone). So the pump remembers the last 256 stamped-but-not-yet-due messages and, on a CLEAR that meets some, calls `sink.clear(dev)` and sends again those with `frame <= marker.frame` (same stamp, same order) and counts the rest in `dropped_cleared`. Without `CAP_TS` or without a `clear` nothing is recalled (nothing is in the OS earlier than 0.5 ms). Test 1 (`ts` mode) delivers exactly what `Drive::shell` kept for all 24 ledgers with a sink that models the flush; the first version without the re-send lost one message in three ledgers. Known gap: a message that the OS delivers between the pump's clock read and its `clear()` is sent twice (a window of microseconds).
4. **Clock map floor needs the engine position.** The web's `imp = ctx.currentTime - (ct + (now - pt))` needs "now" and the render position. The map call gets only `(frame0, host_ns0)`, so the floor reads `sink.now_ns` at the call (so `now_ns` must be callable from any thread; documented in the header) and the scheduler's last block start (`midi_last_now`, published by `midi_end`, a relaxed atomic). The error is at most one block (2.7 ms) and only while the floor is active. No floor set (`set_out_latency(0)`, the default) or no block yet: the pair is used as given. `imp > -0.5 s` is kept as in the web.
5. **Writers of the map.** "Any thread, wait-free": one writer at a time (an `atomic_flag`); a second concurrent call is skipped (the next one is 20 ms away). Readers use a seqlock with acquire / release data (no fences: TSan models them).
6. **Frames before the first map.** Read as "drained before the first `clock_map`" (not "frames earlier than the first `frame0`", which would drop legitimately late messages): those are dropped and counted in `dropped_nomap`. CLEAR markers still apply.
7. **Stale map** (not refreshed for 2 s, judged by the last raw `host_ns0` against the sink's clock at the pump): the last map is kept and every message sent while stale counts in `late`.
8. **Late ticks.** The pump drops a clock tick more than 20 ms behind its time (counted in `late` and `dropped_late_ticks`); anything else late is sent at once at the clock's time (`late` counts more than 2 ms). The core has already made the note verdict (B7).
9. **Queue full.** The queue is a sorted array of 4096 `thunder_midi_msg` (stable for equal frames; messages arrive nearly in order so the insert is at the end). When full the victim is the lowest class below the new message's (the core's own `prioOf` classes: tick, CC / bend / program, note-on / Start / SPP, note-off / Stop / All Notes Off), the latest in time among equals. A note-off, Stop or CLEAR is never a victim; if nothing is less important the new message is dropped, `queue_full` counts, and for a class-3 message `may_hang` is set (a field added at the end of the stats; the struct is size-prefixed).
10. **Stats** has two fields past the spec's: `dropped_late_ticks`, `may_hang`.
11. **`set_playing`** is a CONTROL call added as the spec asked (3.2); `set_out_latency` returns an int (E_ARG outside 0..2 s). Every control call re-syncs the scheduler; a full command ring returns `E_BUSY` and the next control call repeats the missing posts (the table is the truth).
12. **While playing a Gear change** is `set_port` with the values already applied; a cable change is `set_cable`, a clock box is `port_clock`; while stopped one `set_port`. The first sync of a port always uses `set_port`.
13. **`set_devices`** rejects (E_ARG, nothing changed) n > 32, a NULL list, an id without a NUL in 96 bytes, an empty id and a REPEATED id (a silently skipped duplicate would shift the sink's indices).
14. **Spin mode** spins on `sink.now_ns` at most 2^20 times (a stuck clock cannot hang the pump) and then sends. The tests' fake clock advances 1 us per call.
15. `thunder_midiout_*` constants `SEND_AHEAD` 20 ms and `SPIN` 0.5 ms are macros in `midiport.h` (ruling 5.10).
16. `midi_spp.cpp` is built with `-fexceptions` (it allocates a `Seq` and a vector on the control thread) and answers `-1` to a `bad_alloc`; `midiport.cpp` allocates only in `create`.

## The lead's read of #268 (L1-L3), 21 Nov
- **L1 (set_devices vs the pump).** At 09356e3 `set_devices` stored -1 into every `cabDev[i]` and refilled it, so a pump running in between saw a still-listed device as gone and dropped its queued messages (note-offs too). Now (`midiport.cpp`, `set_devices`): the new mapping is built in local arrays and each cable slot is written ONLY if its value changed (a device that stays listed is never written at all); a new device's token is stored before its live flag (release); `cabGone` marks are per cable (not per list index, which the list may renumber) and are cleared only for the slots of the new list. The pump's epoch sweep drops only cables whose live flag is 0, which is true only when the device really left. Test: `threadsDevs(false)` in `test_midiport --threads`: the control thread calls `set_devices` with the same list in a tight loop (about 10^5 calls) while the audio and sender threads run and notes are posted: every posted note must reach the sink once, `dropped_gone == 0`. FAILS-ON-OLD (shown, then reverted): with `set_devices` temporarily put back to "clear every live flag, then refill" the test fails: same list, 2952 notes posted, 70 reached the sink, `dropped_gone` 2882; renumbered, 2968 posted, 78 sent, 2890 dropped. With the fix: 2860 posted / 2860 sent / 0 dropped (same list) and 2846 / 2846 / 0 (renumbered).
- **L2 (renumbered list vs `send`).** Chosen: a TOKEN, not a lock. `thunder_midiout_dev` has `uint64_t token` (struct stays C; `reserved` pads it) and `send` / `clear` take that token instead of an index. The pump reads a cable's token once per message and sends with it, so a renumbering can never make it name another device; a token the shell has just removed is an unknown token: the sink answers `send < 0` (the core counts `send_errors` / `dropped_gone`) and ignores it in `clear`. The contract is in `midiport.h` ("THE DEVICE TOKEN"): no lock is needed between `set_devices` and `pump`; the sink's token-to-device table must be readable from the sender thread while the control thread changes it (the shell's own business); `clock_map` stays lock-free. Tests: `testTokens` (a renumbering between the core's records and the pump: each note on its own token) and `threadsDevs(true)` (renumbered every call, threads): no message on the wrong token.
- **L3 (smoothing rate).** The web calls `mapUpd` from `moClock` (beta index.html:18204, once per pump, the pump runs every 25 ms = 40 Hz while playing), from `io.tick` every 500 ms (:18783), per MIDI-in tick (:18356, which is also the rate the clock-in uses), at 50 Hz while Link is on (:18442), and at record start (:16889): not a fixed rate, but 25 ms is the one that matters for MIDI out while playing. The native shells call `clock_map` once per audio callback (2 to 20 ms), so the smoothing is now `alpha = 1 - 0.98^(dt / 25 ms)` with `dt` = the host time between this call's `host_ns0` and the previous one's (0 .. 2 s): the time constant equals the web's at 25 ms and does not change with the buffer size. The 50 ms jump rule is unchanged. Test `testRates`: a 3 ms step of the host clock, 250 ms later, is the same at 5 ms and at 25 ms call spacing (and equals 3 ms x (1 - 0.98^10)). The case-4 tests use the same formula. Consequence the lead should know: the web's constants (time constant 25 ms / 0.02 = 1.24 s) make the map TRAIL a steady 1000 ppm clock drift by about 1.2 ms (the same in the web at 40 Hz); the drift run of test 1 therefore allows 1.5 ms (it was 0.3 ms with 2 % per 2.7 ms call, i.e. a time constant of 0.13 s, which smoothed the callback jitter 10 times less than the web).

## Decisions
1. **A stem and a MIDI hook refuse each other.** `setMidi` returns false on a stem renderer and `setStem` returns false once a hook is set: the stem's forced heard mask would otherwise reach MidiSched as the audible mask. (`Mixer::setHeard` through `mixer()` is still possible for a caller who bypasses `setStem`; no host does.)
2. **`fxLatSec` is clamped to 0..2 s** before `midi_begin`, so its argument check cannot refuse a block over an absurd plan; if `midi_begin` still refuses, that block makes no MIDI calls at all.
3. **Test 9 compares with the scheduler driven directly** (`runDirect`: the runner's pump, onStep, book, 128-frame blocks, sequencer at time 0), not with `runBlocks` itself: `runBlocks` starts the sequencer at `now + 0.08` after the Play, the renderer's Seq starts at 0. It is the same loop. 18 ledger songs without control actions at block 128; the first five also at 1, 96, 480, 4096. The cases with a STOP / bpm / keys / panic action are not run through the renderer (it has no control side); they stay `midi_ledger`'s. Host-block independence holds because the renderer renders in 128-frame quanta.
4. **Test 10's bus case** uses the two-ports song with a patch 1 -> 3 -> 4 (a chain of two buses). The sequencer plays no notes on a bus (`seq.cpp` `!busT_[t]`), so what is observable on the gear is: soloing the END bus keeps its source on the middle bus (transitive), a solo of the source leaves the unrelated track silent, mute still wins. The expected mask is computed in the test from the web's formula over the edge list (closures walked by hand, not read from `BusPlan`).
5. **Late note on the live-engine route: dropped, like the others.** The web: `coreMsg` (beta index.html ~25325) drops `e.t < ctx.currentTime - 0.15` for the notes the PAGE plays, which are live engines, SoundFonts and MUT / GEN variations; the web's own core plays its sampler notes at once whatever their lateness (`e.core` events `continue` before that line). So for live engines and SoundFonts the native rule is the web's; for the sampler it is the lead's ruling (U36-SPEC 2.5: one rule for pad and MIDI, B7) and differs from the web's core. A dropped live-engine note does not reach `live_.note`, so no node sounds it and nothing is queued; counted in `notesLate`, not in `notesLive`. Tested for sampler, SoundFont and live pads (late 0.16 s dropped, 0.14 s played, flag off played).
   A late mono note on a live pad ends the previous voice with `takeAll` + `live_.take`; the normal live path does NOT end voices for a polyVox pad (`polyVox` takes nothing over). A late note cannot know polyVox without asking the node, so it follows `e.poly` only.
6. **Gone token** (`midiport.cpp`): `cabGoneTok[cable]` next to the mark. `markGone(o, cable, tok)` stores the token then the mark (release) with no compare against the current token (no window). `resolve` reads the mark (acquire), then the cable's token, and says gone only if both marks agree. Same function in the normal send and the CLEAR replay path; `set_devices` clears the mark as before. The race the review found (between compare and store) cannot be entered from a sink callback, so `testGoneToken` pins the outcome: a sink whose send fails and replaces the token inside the call (normal path and replay path); the replacement gets the next note; "control" runs without a replacement show the failed cable stays gone. Mutant: `resolve` ignoring the token fails both replacement checks.

## midiport_threads flake, 21 Nov
**Symptom (CI sanitizers job, PR #273):** `threadsDevs(false)`: posted 2996, sent 2992, `dropped_gone` 0, `send_errors` 0, `dropped_cleared` 0.
**Cause: (a) a real loss, by design and in the TEST'S call order, not a bug in the sweep / purge / gone-token / replay paths.** The four notes were drained while no clock map existed and are counted in `dropped_nomap` (decision 6 of PR A: "drained before the first `clock_map`: dropped"). The test's audio thread called `thunder_midi_process` and THEN `thunder_midiout_clock_map` (the order `midiport.h` documented: "right after thunder_midi_process"); the first posted notes are applied by the first `process`, and a pump that runs in the gap between the two calls (the sender polls every 200 us; sanitizers widen the gap, and a slow first block applies two posts at once = 4 notes) drains them with no map. The failure message did not print `dropped_nomap`, which is why it looked uncounted.
**Reproduced deterministically** (`threadsDevs(false, 1)`, "midiout_flake"): the old order with a 3 ms gap after the FIRST `process`: posted 2984, sent 2980, `dropped_gone` 0 (the same signature); the check `sent + dropped_nomap == posted` holds. Before that, 24 runs of the unchanged test under ASan (two copies at a time) did not reproduce it: the window is microseconds.
**What no other path loses:** I made the accounting explicit: in `threadsDevs` the core's `thunder_midi_stats.sent` (records pushed into its ring; no CLEAR in that run) must equal `sent + dropped_gone + dropped_cleared + dropped_nomap + dropped_late_ticks + queue_full` (ring_full 0). It holds in every run, so no path removes a record without a counter (checked by reading: `resolve` false -> `dropped_gone`; the epoch sweep -> `dropped_gone`; failed send -> `send_errors` and `dropped_gone`; CLEAR -> `dropped_cleared`; full queue -> `queue_full`; no map -> `dropped_nomap`; late tick -> `dropped_late_ticks`). Not exact for CAP_TS runs that CLEAR or replay (a message already counted as sent is counted again as cleared / gone): the ledger check is for the non-TS threads run only.
