# Engine inventory for the C++ core port

Read-only inventory, 10 Nov 2026, build 548 (`index.html` BUILD = 548). Written for a project manager who will cut the port
into tasks. Every row comes from something looked at in the repo on this date; anything not looked at says "not checked".
Line numbers are `index.html` lines unless a file is named. They drift with every build: search the marker / function name.
Sizes are physical lines and KB of text (`index.html` averages about 97 bytes a line, so lines understate effort a little).
Background read first: `NATIVE-PORT-STRATEGY.md`, `NATIVE-DESKTOP-PLAN.md` sections 3, 4, phase 3, `ENGINE-PLUGIN-PLAN.md`
"What the engine is today", `GAIN-STAGING.md`, `tests/README.md`.

Column "runs on": main = page thread; worklet = AudioWorklet (audio thread); Worker = pad-render Worker; offline = an
`OfflineAudioContext` or a Node `vm` run. "Tests" = existing tests or goldens that could prove a port matches. `npm test`
= `node --test tests/*.test.js` (no browser). "Chrome" = needs headless Chrome + playwright, not in `npm test`.

## 0. How the code is laid out (what matters for cutting tasks)

- **`index.html`** is 33,984 lines, 3.28 MB, one big `<script>` (lines 3464 to 33962) plus small script tags that load
  `waves/waves-worklet.js`, `lxr/lxr-engine.js`, `pump/synth/*.js`, `pump/pump-meta.js` and (at the end) `pump/ui/*.js`.
  `NT` = 32 tracks (+ `MT` = the master column), `NI` = 64 instruments, `NPH` = 4096 phrases (lines 17143 to 17149).
- **One JS copy of each piece of DSP is shared by text, not by import.** The ENGINE block (`/* ===ENGINE START=== */` line 3465
  to `ENGINE END` line 8038, 4,574 lines, 381 KB) is sliced out as text and run (a) on the main thread, (b) in the pad-render
  Worker (`new Worker(blob)`, line 8419), (c) in `tools/drums/render.mjs` (Node `vm`). The live engines' worklet code is built
  with `BassCore.toString() + BASS_PROC ...` (line 21344). The track-effect worklet is built from `.toString()` of
  `rvMix`, `DegradeCore`, `VSampCore`, `ResonCore`, `PitchFxCore`, `clkSpb`, `FlexCore`... (line 19071). So there is one source
  per piece, but any C++ replacement has to replace all the places that splice it.
- **`core/seq-core.js` (1,378 lines) is generated**, not hand-written: `tools/make-core.mjs` copies 79 declarations (makeSeq and
  what it reads, about 676 lines) out of `index.html` with acorn and appends `core/core-processor.js` (702 lines, hand-written).
  The source of truth for the sequencer stays in `index.html`.
- **`chains/chains-worklet.js` (5,114 lines, 619 KB) and `waves/waves-worklet.js` (4,995 lines, 594 KB)** share a 3,953-line
  block `/* ===SHARED MODULES START=== ... END=== */` (chains lines 611 to 4563, waves 510 to 4462), copied by
  `tools/sync-shared.py` (chains is the source). Each file also carries one 241 KB base64 line (the `mods.wasm` bytes:
  chains line 4036, waves line 9049), so the real JS is about 378 KB / 353 KB.
- **wasm modules are fetched as files, not embedded** (index.html line 16881: `waves/dsp/thunder-dsp.wasm`,
  `waves/dsp/tfx.wasm`, `pump/pump.wasm`); the comments in `dsp/build.sh` and `dsp/tfx/build.sh` still say "embedded in
  index.html (base64)": stale comments.

## 2. Player and mixer

How a note sounds today: a rendered pad is an `AudioBuffer`; the **page player** starts an `AudioBufferSourceNode` at a future
`ctx.currentTime`, re-pitched with `playbackRate`. With "Sequencer: Audio thread" on, the **core's own sampler** (`Rd`, `Auto`
per voice, output on one of NT+... `AudioWorklet` outputs, one per track) plays the rendered pads instead and sends the rows up
for everything else. Live engines are one `AudioWorkletNode` per track and pad (`bassNode`, `psNode`, `wlNode`). Everything
after the voice is Web Audio nodes.

## 8. Song data the engine reads

**The saved `.thunder` file** (index.html 22708): `JSON.stringify({app:'thunder-project', v:1, build:BUILD, song:{...songOut(S), presets:fullPresets(), irs:irsFull()}, kit:kitToJSON(false)})`.
`songOut(S)` returns `S` unchanged while `NT <= 32` (it only splits tracks above 32 into `songX`). Top-level fields:

- **File:** `app`, `v` (1), `build` (a number; an older app opening a newer build only shows a toast and carries on, line 22831), `song`, `kit`.
- **Song `S`** (from `freshSong`, line 19250, plus the fields `normSong` sets): `app:'thunder-song'`, `v` (6), `flx256`, `gat00`, `name`, `bpm`, `swing`, `swingB`, `limiter`, `renderFrom`, `master`, `mout`, `chainPatch` (the …chains patch, JSON), `song` (256 rows x `NT + 1` ints: chain index per track plus the master column), `chains` (`NPH` entries), `phrases` (`NPH` entries; a row is `RW = 12` ints: 4 note columns, a volume column, instrument, 3 command pairs), `insts` (`NI` = 64; fields include `pad`, `tsp`, `vol`, `pan`, `rev`, `ofs`, `slc`, `smode`, `sync`, `beats`, `grain`, `mo`, `mch`, `mpt`, `pbr`, `cc`, `lcc`, `lsh`...), `mix` (per track: `vol`, `trim`, `pan`, `mute`, `solo`, `sc`, `nm`, `col`), `tfx` (per track effect slots), `mfx` (master effect slots), `mstPump`, `chainOn`, `lpb`, `ticks`, `dlen`, `plen`, `plpb`, `ntr`, `smute`, `tune`, `mst` (mastering: eq, sup, comp, lim), `perf` (scenes, macros, crossfader), `parts`, `presets` (`{voices, layers}`), `secs`, `scale`, `sroot`, `ni`, `sc2`; also `bcol`, `rcol`, `fxPre`, `irs`, `flxOld`, `smuteX` when present.
- **Kit** (`kitToJSON`, line 13291): `{app:'thunder', v:1, name, slots, held, voices:[...], waves}`; a voice (`voiceToJSON`) is the engine block's voice object (`name`, `level`, `tune`, `drive`, `gate`, `len`, `choke`, `sel`, `layers` (8, each with `type`, parameters and `sample`), `fx`, `tail`, the voice filter / amp / LFO / envelope fields `gLpCut...`, `lfo1Rate...`, `env1A...`, `engine` and the engine's own parameter object, `wtData`, `rsData`, `bbExpr`), `waves` the …waves patch doc.

**Where samples live (what was found):**

1. **Embedded in the file.** `kitToJSON(false)` -> `layerToJSON` -> `smpToJSON` writes each sample layer as `sample:{sr, name, id, b64, b64r?}` where `b64` is the mono samples as **16-bit signed PCM, base64** (`smpB64`, line 13261), `b64r` the right channel of a stereo sample. No file paths are written. A song's samples therefore travel inside the `.thunder` JSON. Impulse responses are also inline (`irs: irsFull()` -> `smpToJSON`), as are `presets` audio (`fullPresets()` -> `fullSmp`), `wtData` (loaded wavetables) and `rsData` (resynth analysis).
2. **In the browser, samples live in IndexedDB** (`thunderplus-smp` store `smp`, int16 `pcm` / `pcm2`; `smpPut`, `smpGet`, `idbOpen`), and the kit kept in `localStorage` refers to them by `ref` (`kitToJSON('ref')`). That copy is per device.
3. **Holes to test before promising cross-device songs:** (a) `smpToJSON` returns `{sr, name, ref}` with no audio when `S.data` is not loaded yet ("still loading from IndexedDB"); `saveProj` awaits `presetSmpFill()` (presets only), and I did not find an equivalent wait for the kit's own layers before `projText()`: **not verified**, needs a test with a freshly reloaded page. (b) **SoundFonts are not in the file**: the General MIDI font is fetched from the app (`sounds/FluidR3Mono_GM.sf3`, 24 MB), user `.sf2` / `.sf3` live in IndexedDB `thunderplus-fonts`; a song using one on another device needs that font there. (c) `sounds/ELECTRO.thunder` (856 KB) has 40 voices and **zero** `b64` samples (all synthesised), so it does not exercise sample embedding. (d) The SAMPLE BROWSER keeps a folder handle for browsing only; samples picked from it are loaded into layers and then embedded, not stored as paths (not traced to the end).
4. Size: base64 of int16 is about 2.67 bytes per mono sample, so a 10 s mono 48 kHz sample is about 1.3 MB of JSON text.

The core reads `S` as JSON (`op:'load'`, `'patch'` by `coreDiff`) and the kit as `kv` (per pad: `choke`, `syn`, `rel`, `live`, `sf`) plus rendered buffers; it never reads sample audio from the file itself today.
