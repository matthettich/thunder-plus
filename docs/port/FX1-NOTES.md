Chrome's page player (play('beat'), index.html:21905) ramps a ConstantSource `offset` (no +1 / -1 round trip); native modelled only the core's lane (beat + 1, then + -1.0f: mix.cpp clockBlock) with double ramps. FlexCore reads the clock through clkSpb, which is the slope over blocks: one ulp of the clock moves the estimate by 0.1 sample per block; then D = (p - r) * sp_ differs and every Flex window crossfade differs. Proof: feeding Chrome's per-block spb (39356 values, same song) into native's Flex gives -87.4 dB (from -17.5) on the Flex-only song. - Fix part 2 (next): Chrome's linear ramp float arithmetic. Reverse-engineered from Chrome's own bp per frame (first 1500 blocks, 1497 exact): per chunk of frames [cs, ce) inside a ramp (e -> n): k = f32(1/(n.t - e.t)); vd = f32(f32(n.v) - f32(e.v)); inc1 = f32(f32(k*vd)/sr); inc4 = f32(4*inc1); lane i (0..3) = f32(e.v + f32(f32(f32(cs/sr - e.t) + f32(i*f32(1/sr))) * k) * vd); then value[j] = f32(value[j-4] + inc4) for j in 4..(n - n%4 - 1); the tail frames (n%4) use the lane formula with i = j. Chunks start at the block start or at ceil(event time * sr).
