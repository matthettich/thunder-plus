## Part 2: the live shell

### (a) The page's live protocol (index.html, read at commit `native` base; BASS_PROC / VOX_PROC / XPROC around line 22568, `bassNote` / `kill` around line 21784)

One AudioWorkletNode per track and voice, built from the same core class as the render (`BassCore.toString() + BASS_PROC`). The node never ends itself (`process` returns `true` until a `dispose` message). Parameters:

| lane | rate | what the page writes |
|---|---|---|
| `rate` | a-rate, 0..256 | pitch ratio; a step `setValueAtTime(rate, t)`, or for a slide `setValueAtTime(from, t)` then `linearRampToValueAtTime(rate, t + dur)`; before that `cancelAndHoldAtTime(t)` |
| `gate` | a-rate, 0..1 | `1` at note-on (`setValueAtTime(1, t)`), `0` at note-off (`kill`: `setValueAtTime(0, t)`); a note-on first `cancelScheduledValues(t)` on gate, trig and leg, so a note-off the previous note had booked at or after `t` is taken back |
| `trig` | a-rate | a counter: `++b.n` at every note-on |
| `leg` | a-rate, 0..1 | `1` when the note has a slide (`ev.slide.dur > 0`), else `0`, set at note-on |
| `syl` (vox) | a-rate | the syllable number: `b.sylN++` for a normal note, the current one (`sylN - 1`) for a slide, or a forced `fk`; set at note-on |
| `same` (vox) | a-rate | `1` for a slide (it keeps the syllable it is on), set at note-on |
| `acc` (acid, mach) | a-rate | accent |
| `bpm`, `wob` | **k-rate** | the song tempo and the WOB command (`wob` > 0: beats per wobble cycle instead of the Rate division) |
| `cCut .. oRel` (12) | **k-rate** | the engine targets (commands and LFOs); swapped into the core's parameter object for one quantum (`engOn` / `engOff`) |

Times are seconds (`Math.max(ev.t, ac.currentTime)`), so a value changes at the first sample frame at or after its time.

**Order of operations in a block (`process`, one quantum of 128 samples):**

1. `c.bpm = bpm[0]; c.wob = wob[0]` (k-rate: once per quantum); `engOn(P)` (the engine targets, only when some is not at its default).
2. For every sample `i`: `tg = trig[i]`, `ga = gate[i] >= 0.5`. When `tg !== lt || ga !== lg`: if `i > s` render `[s, i)` with `rate[s]` and set `s = i`; then
   * `tg !== lt && ga` -> `on(leg[i] >= 0.5 [, Math.round(syl[i]), same[i] >= 0.5])` (a new note, or a legato / retrigger when the gate was already high);
   * else `ga && !lg` -> `on(false [, Math.round(syl[i]), false])` (the gate rose with the same counter);
   * else `!ga && lg` -> `off()`;
   * `lt = tg; lg = ga`. (A counter that moves while the gate is low does nothing but is remembered.)
3. `render(L, R, s, n, rate[s])` for the rest of the quantum. 4. `engOff()`.

**Note-on:** a new `trig` with the gate high. Bass: `on(leg)`; legato (`leg >= 0.5` and the voice sounding) keeps the envelope, glides the pitch (`glide` ms) and does not restart the wobble; otherwise the envelope and the wobble delay restart. Vox: `on(leg, n, same)` plans syllable `n mod count`; `same` with a vowel being held does nothing (the slide keeps the vowel); a rest syllable silences the voice.
**Note-off:** the gate falls: `off()` (bass: stage 4, the release; vox: the closing consonants (the coda), then the end segment).
**Retrigger:** a new `trig` with `leg < 0.5` while the gate is high: `on(false)` without an `off()` in between.
**How the tail ends:** the core, not the node. Bass: the release is `env *= exp(-dt*4600/rel)`; below 1e-5 the stage becomes 0 and every block writes zeros. Vox: after the coda's `end` segment the envelope target is 0, `env` below 1e-4 is set to 0 and blocks write zeros. The node keeps running (and costs a render call per quantum that returns zeros).
**The core's own timing:** the control blocks are 32 samples (bass) / 16 (vox, acid, mach) anchored at the `a` of the `render(L, R, a, b, rate)` call; the envelope is linear across a block and the partial amplitudes slide across it, so **a sample depends on its block's end**. `rate` is one number for a whole call.

**Where the page's live result differs from the rendered one today** (measured with the real `process()` code run over the lanes the page schedules, `node native/tools/engine-u26-dump.mjs --page-live`, 92 bass and vox sequences; the rule is the one the shell implements):

1. The page ends a control block at every 128-sample quantum (the call `render(L, R, s, n, ...)` ends at the quantum). A block that is not aligned with the quantum (after a note event at a sample that is not a multiple of 32 / 16 from the quantum start) is cut short, so the envelope and the partials move at the cut. This is block-quantised timing. **69 of the 92 sequences are bit-identical to the rule once the rule also cuts at every 128th sample**, so the cut explains them; against the plain rule they differ by -135 .. -49 dB (bass) and -60 .. -10 dB (vox) relative to the signal's RMS (inaudible to faintly audible; the larger vox numbers are the short `offsets` sequences).
2. `rate[s]` is read once per segment (once per quantum or per note event): a slide or a rate step that is not at a note event reaches the core up to 128 samples late. 18 sequences (bass slides and `offsets` -7.8 .. +1.3 dB, vox glides -7 .. -3 dB: clearly audible, the pitch is in a different place).
3. `bpm` and `wob` are k-rate: they change at a quantum start (up to 127 samples late); the rule applies them at the first control block at or after their sample (the 4 bass sequences whose sound wobbles: -58 .. -28 dB; the other 3 do not wobble and are explained by 1).
4. A note-off and a note-on in the same sample: the page's `cancelScheduledValues(t)` takes the note-off back, so the page sees only the new note (`on(leg)` without an `off()`); the rendered / rule path does `off()` then `on()`. (Measured: `seq_bass_glide_off_early`, -46 dB; for the other sounds the extra `off()` leaves no trace that the following `on()` does not overwrite, they are explained by 1.)
5. The page passes the leg lane's value whatever the state: a note with the leg lane at 1 is `on(true)` also from silence (the core decides).
6. The engine targets (12 k-rate parameters) and the voice's gain / pan stage are page things; the shell does not have them (see the choices).
7. The rendered path is one fixed note (or the whole lyric) at rate 1; it has no legato, no slide and no bpm change. The live path's equivalents are what the sequences test.

### (b) The shell (`core/src/engine/live_shell.h`)

`LiveShell<A>` with `LiveBass`, `LiveVox`, `LiveAcid`, `LiveMach`. A plain object: construction allocates (a voice's lyrics are parsed; ~35 KB of state on the heap or stack), `process()` and `core().set()` (for bass, acid, mach; for vox only when the lyrics change) never do; no locks, no I/O, no exceptions.

```
LiveBass shell(sampleRate);            // or LiveVox ...
shell.core().set(params);              // control thread, between process() calls
shell.process(L, R, n, events, nEvents);   // n any size; runs in chunks of up to 128; events sorted or not, each with at in [0, n)
```

Events (`LiveEvent`): `NoteOn {leg, acc, same, v = syl lane value}`, `NoteOff`, `RateSet {v}`, `RateRamp {v, dur samples}`, `Bpm {v}`, `Wob {v}`, `End` (offline only). An event takes effect at its exact sample: **a note event ends the control block that is running and starts the core's next block at that sample**; a rate / bpm / wob event takes effect at the first control block that starts at or after its sample. Events at the same sample keep their order. At most 256 pending events (`dropped()` counts what did not fit and what lay outside the call), non-finite values are rejected (`rejected()`) and clamped to the AudioParam's range as the page's parameters are (rate 0..256, bpm 10..999, wob 0..64). A core that the JS would have thrown for (a NaN vowel; a vox syllable that is not a whole number) makes the shell silent from then on (`failed()`).

`PageLaneDecoder` turns the page's `gate` / `trig` / `leg` lane values (one sample at a time) into `on(leg)` / `off` exactly as the three lines of `process` do, so a host that has the lanes can feed the shell; it is tested against lanes built the way `bassNote` schedules them.

### (c) THE TEST (`test_live_u26`, ctest `live_u26`)

The shell's output equals the rendered path, bit for bit:

* against the JS cores driven by the rule (`seqRender` in `tools/engine-u26-dump.mjs`, hashes committed in `engine_u26_golden.inc`): **122 sequences** (bass 64, vox 28, acid 15, mach 15): single note, late single note, legato, retrigger (also one sample apart), glide, slides (a rate ramp, also during a legato note), bpm / wob changes, syllable changes (rests, `same`, wrapping), notes whose offsets lie at every edge of the control block (1, 2, 17, 31, 32, 33, 48, 64, 65, 127, 128, 129 ...), a note-off and a note-on in the same sample, notes at sample rate 22.05 kHz; at host block sizes **128, 64, 17, 1** and an uneven pattern (5, 127, 128, 129, 31, 33, 1, 2, 300): every run gives the same hash, and the first `latency()` samples are silent;
* against the rendered path itself: `xeng_bass` (renderBass: one note held, released) and `xeng_vox` (renderVox: the whole lyric, one syllable per note, whose schedule is found by running its own loop, `busy()` included) at two sample rates, several sounds and holds: **32 comparisons**, the same samples up to the final fade (and the trimmed tail is under 1e-4);
* against the rule written once more directly on the cores (random event sequences with same-sample clusters, all four engines, random host blocks of 1 .. 300): **192 runs**;
* the lane decoder and the shell's limits (a full queue, a non-finite value, an event outside the call, a fractional or huge syllable number).

Where the page's live output differs from its render (list above) the shell does **not** copy it: sample-exact = render.

### Choices for the lead to confirm

1. **Latency instead of block-quantised timing.** The output is delayed by `BLK - 1` samples (31 for bass = 0.65 ms at 48 kHz, 15 for vox / acid / mach) so that a control block is only rendered when no later event can cut it. That is what makes the output independent of the host block size and equal to the render. A zero-latency variant would have to end a control block at every host block's end (the page's behaviour) and its sound would depend on the host's block size; it is deliberately not provided. If 31 samples are too much for the bass, the alternative is a cheaper block (not a port of the JS).
2. **A note event cuts the control block, a rate / bpm / wob event does not.** This is what the rendered path does (a note is a `render(a, b)` call) and what the page does at its own note events; the rate is read once per control block (the page: once per segment).
3. **The rate lane is a Web Audio ramp evaluated at the first sample of each control block** (a step or a linear ramp from the value the lane has at the ramp's event). The page's slides are `linearRampToValueAtTime`; the shell samples them 32 / 16 samples apart instead of 128.
4. **Integer sample offsets.** Event times are samples inside the call. The page's times are seconds; the host rounds (a value changes at the first frame at or after its time, as an AudioParam does).
5. **bpm / wob are events**, not k-rate parameters: they apply at the next control block start. The clamps are the AudioParam ranges.
6. **The twelve engine targets (cut / res / dec / atk / rel commands and offsets) are not in the shell.** They are a page feature (`engOn` / `engOff`) that edits the parameter object for one quantum; the shell leaves them to the host (`core().set()` between calls takes effect at the core's position, up to `latency()` samples behind the host clock).
7. **`End` event** (the stream ends at this sample) exists only so that offline use can end the last block as a render does; a live host never sends it.
8. **A shell does not end itself.** After the release the core writes zeros (as in the page) and the shell keeps running; the host decides when to drop it. `failed()` is sticky.
9. **A fixed queue of 256 events**, no allocation; overflow drops (counted) instead of blocking.
10. **Stereo staging:** the shell renders each control block into a 32-float staging pair and copies into a 512-float ring (the latency) per channel; vox writes L = R as the JS does.
11. **Mono vs stereo.** `process` writes L and R (the page's node does); the rendered path mixes to mono `(L + R) * 0.5` after the render; that mix, the trim and the fade are not in the shell.
12. **Interface is provisional and not wired.** Names, the event struct and the `process` signature may change when the mixer / sequencer unit lands; nothing else depends on it.

## Unsupported / not covered

* The engine targets and the track gain / pan stage of the page's live nodes (choice 6).
* A parameter object with a value the page's `normBass` / `normVox` would clamp is clamped by the voice loader (`xeng_voice_from_json`), not by the cores.
* Windows / MSVC and macOS arm64 are exercised by CI only; the committed Linux hashes are the gate on every platform (a platform whose libm differs would fail them, as for U27).

## Least sure

* The `wob` / bpm k-rate difference and the same-sample note-off / note-on case (page differences 3 and 4) are measured with an emulation of the worklet (the real `process()` text with stub `AudioWorkletProcessor`) and not against a browser.
* The shell's latency (choice 1) is the one decision with an audible cost; everything else is a consequence of the rule.
